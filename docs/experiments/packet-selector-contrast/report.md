# 패킷 선별 차이: 실험 결과

## 요약

예정한 12개 대응 계열에서 출발 기록 7개가 유효했고, Jev와 RRF의 첫 전환 패킷 본문과 경쟁 항목이 함께 다른 것은 3/12쌍(25.0%, 정확 이항 95% 구간 5.5~57.2%)이었다. 사전 기준 6쌍에 못 미쳐 H1은 기각한다. 유효한 7쌍에서 Jev가 7개, RRF가 5개를 맞혔으나 이 차이와 비용·시간 차이는 확인 효과로 채택하지 않는다. 현재 Jev 패킷 자동 적용을 보류한다.

## 방법

| 항목 | 값 |
|---|---|
| 설계 | [실험 설계](design.md), 수집 전 커밋 `c225a241` |
| 실행 식별 | 로컬 봉인 파일 SHA-256 `e921b76cbe0b3bd06bf3cd294c104d9d86c40f2d6398e30e96f499675d1486dc`; 별도 실행 시각 ID는 기록하지 않았다 |
| 환경 | [env.json](env.json), 실제 Saturn engine, Codex Luna 출발, Claude Haiku 후속, Jev 1.13.0 |
| 표본 | 예정 12계열·24 target 실행, 실제 유효 계열 7·target 실행 14 |
| 원자료 | [데이터 설명](data/README.md), 로컬 `.runtime/sc/raw`의 26 JSON 파일과 [SHA-256 목록](data/SHA256SUMS) |

각 계열에서 로그 세 개를 별도 출발 입력으로 읽게 하고, 같은 출발 기록 저장소를 두 번 복제했다. 조건 순서를 고정 시드로 섞었고 후속 질문은 동일했다. target 작업 폴더에는 파일을 두지 않았다. 첫 `Switch` 패킷의 실제 캡처·기록 행을 대조했다. 정답은 합성 파일에서 현재 릴리스로 표시된 숫자와 정확히 같은 경우만 인정했다.

## 설계와 다른 점

| 변경 | 시점 | 이유 | 결론에 미친 영향 |
|---|---|---|---|
| 봉인한 `./run.sh verify`는 Python 튜플을 JSON에서 읽은 목록과 직접 비교해 거짓 실패 | 분석 중 발견 | `results/summary.json`의 `competing`·`protected` 배열 표현 차이 | 수집·집계 코드와 원자료는 바꾸지 않았다. [사후 검증기](verify-posthoc.sh)가 JSON 표현으로만 정규화한 뒤 동일 검사들을 통과했다. 봉인 검증기 자체의 통과로 쓰지 않는다 |
| `competing_contrast` 구현이 항목 집합 대신 순서가 있는 목록을 비교 | 분석 중 발견 | 순서만 달라진 두 쌍도 경쟁 항목 차이로 세었다 | 목록 비교 5/12를 원자료에서 집합으로 다시 계산하면 3/12이다. 세 쌍 모두 본문 해시가 달라 H1 공동 조건 3/12과 판정은 변하지 않았다 |
| source가 5계열에서 로그 전문을 `ToolResult`에 남기지 않음 | 수집 중 관측 | Codex가 `wc`만 출력하고 파일 본문은 버리는 명령을 선택한 사례 등 | 계획대로 12계열 분모에 남겼다. 실제 비교는 7쌍이므로 H1 기준 달성이 불가능해졌다 |

## 결과

### 흐름

| 단계 | 수 |
|---|---:|
| 예정 source 계열 | 12 |
| source 재생 실패: 파일 본문 미출력 | 5 |
| 유효 source | 7 |
| 예정 target 실행 | 24 |
| source 실패로 미실행 | 10 |
| 실제 RRF·Jev 대응 실행 | 각 7, 총 14 |
| 첫 패킷 선별 요청대로 적용 | RRF 7/7, Jev 7/7 |

### 확인 분석

| 가설 | 지표 | 값 | 사전 지정 구간·기준 | n | 판정 |
|---|---|---|---|---:|---|
| H1 | 본문 해시와 경쟁 항목 차이, 보호 본문 일치 | 3/12, 보호 본문 불일치 0/7 | 차이 6쌍 이상·불일치 0 | 12쌍 | 기각 |
| H2 | Jev만 정답 대 RRF만 정답 | 2 대 0 | H1 통과 뒤 Jev만 정답이 더 많아야 함 | 12쌍 | 선행 가설 실패로 확인 판정 보류 |
| H3 | Jev−RRF API 환산 비용·시간의 대응 평균 | −$0.000347, −0.95초 | 완전한 12쌍에서 두 95% 구간 상한 모두 0 미만 | 7쌍 | 선행 가설 실패·누락 5쌍으로 보류 |

H1의 정확 이항 구간은 대응 쌍의 차이 유무를 12번의 베르누이 관측으로 보는 범위 표시이며, 작은 합성 표본의 모집단 추정으로 일반화하지 않는다. 원시 결과와 모든 집계는 [summary.json](results/summary.json)에 있다.

### 탐색 분석

첫 패킷 본문 해시가 다른 쌍은 3/12, 경쟁 항목의 ID·형태·생략 사유 집합이 다른 쌍도 3/12였다. 봉인된 집계 코드의 순서 포함 비교값은 5/12이며, 나머지 두 쌍은 항목 순서만 달랐다. 본문이 실제로 다른 3쌍 중 2쌍에서 Jev만 정답이었고 1쌍은 모두 정답이었다. Jev가 골라 남긴 현재 로그가 후속 답에 도움이 될 가능성을 보여 주지만, 사전 H1 실패와 작은 표본 때문에 채택 근거는 아니다.

수집된 7쌍의 첫 패킷 본문 합계는 RRF 13,583바이트, Jev 13,576바이트였다. 공식 API 단가 환산 후속 비용 합계는 RRF $0.17548087, Jev $0.17305469였다. 대응 평균 Jev−RRF 비용의 계열 bootstrap 95% 구간은 −$0.001028~+$0.000332, 시간은 −2.59~+0.38초로 모두 0을 지난다. Jev 판단 행은 RRF 7개, Jev 21개였다. 이는 실제 구독 청구액이 아니다.

## 논의

### 해석

인위적으로 낮춘 패킷 예산에서도 Jev와 RRF의 실제 전송 본문은 대부분 같거나 source 기록 자체가 유효하지 않았다. Jev가 더 맞힌 두 사례는 실제 선택 차이와 연결되지만, 12계열의 사전 문턱과 비용·시간 문턱을 통과하지 못했다. 따라서 현재 설정의 Jev 선별을 기본 압축 전략으로 승격할 근거는 없다. 제브 모델이 모든 맥락 판단에 무용하다는 결론도 아니다.

### 타당성 위협

| 종류 | 위협 | 이 실험에서 |
|---|---|---|
| 내적 | 모델 출력 변동과 조건 순서 | 같은 source를 복제하고 조건 순서를 섞었으나 각 조건 한 번씩이라 출력 변동이 남는다 |
| 구성 | 낮춘 창 설정이 실제 사용자 분포와 다름 | `context.safety_percent=5`, Claude 창 100,000으로 차이를 유도했다. 자연 사용 효과가 아니다 |
| 외적 | 합성 로그, 한 provider 방향과 작은 표본 | Codex→Claude의 숫자 찾기만 측정했다. 같은 session 압축과 실제 작업 완료를 대표하지 않는다 |
| 계측 | 구독 사용량과 API 단가 환산의 차이 | 공식 단가를 2026-10-06 값으로 고정했다. 실제 청구액·캐시 정책 차이는 계산하지 못한다 |

### 한계

- source 5계열은 실패 원인을 남겼지만 target을 재시도하지 않았다. H1을 다시 보려면 새 설계를 먼저 봉인해야 한다.
- 패킷 캡처는 engine이 provider 호출 직전에 가진 본문의 증거다. provider 수신 사실까지 증명하지 않는다.
- 원자료는 로컬에 보관해 공개 저장소만으로 완전 재현할 수 없다. 공개 해시가 원자료의 변경 여부를 확인한다.

## 재현

```sh
./run.sh analyze
./verify-posthoc.sh
```

봉인된 `./run.sh verify`는 앞서 적은 표현 형식 결함으로 실패한다. 사후 검증기는 그 형식 한 곳만 정규화한다. 봉인·시도 장부·도구 결과·패킷 캡처·선별 적용·target 도구 미사용·분석 결정성을 확인했고, 분석 두 번의 `results/summary.json` 바이트가 같았다.

|---|---|
