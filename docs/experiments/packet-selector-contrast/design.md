# 패킷 선별 차이: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#540](https://github.com/woonyong-choi/saturn/issues/540) |
| 관련 설계 | [맥락 고르기](../../design/context-selection.md), [보존 우선 비교](../context-preservation/design.md) |
| 사전 데이터 | 보존 우선 비교의 실제 12칸에서 RRF/Jev 전송 본문이 여섯 쌍 모두 같았다. 별도 탐색 진단에서 실제 도구 결과 세 개와 낮은 고정 패킷 예산을 쓰자 Jev가 현재 로그를 남기고 RRF가 빼는 한 사례가 나왔다. 그 사례와 시드는 이 실험에 넣지 않는다. |

## 질문

실제 Saturn engine의 도구 결과 경쟁 구역에서 Jev 선별이 RRF와 다른 근거를 전달하는가? 다른 패킷이 실제 후속 답의 정확도, 전송량, 완료 시간, 공식 API 단가 환산 비용에 어떤 차이를 만드는가?

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | 두 조건의 첫 전환 패킷 본문 해시와 선택된 경쟁 항목이 함께 다른 대응 쌍이 12쌍 중 6쌍 이상이며 보호된 사용자·assistant 본문은 모두 동일하다. | 아래의 인위적 예산 압박 계열 |
| H2 | Jev에서만 정답인 쌍이 RRF에서만 정답인 쌍보다 많다. | Codex→Claude, 단일 후속 질문 |
| H3 | Jev의 공식 API 단가 환산 비용과 벽시계 시간이 RRF보다 모두 작다. | 출발 세션을 공유한 대응 실행의 후속 요청 |

## 설계

| 항목 | 값 |
|---|---|
| 조건 | R: 기본 RRF 패킷, J: `context.select.packet=jev` 패킷. 두 조건 모두 `context.safety_percent=5`, `provider.claude.context.window=100000`이며 근거 재조회는 끈다 |
| 배정 | seed 54026006으로 12계열을 만든다. 현재 로그의 파일 위치는 `build.log`, `archive.log`, `deploy.log`에 각각 네 번씩 배정한다. 계열별 R/J 실행 순서는 같은 seed로 섞는다 |
| 눈가림 | 작업 모델에게 조건명과 기대 숫자를 주지 않는다. 채점기는 모델·조건을 입력으로 쓰지 않는다 |
| 환경 | source Codex `gpt-5.6-luna`, target Claude Haiku `claude-haiku-4-5-20251001`, router `jev-1.13.0`. CLI 버전, engine 바이너리 SHA-256, 코드 해시와 공식 가격표를 수집 전에 봉인한다 |

각 계열은 서로 다른 세 파일을 가진다. 각 파일 첫 줄에 현재 또는 지난 릴리스의 서로 다른 timeout 숫자를 넣고, 그 뒤에 고정 길이의 무관한 기록을 둔다. source 모델에게 파일 하나씩 세 차례 읽게 하고 `READY`만 답하게 한다. 실제 `ToolResult`에서 세 파일의 표지가 모두 확인되지 않으면 두 조건 모두 재생 실패로 남긴다. 같은 완료된 source 기록 저장소를 복제해 R/J를 각각 한 번 실행한다. target에게 현재 릴리스 timeout 숫자 하나만 묻고 도구 사용을 허용하지 않는다. 도구 사용 시도와 추가 session 전환은 기록한다.

패킷 예산은 탐색 진단에서 차이가 나온 값을 고정한 인위적 압박 조건이다. 실제 사용 빈도나 자연 분포를 대표하지 않는다. Jev 선별의 가능한 효과를 확인하는 진단이며 기본값 승격 시험이 아니다.

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `packet_contrast` | 측정 | 첫 `Switch` 패킷의 SHA-256이 두 조건에서 다른지 | 쌍 |
| `competing_contrast` | 측정 | 첫 패킷의 경쟁 항목 ID·형태 집합이 다른지 | 쌍 |
| `protected_match` | 측정 | 첫 패킷의 User·Assistant 항목의 역할·원문 해시·순서가 같은지 | 쌍 |
| `applied` | 측정 | 요청한 `rank`·`compact`가 대체 없이 기록됐는지 | 실행 |
| `success` | 측정 | 첫 후속 답이 숨긴 현재 timeout 숫자와 정확히 같은지 | 실행 |
| `packet_bytes` | 측정 | 첫 패킷 본문 바이트 수 | 바이트 |
| `usage` | 측정 | target provider와 router의 보고 토큰. 미보고는 null | 토큰 |
| `api_equivalent_cost` | 파생 | 공식 API 단가로 환산한 후속 실행 비용. 구독 청구액은 아니다 | USD 또는 null |
| `duration` | 측정 | 후속 입력부터 완료·실패까지의 벽시계 시간 | 초 |

## 표본

| 항목 | 값 |
|---|---|
| 출처 | 기존 진단과 겹치지 않는 seed 54026006의 합성 계열 12개 |
| 크기 | 계열 12개 × 조건 2개 = 24실행 |
| 크기 근거 | 선별 차이와 전달 경로의 진단 예산. 제품 품질 보장을 위한 검정력은 없다 |
| 중단 규칙 | 12계열 또는 provider 입력 120회·Jev 호출 120회 중 먼저 도달한 때. 누락·실패는 예정 분모에 둔다 |
| 반복과 예열 | 조건마다 계열별 한 번, 예열 없음. 오류·시간 초과·결과 불명은 자동 재전송하지 않는다 |

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | `packet_contrast`, `competing_contrast`, `protected_match` | 예정 12쌍의 수를 직접 센다 | 두 차이가 함께 난 쌍 6쌍 이상, 보호 본문 불일치 0쌍. 실패하면 H2·H3는 원인 효과로 해석하지 않는다 |
| H2 | `success` | 대응 불일치 Jev만 정답 `b`, RRF만 정답 `c`와 `b-c`를 보고한다. 이항 정확 95% 구간은 탐색값이다 | 진단 후보는 `b>c`일 때만. 제품 승격 근거로 사용하지 않는다 |
| H3 | `api_equivalent_cost`, `duration` | 수집된 완전한 대응 쌍의 J−R 차이와 계열 단위 bootstrap 10,000회, seed 54026006 | 두 차이의 95% 구간 상한이 모두 0 미만일 때만 효율 후보. null과 실패가 있으면 보류 |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 없음. source 재생 실패와 패킷 미전달을 각각 별도 상태로 예정 분모에 둔다 |
| 실패한 실행 | 300초 제한, 작업 실패, 빈 답, 미적용은 오답으로 센다. 전송 결과 불명은 재시도하지 않는다 |
| 다중 비교 | 세 가설은 순서대로 판정하고 하나라도 실패하면 후속 가설은 탐색 수치만 보고한다 |

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | 세 가설 모두 통과하면 독립 실과제 확인 평가를 설계한다. 기본값은 그대로 둔다 |
| 기각 | 패킷 차이·품질·효율 중 하나가 기준을 못 채우면 현행 Jev 패킷 자동 적용을 보류한다 |
| 보류 | 누락과 넓은 구간의 원인을 기록하고 지원 범위를 다시 정한다 |

## 탐색 분석

- 파일 위치별 정답, Jev 선별에서 제외한 바이트와 provider 입력 토큰, 추가 session 전환을 분리한다.
- 후속 답이 같은 본문인데 달라진 경우는 실행 변동으로 구분한다.

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
| 내적 | 모델 출력 변동과 R/J 실행 순서 | 대응 source 스냅샷, 순서 무작위화, 패킷 해시 대조 |
| 구성 | 낮춘 창 설정이 실제 사용자 분포와 다름 | 인위적 압박 진단으로만 해석하고 기본값을 바꾸지 않음 |
| 외적 | 합성 로그, 하나의 provider 방향과 작은 표본 | 실제 작업·양방향의 독립 확인 평가 전에는 일반화하지 않음 |
| 계측 | CLI 구독 사용량과 API 단가 환산의 차이 | 공식 단가·조회일 고정, 실제 청구액 주장 금지, null을 0으로 채우지 않음 |
