# Jev 좁은 의미 판단: 개발 실험 결과

## 요약

실제 인간 검토 확정 24건에서 새 지속 제약 질문은 16건을 맞혀 기존 Jev 점수의 22건보다 나빴다. 생성 관찰의 확인 80건에서는 Jev와 문자 유사도 코드가 모두 60건을 맞혀 정확도 차이가 0%p였다. Jev 반복 행동 구간은 156/160건(97.5%, Wilson 95% [93.7, 99.0]%) 일치했지만 정확도 이득은 없었다. 두 역할 모두 자동 적용하지 않는다.

## 방법

| 항목 | 값 |
|---|---|
| 설계 | [실험 설계](design.md), 수집 전 커밋 `b8218811` |
| 실행 id | `20261007T040637Z-b821881` |
| 환경 | [env.json](env.json), HTTPS 응답 모델 `jev-1.13.0` |
| 표본 | 예정·실제 모두 인간 검토 40건, 생성 관찰 120건, 두 반복 320호출 |

제약 질문은 입력 문장만 제공하고 여러 별도 작업에 지속되는 규칙인지 물었다. 기존 Jev 점수는 이전 실험이 보존한 값이다. 따라서 두 질문의 맥락과 시점이 달라 모델 능력만 분리한 대응 비교가 아니다. 관찰 질문에는 두 문장만 제공하고 실행·검사·결과가 모두 같은지 물었다. 문자 3-gram Jaccard 경계 0.30은 개발 주제 10개의 40쌍에서 고른 뒤 확인 주제 20개의 80쌍에 적용했다.

## 설계와 다른 점

| 변경 | 시점 | 이유 | 결론에 미친 영향 |
|---|---|---|---|
| 종류별 오류와 0.8 경계의 참고 집계 추가 | 수집 후 | Jev 오답의 위치 확인 | 탐색 분석만 사용. 수집 전 H2의 0.5 기준과 판정은 유지 |
| 생성 형식 전용 구조 파서 추가 | 결과 확인 뒤 | 실행 번호·파일·검사·결과가 추출 가능하면 코드로 구분되는지 확인 | 사후 탐색만 사용했다. H2의 사전 코드 기준선은 바꾸지 않았다 |

## 결과

### 흐름

| 단계 | 수 |
|---|---:|
| 예정·예약·실제 호출 | 각 320 |
| HTTP·형식 성공 | 320 |
| 실패·제외 호출 | 0 |
| 인간 확정·판단 보류 | 24·16 |
| 관찰 개발·확인 | 40·80 |

모든 원자료를 보존했다. 예약과 응답의 일대일 대응, 입력 파일 해시, 집계 재실행의 바이트 일치가 통과했다. 키 형태 문자열은 원자료에서 발견되지 않았다.

### 확인 분석

| 가설 | 값 | 사전 기준 | 판정 |
|---|---|---|---|
| H1: 지속 제약 좁은 질문 | 새 질문 16/24, 기존 22/24. 기존만 정답 8, 새 질문만 정답 2 | 새 질문 정답 3건 이상 증가 | 개발 기준 미충족 |
| H2: 동일 관찰 | Jev 60/80, 코드 60/80. Jev만 정답 20, 코드만 정답 20. 차이 0%p, 주제 군집 95% [0, 0]%p. Jev 동일 관찰 누락 0/20 | 차이 ≥5%p·구간 하한 >0·누락 ≤4 | 미충족 |
| H3: 반복 행동 구간 | 156/160, 97.5%, Wilson 95% [93.7, 99.0]% | 점추정 ≥90%·하한 ≥85% | 충족 |

H2의 균형 잡힌 쌍은 주제마다 Jev만 맞힌 쌍과 코드만 맞힌 쌍이 하나씩이라 군집 재표집의 차이가 모두 0이었다. 이 구간이 0이라는 사실은 실제 업무 분포에서도 두 방법이 같다는 뜻이 아니다.

### 탐색 분석

| 관찰 쌍 종류 | 수 | Jev 예(0.5 이상) | Jev 예(0.8 이상) |
|---|---:|---:|---:|
| 같은 실패를 바꿔 씀 | 20 | 20 | 20 |
| 같은 실행의 다른 검사 | 20 | 20 | 0 |
| 다른 실행의 비슷한 실패 | 20 | 0 | 0 |
| 같은 검사의 반대 결과 | 20 | 0 | 0 |

0.8 경계를 결과를 보고 골랐다면 이 생성 자료에서는 80/80 정답이 된다. 이는 사후 탐색이며 H2의 판정을 바꾸지 않는다. 새로운 문장 형태와 실제 관찰에서 기준을 고정한 채 확인해야 한다. 사람의 `unsure` 16건에는 새 Jev가 절반 기준으로 예 10건을 냈지만 정답은 확정할 수 없다.

같은 문장 틀에 맞춰 실행 번호·파일·검사 이름·성공 또는 실패를 추출하는 사후 코드 파서도 80/80을 맞혔다. 생성기에 맞춘 파서이므로 실제 로그 성능으로 일반화하지 않는다. 이 결과는 구조화된 실행 필드가 있으면 Jev 없이도 이 시험의 구분을 할 수 있다는 설계 단서다.

Jev는 320호출에서 입력 149,508토큰과 출력 7,040토큰을 보고했다. 요청당 지연 중앙값은 340.0ms, 95분위는 471.6ms였다. 병렬 수집이므로 합산 지연을 제품 응답 시간으로 보지 않는다. 코드 기준선에는 Jev 호출 토큰이 없다. 후속 작업 LLM의 토큰·완료 품질·재작업은 이번 개발 검사에서 측정하지 않았다.

## 논의

### 해석

Jev는 생성 문장에서 성공·실패와 실행 번호의 차이를 안정적으로 구별했다. 같은 실행의 다른 검사에서 20건을 잘못 합친 것은 Saturn의 관찰 중복을 자동 병합하기에 치명적이다. 구조화된 실행 ID·검사 ID·종료 상태가 있는 관찰은 먼저 코드로 비교하고, 빠진 메타데이터가 있는 자연어 관찰만 별도 확인 대상으로 남기는 편이 낫다.

지속 제약은 입력 문장만으로 분리한 질문이 기존 맥락 포함 점수보다 악화됐다. 이 결과는 작은 질문을 더 많이 만들수록 성능이 좋아진다는 가설을 지지하지 않는다. 현재는 작업 LLM이 후보의 맥락을 함께 읽고 제안하는 경로를 유지한다.

Saturn의 대안 경로는 실행 관찰의 ID·도구 종료 상태·검사 이름을 기록 저장소에서 직접 비교하고, 자연어 근거는 원문 ID로 다시 찾는 것이다. 같은 provider 세션의 길이 관리는 해당 provider가 지원하는 압축을 기준선으로 삼는다. provider를 바꾸거나 세션을 다시 열 때만 Saturn이 목표·남은 일·검증 결과와 원문 위치를 묶은 패킷을 만든다. 이 경로도 독립적인 후속 작업의 품질·비용 실험을 통과하기 전에는 우수하다고 단정하지 않는다.

### 타당성 위협

| 종류 | 위협 | 이 실험에서 |
|---|---|---|
| 내적 | 인간 검토층과 이전 Jev 점수를 이미 열람 | H1은 탐색으로만 해석했다. 실제 호출 전 정답과 이전 점수를 Jev 요청에서 뺐다 |
| 구성 | 문장 틀의 정답이 실제 관찰 중복을 대표하지 않는다 | H2는 생성 기능 검사다. 실제 업무 효과 판정에 쓰지 않았다 |
| 외적 | 한 사용자의 한국어 입력과 합성 개발 로그 | Claude·Codex·혼합어 성능으로 일반화하지 않았다 |

### 한계

- 인간 검토 40건은 어려운 사례 위주이며 16건은 사람도 판단을 보류했다.
- 제약 새 질문의 맥락은 이전 점수의 맥락과 다르다.
- 문자 유사도는 최소 코드 기준선이다. Saturn의 구조화된 실행 필드를 비교하는 코드와 대조하지 않았다.
- 관찰 확인층은 생성 문장 규칙을 공유한다. 0.8의 사후 발견은 독립 검증이 아니다.
- 실제 사용자 작업 완료, 캐시, 총비용은 측정하지 않았다.
