# 맥락 선별 순효과 측정: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#7](https://github.com/woonyong-choi/saturn/issues/7) |
| 관련 설계 | [맥락 정리](../../design/context-management.md), [맥락 고르기](../../design/context-selection.md), [설정](../../design/settings.md), [provider 연결과 session](../../design/providers-and-sessions.md) |
| 사전 데이터 | 이 실험의 실행기가 동작하는지 확인한 예비 실행 9건(시드 9001, Claude 4조건, Codex 4조건, Claude에서 Codex로 전환 1조건)을 수집 전에 열람했다. 이 실행으로 소켓 경로 길이, 동시 시작 한도, Claude 자동 메모리 차단, 전환 창 조작, Codex 응답 조각 이어 붙이기를 고쳤고 조건별 `t_abs`를 정했다. 예비 시드는 표본에 넣지 않고 분석하지 않는다. 같은 세션 축약 비교([#529](https://github.com/woonyong-choi/saturn/issues/529), [same-session-compaction](../same-session-compaction/report.md))의 결과를 열람했고 그 합성 코드 회수 과제와 겹치지 않게 과제를 새로 만들었다. 대응 실행 검증기([#540](https://github.com/woonyong-choi/saturn/issues/540))의 오프라인 결과는 참조만 한다. |

## 질문

Saturn이 맥락을 정리할 때 provider 기본 압축 대신 Saturn 패킷(RRF 순서, Jev `compact` 판단 순서)을 쓰면, 같은 기록과 같은 후속 작업에서 품질을 유지하면서 캐시 손실과 Jev 호출을 포함한 전체 토큰과 시간이 줄어드는가. 맥락 정리를 하지 않는 조건을 함께 두어 정리 자체의 순효과를 같은 표에서 본다.

이 실험은 새 session으로 옮기는 층만 비교한다. 같은 session 안에서 도구 결과를 지우는 개입은 Saturn 패킷 경로가 아니다. 그 효과는 [#529 결과](../same-session-compaction/report.md)를 참조하고 이 실험의 새 패킷 효과로 대신하지 않는다. 같은 session 안에서 Saturn이 판단 순서를 개입시키는 경로는 지원하지 않으므로 이 실험은 그 칸을 `미지원`으로 보고한다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | 후속 작업 3개를 모두 통과한 비율(`composite`)에서 `rrf`와 `jev` 각각이 `provider`보다 낮지 않다. 대응 차이의 95% Newcombe 구간 하한이 0 이상이다(허용폭 0). | 트랙 `claude`, `codex`, `claude-codex` 각각 |
| H2 | `rrf`와 `jev` 각각의 경계 뒤 전체 비용과 전체 시간이 `provider`보다 줄어든다. 두 차이의 95% 시드 단위 bootstrap 구간 상한이 모두 0 미만이다. | 같은 트랙 |
| H3 | `rrf`와 `jev`는 `none`보다 `composite`이 낮지 않다(허용폭 0, H1과 같은 구간). | 트랙 `claude`, `codex` |
| H4 | `jev`는 `rrf`보다 `composite`이 낮지 않고(허용폭 0) 전체 비용이 줄어든다. | 트랙 `claude`, `codex`, `claude-codex` |
| H5 | 기록된 `compact` 요청을 5번 다시 보냈을 때 기록된 응답과 합친 6개 응답에서 패킷에 들어간 항목 집합이 모두 같고 항목별 확률 폭이 0.10 이하인 요청의 비율은 Wilson 95% 하한이 90% 이상이다. | `jev` 조건의 `compact` 요청 전체 |
| H6 | `jev` 조건의 패킷 중 판단이 실제로 적용된(경쟁 구역 항목이 `compact` 판단 순서로 채워진) 비율은 Wilson 95% 하한이 90% 이상이다. | `jev` 조건 |

전체 판정은 [판정](#판정)에 있다. 효과 크기는 가설과 별개로 모두 보고한다.

## 설계

| 항목 | 값 |
|---|---|
| 조건 | `none`: 경계에서 아무것도 하지 않고 같은 session을 이어 간다. `provider`: 정리 모드 `context.mode=provider`로 두고 경계에서 provider 압축(`/compact`)을 보낸 뒤 같은 session을 이어 간다. `rrf`: 경계에서 새 session을 패킷으로 열고 경쟁 구역을 후보 순위(RRF) 순서로 채운다(`context.select.packet=rrf`). `jev`: 같은 경계에서 경쟁 구역을 `compact` 판단 순서로 채운다(`context.select.packet=jev`). |
| 트랙 | `claude`: Claude로 쌓고 Claude로 잇는다(4조건). `codex`: Codex로 쌓고 Codex로 잇는다(4조건). `claude-codex`: Claude로 쌓고 경계에서 `/model codex`로 Codex에 넘긴다. Codex에는 이어 갈 session이 없어 `none`이 없고 `provider`, `rrf`, `jev` 3조건이다. `provider` 조건은 경계 전 Claude에 `/compact`를 보내 압축 요약을 만든 뒤 전환해 [#122](https://github.com/woonyong-choi/saturn/issues/122)의 요약 전달 경로를 잰다. |
| 경계 | 모든 조건이 같은 입력 8개(설정 입력 7개와 경계 입력 1개)를 같은 문장으로 받은 뒤 갈라진다. 경계 입력의 접속 설정(`-c`)에만 `provider.<id>.context.t_abs=20000`을 걸어 턴 끝 판정이 새 session을 열게 한다(`rrf`, `jev`). 20000이면 패킷 크기 상한 `P_max = T / 10`이 2000토큰이라 경쟁 구역 후보(예비 실행에서 도구 호출 27개 안팎)가 예산보다 많다. 제품 기본(`t_abs` 200000, `P_max` 20000)은 후보가 예산에 모두 들어가는 크기라 이 규모의 세션에서는 선별이 일어나지 않는다. 그래서 세션 길이와 기준을 같은 비율로 줄여 후보가 예산의 4배 안팎인 상태를 만든다. 긴 세션의 절대 길이는 이 실험이 다루지 않는다. |
| 후속 작업 | 경계 뒤 3개를 순서대로 보낸다. F1은 피드의 원인대로 코드를 고치게 한다(헤더 이름은 정정한 값, 타임아웃은 피드의 값). F2는 피드의 티켓 번호를 묻는다. F3은 지표 덤프에서 p99가 가장 큰 엔드포인트를 코드에 넣게 한다. 3턴을 모두 재서 새 session의 캐시 쓰기를 이어지는 턴이 얼마나 되갚는지 포함한다. |
| 배정 | 시드 7007과 트랙 이름으로 (프로젝트, 조건) 쌍의 실행 순서를 섞는다. 같은 프로젝트의 조건은 같은 시작 저장소와 같은 입력을 받고 각자 새 저장소, 새 `SATURN_HOME`, 새 채팅에서 실행한다. |
| 눈가림 | 정답(숨긴 값, 티켓 번호)은 Saturn 기록, router 요청, 에이전트에게 보이지 않는 `hidden/`과 `feed/` 밖에 있다. 채점기는 조건 이름을 읽지 않는다. 입력 문장은 조건과 무관하게 같다. |
| 환경 | macOS, 로컬 `saturn`과 `saturn-engine` 릴리스 빌드(실행 커밋은 `env.json`), Claude Code, codex-cli, router Jev 1.13.0(키체인 `saturn-verify-router`를 수집 명령 안에서만 읽어 환경 변수로 넘긴다). 모델은 Claude `haiku`, Codex `gpt-5.6-luna`이고 실제 보고된 모델 이름은 사용량 행에서 읽는다. 권한 모드는 `full`(키 보호는 켜져 있다). Claude 자동 메모리가 세션 사이로 사실을 옮기지 않게 시작 저장소의 `.claude/settings.json`에 `autoMemoryEnabled: false`를 둔다. 기존 사용자 설정과 로그인은 건드리지 않으며, Claude Code는 실행 폴더마다 자기 기록을 사용자 폴더에 남긴다. |

### 시작 저장소와 후속 작업의 과제

프로젝트마다 시드로 작은 Python 서비스 저장소를 생성한다([fixtures.py](scripts/fixtures.py)). 실제 코드 수정, 구버전과 새 규칙의 충돌, 긴 출력 중간의 근거, 한 번만 읽히는 근거를 다음처럼 넣는다.

| 요소 | 내용 | 검사하는 것 |
|---|---|---|
| 실제 코드 수정 | F1은 `app/config.py`의 헤더 이름과 타임아웃을, F3은 `app/report.py`의 상수를 고친다. 공개 시험 5개가 계속 통과해야 한다. | 숨긴 검사가 값과 공개 시험을 읽는다 |
| 구버전 충돌 | 입력 3에서 `X-Req-Id`를 규칙으로 정하고, 입력 6에서 시드별 새 이름으로 정정한다. README와 코드는 옛 이름을 가진다. | 정정한 이름이 패킷, 압축 요약, 원래 맥락에서 살아남는가 |
| 한 번만 읽히는 근거 | `tools/incident.sh`는 작은 피드(티켓 번호와 필요한 타임아웃)를 한 번만 출력하고 지운다. 읽는 입력은 `읽음`만 답하게 해 답 글에 근거가 남지 않는다. | 선별이 이 호출을 남기는가. 다시 실행해도 얻을 수 없다 |
| 긴 출력의 중간 근거 | `tools/dump-metrics.sh`는 엔드포인트 58개 표를 출력하고 p99가 가장 큰 행이 중간에 있다. 다시 실행하면 같은 출력이 나온다. | 근거가 잘리거나 빠졌을 때 재조회(다시 실행)로 되살리는 횟수와 비용 |
| 읽기만 하는 방해 호출 | README, 구조 문서, 소스 두 개, 테스트 실행, 파일 목록 | 후보가 예산을 넘게 만든다 |

설정 입력 7개와 경계 입력의 문장은 [plan.py](scripts/plan.py)에 고정한다. 재조회 권한은 모든 조건에서 같다. 에이전트는 기본 도구(파일 읽기, 셸)를 모두 쓸 수 있고 `context.evidence.lookup`은 모든 조건에서 꺼 둔다. 따라서 근거가 빠지면 복구는 도구 재실행뿐이고, 한 번만 읽히는 피드는 복구할 수 없다.

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `arm` | 조작 | `none`, `provider`, `rrf`, `jev` | 범주 |
| `f1`, `f2`, `f3` | 측정 | F1: 헤더 이름, 타임아웃 값이 숨긴 값과 같고 `RETRIES`가 2이며 공개 시험이 통과한다. F2: 티켓 번호가 답 글에 있다. F3: 상수가 숨긴 엔드포인트이고 F1의 값이 유지되며 공개 시험이 통과한다. | 0/1 |
| `composite` | 파생 | `f1`, `f2`, `f3` 모두 1 | 0/1 |
| `provider_cost` | 파생 | 경계 입력 끝 이후에 시작한 실행의 입력 + 캐시 쓰기 배수 × 캐시 쓰기 + 0.1 × 캐시 읽기 + 5 × 출력. 캐시 쓰기 배수는 Claude 1.25, Codex 1.0([설정](../../design/settings.md)). Claude 사용량은 턴 값의 합, Codex는 thread 누적값의 구간 차이. 두 provider를 쓰면 provider별로 계산해 합한다. 출력 배수 4와 8의 값을 민감도로 함께 낸다. | 가중 토큰 |
| `router_tokens` | 측정 | 같은 구간의 router 판단 입력과 출력 토큰 합(입력 판단과 `compact` 판단 모두). | 토큰 |
| `total_cost` | 파생 | `provider_cost` + `router_tokens`. router 토큰을 같은 단가로 더하는 것은 가정이며, 분리한 값도 보고한다. | 가중 토큰 |
| `window_seconds` | 측정 | 경계 입력 끝에서 F3 실행 끝까지의 벽시계 시간. 새 session 열기, `compact` 판단 대기, 패킷 전달 턴을 포함한다. | 초 |
| `tool_calls`, `metrics_reruns`, `incident_reruns` | 측정 | 경계 뒤 도구 호출 수, 지표 덤프 재실행 수, 피드 재실행 수(복구 시도 횟수) | 개수 |
| `incident_form` | 측정 | 패킷에서 피드 호출 항목이 들어간 형태(`Full`, `Digest`, `Path`)나 빠진 이유(`dropped:budget`) | 범주 |
| `jev_applied` | 측정 | 패킷의 경쟁 구역에 `selector=compact`로 들어간 항목이 하나 이상이다. | 0/1 |
| `restarts`, `packet_tokens` | 측정 | 경계 뒤 새 session 패킷 수와 추정 토큰 | 개수 |

비용의 원자료(입력, 캐시 읽기, 캐시 쓰기, 출력, router)도 가중 없이 보고한다. Jev 확신도는 후속 작업 성공 확률로 쓰지 않는다. 모델 합의가 아니라 숨긴 값과의 일치가 정답이다.

## 표본

| 항목 | 값 |
|---|---|
| 출처 | 시드 1부터 12까지 생성한 합성 서비스 저장소 12개(`claude`, `codex` 트랙)와 시드 1부터 8까지(`claude-codex` 트랙). 저장소마다 숨긴 값(티켓 번호, 정정 헤더 이름, 타임아웃, 가장 느린 엔드포인트)이 다르다. 프로젝트 단위로 분리해 한 프로젝트의 조건은 서로 짝이고 다른 프로젝트와 섞이지 않는다. 예비 시드 9001, 9002는 쓰지 않는다. |
| 크기 | `claude` 12 x 4 = 48, `codex` 12 x 4 = 48, `claude-codex` 8 x 3 = 24, 합계 120 trial |
| 크기 근거 | 예산. 후속 3턴과 설정 8턴을 실제 engine에서 돌리는 trial 하나가 provider 요청 11~12개와 router 판단 12개 안팎이다. 이 표본의 대응 차이 구간은 넓다(12쌍에서 두 방식이 같으면 `composite` 차이 95% 구간이 약 ±0.2 안팎). 허용폭 0을 증명하려면 한쪽이 확실히 앞서야 하고, 품질이 포화되어 같으면 판정은 `보류`가 된다. 이것은 허용폭을 느슨하게 하지 않기 위한 의도된 결과이며, 채택이 필요하면 더 큰 표본을 새로 사전 등록한다. |
| 호출 상한 | provider 요청: `claude` 트랙 700, `codex` 트랙 700, `claude-codex` 트랙 400(예상 약 540, 540, 270). router 판단: 엔진 호출 1800(예상 약 1450)에 `compact` 재전송 150을 더한다. |
| 중단 규칙 | 호출 상한 도달, 인증 거절, 키 문자열이 원자료에서 발견됨, 원자료 해시 불일치에서 멈춘다. 한 입력이 실패하거나 시간이 넘으면(900초) 그 trial은 `usable=false`로 보존하고 다음 trial로 간다. 자동 재시도와 재전송은 없다. 중간에 오류가 난 trial의 폴더는 지우지 않고 남겨 새로 시작할 때 사람이 보고서에 적고 지운다. |
| 반복과 예열 | trial마다 1회. 예열은 없다. 조건마다 같은 프로젝트의 반복은 없다. |
| 동시 실행 | 트랙마다 최대 3개를 15초 간격으로 시작한다. 한꺼번에 시작하면 router 점검이 실패하는 것을 예비 실행에서 관측했다. |

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | `composite` 대응 차이(`rrf` − `provider`, `jev` − `provider`) | 프로젝트별 짝, 둘 다 성공/X만/Y만/둘 다 실패 개수, 차이와 95% Newcombe 방법 10 구간([Newcombe 1998](https://doi.org/10.1002/(SICI)1097-0258(19980430)17:8%3C873::AID-SIM779%3E3.0.CO;2-I), 대응 자료용 Wilson 기반) | 구간 하한 ≥ 0 |
| H2 | `total_cost`, `window_seconds`의 짝 차이 평균 | 프로젝트 단위 복원 추출 percentile 구간(5000회, 시드 7007) | 두 지표 모두 구간 상한 < 0 |
| H3 | `composite` 대응 차이(`rrf` − `none`, `jev` − `none`) | H1과 같은 구간 | 하한 ≥ 0 |
| H4 | `composite` 대응 차이(`jev` − `rrf`), `total_cost` 짝 차이(`jev` − `rrf`) | 위와 같은 방법 | 품질 하한 ≥ 0, 비용 상한 < 0 |
| H5 | 요청마다 (항목 집합 일치 그리고 확률 폭 ≤ 0.10) | 요청 수 n, Wilson 95% 구간([04-replay.py](scripts/04-replay.py)). 항목 집합은 기록된 패킷에 들어간 `compact` 항목 수 k로 항목별 `max(호출, 결과)` 확률 상위 k개를 정렬(동률은 번호 오름차순)해 만든다. | 하한 ≥ 0.90 (일관성 기준은 [jev-decision-consistency](../jev-decision-consistency/design.md)와 같다) |
| H6 | `jev_applied` | `k/n`, Wilson 95% 구간 | 하한 ≥ 0.90 |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 없다. 실패한 trial은 모든 성공 지표를 0으로 세어 분모에 남긴다. 비용과 시간 차이는 두 조건 모두 `usable`인 짝만 쓰고 제외한 짝 수를 낸다. |
| 실패한 실행 | trial 상태(`complete`, 입력별 상태)를 흐름 표에 센다. 시간 초과는 전송 여부가 불명확한 입력으로 보고 다시 보내지 않는다. |
| 다중 비교 | 판정 구간은 보정하지 않는다. 트랙마다 확인 비교가 여럿이므로, 채택은 아래 규칙의 모든 조건을 동시에 만족할 때만 하고 하나라도 구간이 0을 지나면 `보류`다. 보정하지 않은 구간은 채택을 더 쉽게 하므로 이 선택을 보수적으로 쓰지 않는다. 두 비교의 확인 구간 모두 같은 표본이라 독립이 아니다. |

### 보고하는 부가 수치

조건별 성공 `k/n`과 Wilson 구간, 비용 구성(입력, 캐시 쓰기, 캐시 읽기, 출력, router)의 합과 평균, 복구 횟수(`metrics_reruns`, `incident_reruns`, `tool_calls`), 피드·지표 호출이 패킷에 들어간 형태의 분포, 패킷 토큰, `jev` 적용률, `compact` 판단 성공 수, 출력 배수 4와 8의 비용 민감도, 입력별 상태와 실패 수를 모두 `results/`에 둔다. 낮은 확신도 대체는 제품에 없다([낮은 확신 대체 규칙을 쓰지 않는 이유](../../design/context-management.md)). 판단이 실패해 RRF로 돌아간 비율은 `jev_applied`가 0인 비율로 본다.

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | 트랙과 후보(`rrf`, `jev`)마다 H1(`provider` 대비 품질), H3(`none` 대비 품질, 해당 트랙에만), H2(`provider` 대비 비용·시간)를 모두 만족하면 그 트랙에서 그 후보를 채택한다. `jev`는 H4, H5, H6을 추가로 모두 만족해야 한다. 채택하면 맥락 정리 설계의 해당 조건에 실측 근거를 적고 [settings](../../design/settings.md)의 `context.select.packet` 기본값 변경을 별도 이슈에서 제안한다. 이 실험이 기본값을 바꾸지 않는다. |
| 기각 | 후보의 품질 구간 상한이 0 미만이거나 비용 구간 하한이 0 초과면 그 트랙의 그 후보를 기각한다. 맥락 정리 설계의 해당 선택에서 그 후보의 기대 효과 문장을 지운다. |
| 보류 | 그 밖은 보류한다. 자동 적용을 켜지 않고, 부족한 증거(표본 수, 필요한 구간 폭)와 다음 실험의 입력 계약(실행 명령, 표본, 조건)을 이슈에 남긴다. |

두 줄은 채택 표와 별개로 항상 보고한다. 같은 session 안의 개입은 `미지원`이고 [#529](../same-session-compaction/report.md)의 값을 따른다. 실제 긴 세션(수만 토큰 이상)의 후보 선별은 이 실험의 축소 세션으로 대신할 수 없으므로 `미측정`으로 남긴다.

## 재현

| 명령 | 하는 일 |
|---|---|
| `./run.sh collect <claude\|codex\|claude-codex> formal` | 설계와 실행기를 커밋한 뒤에만 시작한다. 실제 engine과 provider를 부르고 원자료를 `data/raw/`에 gzip으로 둔다. |
| `./run.sh process` | 원자료에서 trial 표를 다시 만든다. |
| `./run.sh analyze` | 요약 JSON을 다시 만든다. |
| `./run.sh verify` | 표와 요약이 원자료에서 같은 바이트로 다시 만들어지는지 확인한다. |

`compact` 일관성은 `scripts/04-replay.py collect`, `analyze`로 따로 수집한다. 원자료에는 router 키가 들어가지 않으며 수집 뒤 키 문자열 수를 `grep -c`로 센다.

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
| 내적 | 같은 프로젝트의 조건이 각자 기록을 새로 만들므로 모델의 설정 입력 답이 조건마다 다르다. | 설정 입력은 `읽음`, `확인`만 답하게 해 답 글 차이를 줄이고, 도구 호출 결과(근거)는 프로젝트마다 같다. 차이는 잡음으로 보고 프로젝트 단위 짝으로 상쇄한다. |
| 내적 | `provider` 조건은 `/compact` 입력이, `rrf`와 `jev`는 새 session 열기와 패킷 전달 턴이 한 번씩 더 든다. | 두 부담 모두 비용과 시간에 포함한다. 제품 경로에서 일어나는 일이다. |
| 내적 | 호출 시각, 서버 부하, 프롬프트 캐시 상태가 시간과 비용을 바꾼다. | 순서를 섞고 3개씩만 동시에 돌리며 원시 시각과 사용량을 보존한다. |
| 내적 | `t_abs`를 낮춰 만든 경계가 제품 기본에서는 일어나지 않는 상황이다. | 기준과 세션을 같은 비율로 줄였음을 문서에 적고 결과를 이 규모로 한정한다. 실제 긴 세션은 `미측정`이다. |
| 구성 | 합성 저장소 하나의 틀에 값만 바꾼 12개라 실제 프로젝트의 다양성을 대표하지 않는다. | 적용 범위를 이 틀로 한정하고, 프로젝트 단위 분리와 값 변경으로 외우기를 막는다. 다른 틀은 후속 실험으로 남긴다. |
| 구성 | 한 번만 읽히는 피드는 복구 불가능이라 `none`과 `provider`가 유리하다. | 정리 방식이 근거를 잃을 때의 비용을 재려는 과제이며, 지표 덤프(다시 실행 가능)로 복구 비용 쪽도 함께 잰다. 결과는 두 근거를 나눠 보고한다. |
| 구성 | 숨긴 값과의 일치는 에이전트가 파일을 잘못 고쳐도 값만 맞으면 통과한다. | 공개 시험 통과와 `RETRIES` 불변을 함께 요구한다. |
| 외적 | 저렴한 모델(haiku, gpt-5.6-luna)의 결과가 큰 모델과 다를 수 있다. | 결과를 이 모델 쌍으로 한정한다. |
| 외적 | 에이전트가 피드 스크립트를 열어 값을 얻을 수 있다. | 피드는 저장소 밖 파일에서 읽고 읽은 뒤 지운다. 그래도 에이전트가 다른 경로를 찾으면 `incident_reruns`와 `tool_calls`로 드러난다. |
