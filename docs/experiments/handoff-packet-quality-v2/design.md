# 새 패킷 규칙의 전환 품질 재측정: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#218](https://github.com/woonyong-choi/saturn/issues/218) |
| 관련 설계 | [맥락 정리](../../design/context-management.md), [맥락 고르기](../../design/context-selection.md), [judge](../../design/router.md) |
| 사전 데이터 | [handoff-packet-quality](../handoff-packet-quality/report.md)의 결과와 후속 분석을 규칙 변경의 근거로 봤다. 시나리오 생성, 질문 유형, 채점, 실행 방식은 그 실험의 스크립트를 가져오고 시드만 218로 바꾼다. 시드 218 시나리오 하나를 판단 없이 RRF 순서로 채운 패킷의 형식(session 제목, 기록 번호, 시각 표기)만 확인했고, provider 답과 judge 판단은 보지 않았다. |

## 질문

[결정 기록](../../decisions/2026-10-02-fill-packet-by-probability.md)에 따라 compact 기준값을 없애고 judge의 남김 확률 순으로 채우며([#211](https://github.com/woonyong-choi/saturn/issues/211)), 패킷 항목에 session 제목, 기록 번호, 시각을 표기하는([#212](https://github.com/woonyong-choi/saturn/issues/212)) 새 규칙으로 전환 품질을 다시 잰다. 이 패킷이 패킷 없음보다(비교 A), judge 없이 순위로 채운 패킷보다(비교 B) 이전 작업 질문을 더 맞히는지 측정한다. 날짜와 여러 session 질문(`temporal`, `multi-session`)의 변화를 따로 본다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | `judge-all`의 정답률은 `no-packet`보다 10%p 이상 높다. 차이의 95% 신뢰구간 하한이 +10%p 이상이다. | 합성 시나리오 48개, Claude Code Opus 5.5와 Codex GPT-6 Sol 새 session, Jev, `k`=60, 패킷 예산 8,000토큰, 기준값 없는 확률 순 채우기 |
| H2 | `judge-all`의 정답률은 `rrf-fallback`보다 10%p를 넘게 높지 않다. 차이의 95% 신뢰구간 상한이 +10%p 이하다. | H1과 같다 |

## 설계

| 항목 | 값 |
|---|---|
| 조건 | `judge-all`: Jev가 후보 전체를 판단하고 남김 확률 순으로 채운 패킷이다(기준 조건). `rrf-fallback`: judge 없이 후보 순위(RRF) 순서로 채운 패킷이다. `no-packet`: 패킷 없이 사용자의 마지막 입력만 넘긴다. 두 패킷 조건은 고정 구역, 표기, 채우기 규칙이 같고 경쟁 구역의 순서만 다르다. |
| 배정 | 모든 조건이 같은 시나리오와 질문을 받는 대응 설계다. 시나리오 처리 순서는 시드 218로 섞고, 시나리오 안에서 provider마다 조건 순서를 시드 218과 시나리오 번호로 섞는다. 질문 순서는 시나리오마다 시드 218로 정하고 세 조건에서 같다. 세션 288개(시나리오 48 × provider 2 × 조건 3)를 실행한다. |
| 눈가림 | provider는 조건을 모른다. 프롬프트에 조건 이름을 넣지 않는다. 채점은 `02-process`가 정답 목록으로 하고 조건 이름을 보지 않는다. |
| 환경 | macOS, Python 3.9 이상(표준 라이브러리), Rust 툴체인(패킷 예제), Claude Code(`claude -p --model claude-opus-5-5`), Codex CLI(`codex exec -m gpt-6-sol`), Jev(`jev-1.13.0`). 도구와 모델 버전은 수집 때 `env.json`에 적는다. provider와 judge의 LLM 샘플링은 시드로 고정할 수 없다. |
| 실행 조건 | `SATURN_JUDGE_KEY`에 Jev 키(환경 변수로만 전달, 파일과 출력에 남기지 않음), 로그인된 `claude`와 `codex`, `cargo`. 하나라도 없으면 `01-collect`는 원인 한 줄을 쓰고 종료한다. |

- 패킷은 `saturn-terminal/core/examples/packet`(`cargo run -q -p saturn-core --example packet --`)이 만든다. `rrf-fallback`은 `--condition rrf-only`, `judge-all`은 `--condition judge-only --judgments`로 만든다. 예제는 기준값 없이 확률 순으로 예산까지 채우고 항목마다 session 제목, 기록 번호, 시각을 적는다.
- 시나리오 생성기는 기록 항목마다 `session`(1~4)과 `ts`(session마다 하나의 날짜)를 넣는다. 이전 실험과 같은 생성 규칙이고, 예제가 이 두 값을 읽어 표기한다. 이전 실험의 패킷에는 표기가 없었다.
- 패킷은 시나리오마다 한 번 만들어 두 provider가 같은 패킷을 받는다. 패킷을 만드는 judge 호출도 시나리오마다 한 번이다.
- `01-collect`가 Jev를 부른다. 후보는 시나리오의 도구 호출 128개 전체이고 호출마다 `call_<기록 번호>_keep`, `result_<기록 번호>_keep` 질문 2개를 `noul`로 묻는다. 결과는 앞 4,000자까지 싣는다. `state`는 마지막 사용자 입력과 그 앞 사용자 입력 3개다.
- 질문은 64,000바이트 이하 요청으로 나누고 조각마다 같은 `state`를 싣는다. 동시에 최대 8개를 보낸다. 항목의 남길 확률은 두 질문 확률의 큰 값이다. 조각이 실패하면 그 조각의 항목은 판단 없음이고 패킷 규칙대로 순위 순으로 뒤에 놓인다.
- 시나리오에 제약 입력이 없어 `is_constraint`와 `replaces_<n>`은 묻지 않고 제약 목록은 비운다.
- 새 session은 도구를 끈 채로 연다. Codex는 `--ephemeral --ignore-user-config --ignore-rules --sandbox read-only`, Claude Code는 `--safe-mode --tools "" --no-session-persistence`로 실행한다. provider가 패킷 밖 파일을 읽지 않게 하기 위해서다. provider 작업 폴더는 저장소 밖 오케스트레이션 폴더 하나다. 동시에 실행하는 provider 세션은 2개 이하다.
- `no-packet` 프롬프트의 맥락 절은 `사용자의 마지막 입력: {원문}` 한 줄이다. 질문 10개는 한 프롬프트에 묻는다.

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `condition` | 조작 | `judge-all`, `rrf-fallback`, `no-packet` | 없음 |
| `provider` | 조작 | 맥락을 받는 새 session의 provider. `claude`(Opus 5.5), `codex`(GPT-6 Sol) | 없음 |
| `qtype` | 조작 | 질문 유형. `extract`(정보 추출), `multi-session`(여러 session 추론), `temporal`(시간 추론), `update`(지식 갱신), `abstain`(모르면 모른다고 답하기). LongMemEval의 다섯 유형이다. | 없음 |
| `correct` | 측정 | 답이 정답 규칙에 맞으면 1, 아니면 0 | 없음 |
| `packet_tokens` | 측정 | 맥락 글자 수를 4로 나눈 추정 토큰 수 | 토큰 |
| `judge_calls` | 측정 | 패킷을 만드는 동안 보낸 judge 요청 수(나눈 조각 수) | 회 |
| `judge_failures` | 측정 | 응답을 받지 못한 judge 요청 수 | 회 |
| `evidence_in_packet` | 측정 | 질문의 근거 항목이 패킷의 포함 항목에 든 여부 | 없음 |
| `accuracy` | 파생 | 조건별 `correct` 합 / 시행 수 | % |
| `diff_a` | 파생 | 같은 시행 쌍의 `accuracy(judge-all) - accuracy(no-packet)` | %p |
| `diff_b` | 파생 | 같은 시행 쌍의 `accuracy(judge-all) - accuracy(rrf-fallback)` | %p |

정답 규칙은 이전 실험과 같다.

| 질문 유형 | 정답 |
|---|---|
| `extract`, `multi-session`, `temporal` | `unknown`이 거짓이고 답에 정답 값 중 하나가 있다. 정답 값이 여럿이면 모두 있다. |
| `update` | `unknown`이 거짓이고 답에 새 값이 있으며 옛 값이 없다. |
| `abstain` | `unknown`이 참이다. |

- 답의 비교는 소문자로 바꾸고 공백과 쉼표를 지운 글로 한다.

## 표본

| 항목 | 값 |
|---|---|
| 출처 | `01-collect`가 시드 218로 만드는 공개 합성 시나리오 48개. 가상의 쇼핑 서비스 저장소에서 4개 session에 걸쳐 일한 기록이다. 시나리오마다 도구 호출 128개, 질문 10개(유형마다 2개), 정답과 근거 항목 번호가 있다. |
| 크기 | 조건마다 960 시행(시나리오 48 × provider 2 × 질문 10) |
| 크기 근거 | 정밀도. 이전 실험의 신뢰구간 반폭이 약 2.4%p였고, 같은 크기로 기준 10%p 둘레를 가른다. 시나리오 단위 군집 부트스트랩의 반폭 목표는 7%p 이하다. |
| 중단 규칙 | 세션 288개를 모두 실행하면 멈춘다. 연속 5개 세션이 실패하면 환경 문제로 보고 멈추며, 고친 뒤 새 실행 id로 처음부터 다시 수집한다. 사용률 규칙은 아래에 있다. |
| 반복과 예열 | 세션마다 1회, 예열 없음 |

사용률 규칙은 다음과 같다.

- 사용률은 Claude 주간(`claude -p "/usage"`의 `Current week (all models)`), Claude 5시간 창, Codex 주간(가장 최근 `~/.codex/sessions` 기록의 `rate_limits.primary.used_percent`, 창 10080분)이다. 수집 시작 값을 `env.json`에 적는다.
- 이 실험과 [#219](https://github.com/woonyong-choi/saturn/issues/219)를 합쳐 Claude 주간과 Codex 주간이 각각 이 실험 시작 대비 5%p를 넘게 오르면 둘 다 멈추고 보고한다. #219의 몫을 남기기 위해 이 실험의 한도는 +4%p다. 한도에 닿으면 수집을 멈추고 보고하며 분석하지 않는다.
- 시나리오 5개를 먼저 수집해 증가를 잰다. 사용률은 정수라 증가가 0 또는 1로만 읽히므로 두 가지로 외삽한다. (가) 읽은 증가 × 48/5. (나) 시험 5개의 provider 비용 합(Claude는 `total_cost_usd`, Codex는 `turn.completed`의 토큰 합)을 이전 실험의 같은 합과 그 실험의 사용률 증가(Claude 24%에서 26%, Codex 9%에서 10%)로 환산한 전체 추정치. 읽은 증가가 2%p 이상이거나 (나)가 4%p를 넘으면 멈추고 보고한다. 읽은 증가가 1%p이고 (나)가 4%p 이하여서 판단이 갈리면 멈추고 보고한다.
- 이 5개는 본 수집에 포함하고, 전체 수집이 끝나기 전에는 답을 분석하지 않는다. 수집 중에는 시나리오 6개마다 사용률을 다시 읽고 한도를 확인한다. Claude 5시간 창이 85%를 넘으면 초기화될 때까지 기다린다.
- 같은 계정을 다른 작업도 쓰므로 사용률 증가에는 이 실험 밖의 사용이 섞인다. 증가는 상한 판단용 값이다.
- 시나리오의 근거 항목은 마지막 입력과 같은 낱말, 번역어, 같은 뜻의 다른 말 중 하나로 이어진다. 세 관계를 시나리오마다 섞고, 실제 비율은 보고서에 적는다.
- 근거 항목은 최근 3턴보다 앞의 도구 결과에만 둔다. 에이전트 답 글은 사실을 다시 말하지 않는다. 고정 구역만으로 답할 수 없게 하기 위해서다.

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | `diff_a` | 시나리오 단위 군집 부트스트랩(10,000회, 시드 218)의 95% 백분위 신뢰구간과 기준 +10%p에 대한 양측 부트스트랩 p값. 보조로 2×2 표와 불일치 수 b, c, McNemar 검정(b+c < 25면 정확 이항 검정), Newcombe 대응 차이 신뢰구간 | Holm 보정 p ≤ 0.05이고 차이의 95% 신뢰구간 하한 ≥ +10%p |
| H2 | `diff_b` | H1과 같다 | Holm 보정 p ≤ 0.05이고 차이의 95% 신뢰구간 상한 ≤ +10%p |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | provider가 도구를 한 번이라도 부른 세션, 답 JSON을 읽을 수 없는 세션. 제외는 시나리오와 provider 단위로 세 조건에서 함께 한다. |
| 실패한 실행 | provider 종료 코드가 0이 아니거나 300초를 넘으면 한 번 다시 실행한다. 다시 실패하면 그 시나리오와 provider 단위를 세 조건에서 빼고 흐름 표에 센다. 패킷을 만드는 중의 judge 실패는 `judge-all` 조건의 일부로 보고 빼지 않는다. |
| 다중 비교 | 확인 가설 둘에 Holm-Bonferroni |

- H1의 기각은 차이의 95% 신뢰구간 상한 < +10%p이고 Holm 보정 p ≤ 0.05일 때다. H2의 기각은 하한 > +10%p이고 Holm 보정 p ≤ 0.05일 때다. 채택도 기각도 아니면 보류다.
- 정답률은 조건마다 `k/n`, 비율, 95% Wilson 신뢰구간으로 쓴다.

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | H1 채택이면 패킷 설계를 유지하고 [맥락 정리](../../design/context-management.md) 요구사항 표와 단점의 `측정 전` 항목에 보고서 링크와 수치를 단다. H2 채택이면 judge 무응답 때 순위로 채우는 대체 규칙을 유지하고 [맥락 고르기](../../design/context-selection.md) 요구사항 표에 보고서 링크를 단다. |
| 기각 | H1 기각이면 패킷 구성을 다시 설계하는 `design` 이슈를 연다. H2 기각이면 judge 실패 시 재시도와 지연 규칙을 정하는 `design` 이슈를 연다. |
| 보류 | 시나리오를 늘려 새 실행 id로 다시 수집하고, 질문 유형별 탐색 결과로 차이가 나는 유형을 확인한다. 설계 문서에는 보고서 링크와 수치만 단다. |

## 탐색 분석

- 질문 유형별, provider별 조건 정답률과 `diff_a`, `diff_b`. 특히 `temporal`과 `multi-session`
- `judge-all`과 `rrf-fallback` 패킷의 근거 항목 포함 비율(`evidence_in_packet`)과 근거 관계(같은 낱말, 번역어, 같은 뜻의 다른 말)별 비율
- 조건별 `packet_tokens`, `judge_calls`, `judge_failures`, 패킷의 포함 항목 수
- 이전 실험 대비 조건별, 질문 유형별 정답률 변화. 시나리오가 다르고 패킷 규칙이 둘 다 바뀌었으므로 기술 통계로만 쓴다.
- `McNemar` 검정과 Newcombe 신뢰구간(보조)

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
| 내적 | 한 세션에서 질문 10개를 함께 물어 같은 세션의 답이 서로 기대므로 시행이 독립이 아니다. | 판정에 시나리오 단위 군집 부트스트랩을 쓰고 McNemar는 보조로만 보고한다. |
| 내적 | provider와 judge의 샘플링이 고정되지 않아 같은 패킷도 다른 답을 낼 수 있다. | 한 시나리오의 세 조건을 같은 시간대에 무작위 순서로 실행한다. |
| 내적 | 시나리오마다 judge 호출이 한 번이라 한 번의 판단 오차가 두 provider에 같이 실린다. | 판정 단위를 시나리오로 두어 이 상관을 신뢰구간에 반영한다. |
