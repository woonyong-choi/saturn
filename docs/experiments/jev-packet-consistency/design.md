# Jev 패킷 판단 일관성: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#544](https://github.com/woonyong-choi/saturn/issues/544) |
| 관련 설계 | [맥락 정리](../../design/context-management.md), [맥락 고르기](../../design/context-selection.md) |
| 사전 데이터 | [기존 Jev 반복 실험](../jev-decision-consistency/report.md)과 [#7 결과](../context-net-effect/report.md)를 열람했다. #7의 기존 `compact` 선택 집합 일치는 11/35(31.4%)이며 정답률이 아니다. [#606](https://github.com/woonyong-choi/saturn/pull/606)의 자료는 실행기 개발·스모크에만 쓴다. |

## 질문

#7과 같은 실제 작업의 패킷 판단 요청을 새로 수집할 때 Jev가 같은 뜻에는 같은 항목을 남기고, 필요한 근거가 바뀐 작업에는 선택을 바꾸는지 측정한다. 원응답 파싱, 선택 집합, 필수 근거 포함, 최종 행동을 각각 검사한다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | 같은 요청 5회의 원 선택 집합 전체 일치율의 Wilson 95% 하한은 90% 이상이다. | 확인 실과제의 `compact` 요청 |
| H2 | 후보 질문 순서와 무관 문구를 바꾼 요청의 원 선택 집합이 기준 요청의 다수 집합과 같은 fixture 비율의 Wilson 95% 하한은 각각 90% 이상이다. | 사전 검토한 의미 보존 변형 |
| H3 | 중요한 작업 조건을 바꾼 요청에서 바뀐 필수 근거를 모두 선택한 fixture 비율의 Wilson 95% 하한은 90% 이상이다. | 사전 검토한 의미 변경 변형 |
| H4 | 원 선택에 필요한 근거가 남고 최종 행동도 사전 채점 계약을 통과한 fixture 비율의 Wilson 95% 하한은 90% 이상이다. | engine 연결 확인 과제만. 오프라인 호출만 있으면 보류 |

H1의 90% 기준은 기존 기준을 그대로 둔다. H2~H4도 같은 수치를 쓴다. 모든 가설은 fixture를 분모로 세며 5회 응답을 독립 표본으로 늘리지 않는다. 한 번이라도 요청 실패, 파싱 오류, 미적용, 증거 누락이 있으면 해당 fixture의 해당 가설은 실패다.

## 설계

| 항목 | 값 |
|---|---|
| 조건 | `identical` 5회, `order` 3회, `neutral` 3회, `critical` 3회. `order`는 `questions`의 순서만 바꾸고, `neutral`은 사전 검토한 무관 문구만 추가한다. `critical`은 후속 작업의 중요 요구와 필수 근거를 함께 바꾼다. |
| 배정 | fixture와 변형·반복 전체를 `random.Random(5447)`로 섞는다. 한 fixture의 반복은 인접하도록 강제하지 않는다. |
| 눈가림 | 호출기는 정답·필수 근거·후속 행동 결과를 읽지 않는다. `eval/`의 별도 라벨 파일은 수집 전에 두 사람이 원문만 보고 검토하고 해시를 봉인한다. |
| 환경 | TypeSafe HTTPS `POST /v1/systemone`, 실제 응답 `model`과 요청 모델을 모두 기록한다. 키는 보호된 로컬 파일에서 읽고 원자료·오류 출력에서 일치 문자열을 가린다. 공식 API에 캐시 끄기 계약이 확인되지 않으면 캐시 비활성이라고 주장하지 않고 완전히 같은 확률 응답의 비율을 병기한다. |

### 자료와 봉인

한 fixture는 #7과 같은 코드 수정·근거 회수 작업의 첫 패킷 판단에 쓰인 요청 원문, 후보 질문과 항목 번호, 경쟁 구역 예산으로 정해지는 선택 개수 `k`, 필수 근거 ID, 의미 보존 변형 두 개, 중요 조건 변경 변형과 변경 뒤 필수 근거 ID를 담는다. `eval/fixtures.jsonl`은 개발과 확인의 프로젝트·세션 계열을 분리한다. #7 manifest의 `task_id`, `source_sha256`, `goal_sha256`, `candidate_sha256`, `policy_sha256`를 그대로 연결한다. 실제 J trial의 `judgments.sent` 원문으로 `compact_request_sha256`을 계산한다. #7 기존 35건과 #606 자료는 개발 집합으로만 쓴다. 확인 집합은 새 프로젝트 계열의 첫 요청만 쓰고 같은 계열의 다른 session을 독립 fixture로 세지 않는다. 같은 시작 상태와 예산에서 조건을 대응시키며 요청 생성 순서를 무작위화한다. 정답과 이후 기록은 Jev 요청에 넣지 않는다.

수집 전에 fixture 목록, 각 요청의 SHA-256, 후보 ID, `k`, 필수 근거, 변형의 의미 판정, 채점기 SHA-256, 실행 환경과 표본 수를 `eval/lock.json`에 봉인한다. `verify`가 해시나 누락을 발견하면 수집을 멈춘다. 수집 뒤 fixture와 판정 기준을 고치지 않는다. 원자료는 시도별 JSONL로 추가만 하고 재시도는 새 시도로 남긴다.

### 선택과 행동

응답은 모든 질문에 0~1의 유한한 `noul` 값이 있을 때만 유효하다. 질문 이름의 `call_<번호>_keep`, `result_<번호>_keep`을 같은 항목에 묶어 두 확률의 최대값을 쓴다. 높은 점수 순서, 동률이면 항목 번호 오름차순으로 `k`개를 고른다. 파싱 성공률은 호출 수, 원 선택 일치율은 fixture 수, 필수 근거 포함률은 fixture 수로 분모를 따로 기록한다. 실제 적용된 집합은 engine의 전송 직전 패킷으로만 확인한다. 원 선택과 적용 선택, 후속 수정·답·검사의 통과를 별도 값으로 둔다. 오프라인 호출에서 행동 결과를 추정하지 않는다.

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `variant` | 조작 | `identical`, `order`, `neutral`, `critical` | 범주 |
| `parse_ok` | 측정 | HTTP 성공, JSON 형식, 요청 질문과 완전 일치하는 유한 `noul` 응답 | 0/1 |
| `selected_ids` | 파생 | 위 규칙의 상위 `k` 항목 번호 집합 | ID 목록 |
| `selection_agreement` | 파생 | 한 fixture의 유효 응답 모두 같은 원 선택 집합 | 0/1 |
| `evidence_complete` | 파생 | 선택 집합이 사전 고정한 필수 근거 ID를 모두 포함 | 0/1 |
| `applied_ids` | 측정 | 실제 패킷에 들어간 항목 번호 집합. 미연결이면 null | ID 목록 |
| `action_pass` | 측정 | #7의 F1~F3처럼 사전 고정한 후속 작업 검사 전체 통과. 미연결이면 null | 0/1 |
| `fallback`, `usage_missing`, `latency_ms` | 측정 | 대체 경로, usage 결측, 요청 소요 시간 | 범주, 0/1, ms |

## 표본

| 항목 | 값 |
|---|---|
| 출처 | #7과 같은 실제 provider 작업에서 새로 발생한 첫 `compact` 요청. 기존 #7 35건과 #606은 개발·스모크 전용이다. |
| 크기 | 확인 fixture 수는 개발 자료의 fixture 단위 불일치·군집 분산으로 계산해 확인 수집 전에 `eval/lock.json`과 설계 확정 절에 고정한다. 5회 동일 요청과 세 변형 각 3회다. |
| 크기 근거 | Wilson 95% 하한이 0.90을 넘는 최소 성공 수와 프로젝트 계열 군집 bootstrap 95% 하한을 모두 충족할 수 있는 크기를 개발 자료로 산정한다. 비용 상한 때문에 못 채우면 기준을 낮추지 않고 보류한다. |
| 중단 규칙 | 봉인 해시 불일치, 키 거절, 키 문자열 유출, 사전 고정한 호출 상한 도달에서 멈춘다. 시간 초과는 전송 여부가 불확실하므로 재전송하지 않고 실패로 남긴다. |
| 반복과 예열 | 동일 요청 5회, 변형마다 3회, 예열 없음. |

확인 수집 전 `설계 확정`에 표본 수, 호출 상한, 개발 자료의 분산, 채점기 해시, 실과제 계열 목록을 적고 별도 커밋으로 고정한다. 값이 비어 있으면 확인 수집기는 실행을 거부한다. 현재 문서는 사전 설계와 실행 계약 단계이며 확인 자료는 수집하지 않았다.

결과 보고서에는 `설계와 다른 점` 절을 두고 수집·분석 중 변경과 확인 판정에 미친 영향을 적는다. 개발 스모크의 결과는 확인 판정과 분리한다.

### 개발 스모크

기존 독립 실험의 봉인된 12개 J trial은 [개발 소스 봉인](eval/dev-source-lock.json)에 manifest·각 원자료·첫 `compact` 요청 SHA-256과 선택 개수 `k`를 고정한다. `./run.sh collect dev SOURCE_DIR KEY_FILE`은 해당 소스를 읽기 전용으로 검사한 뒤 요청 원문 바이트를 5회씩 총 60회 재전송한다. 결과는 이 worktree의 Git 제외 `.runtime/jev-packet-consistency/`에 기록한다. `./run.sh analyze dev SOURCE_DIR`와 `./run.sh verify dev SOURCE_DIR`로 원 선택 집합과 파싱 실패를 확인한다. 12개는 개발 스모크라 확인 가설을 채택할 수 없다. 12/12 일치해도 Wilson 95% 하한이 90%에 못 미친다. 불일치가 나타나면 자동 적용 보류의 근거로 쓴다.

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | `selection_agreement` | fixture별 `k/n`, Wilson 95%와 프로젝트 계열 bootstrap 95% 구간 | 두 하한 ≥ 0.90 |
| H2 | `order`, `neutral` 기준 다수 집합 일치 | 각각 fixture별 Wilson 95%와 계열 bootstrap | 두 변형의 두 하한 모두 ≥ 0.90 |
| H3 | `critical`의 변경 후 `evidence_complete` | fixture별 Wilson 95%와 계열 bootstrap | 두 하한 ≥ 0.90 |
| H4 | 필수 근거와 후속 행동 동시 통과 | 실제 engine 연결 fixture별 Wilson 95%와 계열 bootstrap | 두 하한 ≥ 0.90, 적용률 하한 ≥ 0.90, 품질 차이 하한 ≥ 0 |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 수집 전 스키마와 사람 검토를 통과하지 않은 fixture만 제외한다. 수집 뒤 실패·미적용은 분모에 남긴다. |
| 실패한 실행 | HTTP·파싱·후속 작업 실패, fallback, 원 선택과 실제 적용 불일치를 각각 센다. usage 결측과 재조회·재작업 횟수도 별도 분모로 보고한다. |
| 다중 비교 | H1~H4를 모두 만족해야 전체 통과로 판정한다. 각 가설의 개별 구간은 기술적으로 보고하고 역할 채택은 교집합으로만 한다. |

Claude와 Codex, 한국어와 혼합어, 짧은 맥락과 긴 맥락을 별도 층으로 보고한다. 각 층에 표본이 부족하면 그 층의 일반화 판정은 보류한다. 확률이나 API confidence를 후속 작업 성공 확률로 해석하지 않는다. 품질 저하 허용폭 0을 유지한다. 토큰·완료 시간은 대응 차이와 95% 계열 bootstrap 구간, p95를 보고하고 절감 기준은 개발 측정 후 확인 자료 열람 전에 고정한다. 전부 fallback한 정책은 일관성 지표가 높아도 효율 통과가 아니다.

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | 확인 집합에서 H1~H4와 품질·효율 기준을 모두 충족한 역할과 환경만 제한 적용 후보로 기록한다. 이 문서만으로 기본 자동 적용을 켜지 않는다. |
| 기각 | 어느 가설의 95% 상한이 0.90 미만이거나 안전 위반이 있으면 해당 역할의 자동 적용 근거를 기각한다. |
| 보류 | 구간이 경계를 가로지르거나 engine 행동, usage, 확인 표본이 부족하면 보류하고 부족한 분모를 기록한다. |

## 탐색 분석

- 원응답 파싱 실패와 원 선택 불일치, 실제 적용 실패, 후속 행동 오류 사이의 단계별 이탈을 비교한다.
- 경계 확률과 항목별 최대·최소 폭, 완전히 같은 확률 재현 비율을 보고한다.
- #7의 11/35와 확인 결과를 나란히 놓되 서로 다른 자료의 정답률 차이로 해석하지 않는다.

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
| 내적 | 서비스의 숨은 캐시나 버전 변경이 반복을 바꾼다. | 호출 시각, 응답 모델, 같은 확률 반복을 기록하고 버전별로 분리한다. |
| 구성 | 무관 문구가 실제로 선택 의미를 바꿀 수 있다. | 사람 두 명이 요청과 필수 근거만 보고 사전 검토하고, 합의하지 못한 fixture는 수집 전에 제외한다. |
| 구성 | 원 선택 집합 일치는 작업 정답이 아니다. | 필수 근거, 실제 패킷, 후속 행동을 별도 채점한다. |
| 외적 | 한 합성 서비스 틀은 다른 저장소·언어·긴 맥락을 대표하지 않는다. | 프로젝트 계열을 분리하고 층별 표본 부족을 보류한다. |
