# Jev 패킷 판단 일관성: 실험 결과

## 요약

개발 스모크에서 봉인된 12개 요청을 5회씩 반복했고 원 선택 집합은 12/12가 일치했다. Wilson 95% 구간은 [75.8%, 100.0%]라 사전 기준인 하한 90%를 넘지 못한다. 이 자료는 개발용이므로 확인 가설 H1~H4는 보류하고 자동 적용은 시작하지 않는다.

## 방법

| 항목 | 값 |
|---|---|
| 설계 | [실험 설계](design.md), 수집 전 커밋 `c09ff4a4` |
| 실행 id | 개발 스모크. 원자료 파일 수정 시각 2026-10-06 16:12:57 UTC이며 개별 호출 시각은 기록되지 않았다. |
| 환경 | [env.json](env.json) |
| 표본 | 봉인된 개발 12 fixture 전수, 각 동일 요청 5회, 예정·시작·완료 모두 60회. 확인 fixture는 수집하지 않았다. |

개발 소스의 manifest, 원자료, 첫 `compact` 요청 SHA-256과 선택 개수 `k`는 [dev-source-lock.json](eval/dev-source-lock.json)에 수집 전에 고정했다. source 파일은 읽기 전용으로 확인했고 Jev에 보낸 것은 기록된 요청 원문 바이트다. 각 시도의 `start`를 전송 전에, `end`를 응답 뒤에 fsync했다. 완료되지 않은 시도를 재전송하지 않는 규칙이다. 원자료에는 요청·응답 원문이 있어 Git 제외 로컬 저장소에 보존하고 공개 집계만 [summary.json](results/summary.json)에 둔다.

## 설계와 다른 점

확인 판정에 쓰는 설계·가설·90% 기준은 변경하지 않았다. 설계의 Python 최소 환경은 3.10이지만 실제 호출 프로세스 버전은 원자료에 기록되지 않았다. 수집 뒤 검증한 호스트의 `python3`은 3.9.6이었다. 실행기와 검증기가 통과한 사실은 확인했지만, 호출 당시 Python 버전을 확정할 수 없어 환경 재현성의 한계로 남긴다. 개발 원자료에는 개별 UTC 시각이 없어 파일 수정 시각만 보고한다.

## 논의

### 해석

12개 개발 fixture에서 불일치는 관측되지 않았다. 그러나 12/12에서도 Wilson 하한이 75.8%라 90% 이상의 반복 안정성을 입증하지 못한다. #7의 기존 `compact` 선택 집합 일치 11/35와 이번 12/12는 서로 다른 개발 자료의 관측이며, 어느 쪽도 후속 작업 정답률이 아니다. 확인 평가에 새 #7 실과제 요청과 필수 근거 라벨, 실제 적용·행동 기록이 필요하다.

### 타당성 위협

| 종류 | 위협 | 이 실험에서 |
|---|---|---|
| 내적 | 서비스의 숨은 캐시나 버전 변경이 반복을 바꾼다. | API 캐시를 끄는 계약을 확인하지 못했다. 응답 모델은 모두 `jev-1.13.0`이었다. |
| 구성 | 무관 문구가 실제로 선택 의미를 바꿀 수 있다. | 개발 스모크에서는 문구 변형을 보내지 않았다. 확인 평가 전에 사람 검토가 필요하다. |
| 구성 | 원 선택 집합 일치는 작업 정답이 아니다. | 원 선택 집합만 비교했다. 필수 근거와 후속 행동은 채점하지 않았다. |
| 외적 | 한 합성 서비스 틀은 다른 저장소·언어·긴 맥락을 대표하지 않는다. | 기존 봉인된 12개 개발 과제만 다시 물었다. 새 실과제 계열로 일반화하지 않는다. |

### 한계

- 12개를 독립 확인 표본으로 세지 않는다. 5회 반복도 독립 fixture 60개로 늘리지 않는다.
- 후속 작업 품질, 실제 패킷 적용률, fallback, 토큰 순효과, 재조회·재작업은 측정하지 않았다.
- 수집 당시 Python 버전과 개별 호출 시각을 원자료에서 복원할 수 없다.
