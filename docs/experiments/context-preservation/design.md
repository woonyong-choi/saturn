# 보존 우선 비교: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#7](https://github.com/woonyong-choi/saturn/issues/7), 실행기 [#540](https://github.com/woonyong-choi/saturn/issues/540) |
| 관련 설계 | [보존 우선 경로](../../design/context-management.md#보존-우선-경로) |
| 사전 데이터 | 기존 맥락 실험과 #587의 실패 사례를 열람했다. 기존 시드는 개발 회귀에만 사용한다. |

## 질문

대화 본문을 보호하면 정정 유실이 사라지는지, 같은 보호 규칙에서 Jev 도구 선별이 코드 순위보다 추가 이득을 주는지 확인한다. 이 문서는 최소 기능 진단의 계획이며 일반 제품 채택을 위한 충분한 표본이라고 주장하지 않는다. 실행기와 환경을 함께 고정한 후에만 수집한다. 이번 설계 PR에서는 provider 호출을 실행하지 않는다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | 보존 적용 실행의 보호 본문 누락과 순서 오류는 0건이다. | 같은 채팅의 허용된 텍스트 본문 |
| H2 | 보존 RRF와 보존 Jev의 후속 과제 성공률은 원문 전체 조건보다 낮지 않다. | 아래 합성 진단 과제와 실제 두 provider |
| H3 | 보존 Jev는 보존 RRF보다 품질을 낮추지 않고 과제 완료까지의 비용을 줄인다. | 같은 원문·후보·예산의 대응 실행 |

## 설계

| 항목 | 값 |
|---|---|
| 조건 | F: 대화·도구 원문 전체로 새 session 시작, R: 대화 본문 보존과 RRF 도구 선별, J: 대화 본문 보존과 Jev 도구 선별, N: 현행 provider 모드 |
| 경로 | Claude→Claude 새 session, Codex→Codex 새 session, Claude→Codex, Codex→Claude |
| 배정 | 계열별 네 조건의 순서를 seed 536592로 섞는다. 동시에 도는 trial은 최대 2개다. |
| 눈가림 | 선택기와 작업 모델에 숨긴 검사와 미래 질문을 주지 않는다. 검사기는 arm을 판정 입력으로 사용하지 않는다. |
| 환경 | 첫 진단의 provider 모델은 claude-haiku-4-5-20251001, gpt-5.6-luna, 판단은 jev-1.13.0으로 고정한다. 기존 실험과 연속성을 확인할 용도다. 제공 불가하면 실행을 멈추고 다른 모델의 별도 계획을 고정한다. |

CLI 버전·OS·바이너리 해시·제품 커밋·실험 커밋·정책 지문·가격표와 계측 범위는 수집 전 환경 파일에 고정한다. 실제 응답 모델이 다르면 계획 이탈로 분리한다. 이 진단은 Sonnet·Sol·Astra 성과를 대신하지 않는다. 제품 채택 전에는 실제 사용 모델의 별도 확인 설계를 등록한다.

R과 J는 같은 기준 기록 스냅샷을 사용한다. 보호 본문과 후보 해시가 다르면 선별기만 다른 비교로 판정하지 않는다. fixture와 전송 경로는 기존 engine 실험 실행기를 재사용하고 사용자 DB를 수정하지 않는다. 대화 본문을 도구 실행이 이미 끝난 기록으로 전달하며 인계만으로 작업을 재실행하지 않는다.

N의 같은 provider 조건은 같은 길이의 준비 입력 뒤 실제 기본 압축을 수행한다. provider 전환 조건의 N은 현행 provider 모드의 인계이며 native 압축만의 효과로 해석하지 않는다. 서로 다른 준비 실행의 모델 출력과 내부 캐시는 동일 복제가 불가능하므로 F/R/J의 선별 인과 비교와 N의 전체 정책 비교를 분리한다.

실험 예산은 보호 본문과 provider 한도를 따로 둔다. 도구 경쟁 예산은 3,500토큰 추정치로 고정한다. 예산 초과를 맞추려고 본문을 자르지 않는다. 보호 본문이 provider 실제 한도에 들어가는 사례와 의도적으로 넘기는 사례를 구분한다. 한도 초과의 정상 거절은 기능 검사 통과지만 작업 성공으로 세지 않는다.

## 표본

| 항목 | 값 |
|---|---|
| 출처 | 기존 실험 생성기와 별도 시드 536001~536006의 합성 저장소 |
| 크기 | 6계열 × 4경로 × 4조건 = 96실행 |
| 크기 근거 | 결함 진단 예산. 여섯 실패 유형을 한 계열씩 확인하며 모집단 품질 보장에 필요한 검정력으로 정한 수가 아님 |
| 중단 규칙 | 96실행 또는 provider 입력 1,920회·Jev 256회 중 먼저 닿는 상한. 초과하지 않고 남은 실행은 미완료로 기록 |
| 반복과 예열 | 각 trial 1회. 경로당 예열 1회는 별도 보존하고 96회에서 제외. 선택 일관성은 같은 요청 5회이며 독립 과제 수에서 제외 |

여섯 계열은 오래된 정정 뒤 읽기 요청, 같은 문자열의 서로 다른 입력, 작업 한정 예외와 지속 지시, 긴 도구 결과 중간 근거, 중단·결과 불명, 무관 문서의 지시 교란이다. 모든 실행에 한국어 사용자 지시와 영어 코드 식별자를 사용한다. 과제별 세 후속 요청을 정정 준수·사실 조회·기능 수정으로 고정한다. 생성한 hidden 정답은 수집 전에 hash를 고정하고 실행 작업 폴더에서 제거한다.

한도 초과·revision 경합·거절·권한 축소·record off는 가짜 provider와 고정 원문을 사용하는 기능 검사다. 이 기능 검사와 여섯 실과제 성공률을 합산하지 않는다. 실제 provider 원문 조회는 Claude와 Codex 각각 한 smoke에서 검색·read·응답을 대조한다. 실패하면 조회 효과 실험은 시작하지 않는다.

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | body_fidelity | source ID별 실제 전송 원문과 독립 비교 | 누락·역할 변경·순서 오류·잘못된 중복 제거 0건. 한 건이라도 있으면 기능 실패 |
| H2 | task_success | 경로별 k/n, 대응 불일치 수와 보수적 정확 구간 | 기능 진단에서는 관측 손실 0건을 다음 평가 착수 조건으로만 사용. 품질 보장 채택 불가 |
| H3 | cost, duration | 대응 차이와 계열 단위 bootstrap 10,000회, seed 536592 | 비용 계측 완전성·관측 품질 손실 0건·비용 차이 상한 < 0인 경우만 추가 확인 평가 후보 |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 예열만 제외한다. 오류·거절·미적용·자동 native 압축은 삭제하지 않고 별도 열과 전체 분모에 남긴다. |
| 실패한 실행 | 제한 시간 300초, 결과 불명, 승인 대기 중단, 잘못된 입력 분할은 실패 또는 실행 규약 위반으로 보존한다. 자동 재시도하지 않는다. |
| 다중 비교 | F 대비 R/J와 R 대비 J의 탐색 진단이다. 다중 비교를 통한 제품 채택을 하지 않는다. |

성공률 차이는 대응 불일치 b/n과 c/n 각각에 꼬리 확률 0.0125의 Clopper–Pearson 경계를 구하고 차이 경계를 만든다. 네 꼬리에 Bonferroni를 적용한 95% 보수 구간이다. bootstrap 비용·시간 구간은 작은 여섯 계열에서 불안정하므로 탐색값으로 표시한다. 계산은 기존 분석기를 재사용한다. 통계 구간은 무오류의 증명이 아니다.

기본 압축 비용이 보고되지 않으면 전체 cost는 null이다. 원시 토큰과 cache 할인 가중 토큰, 실제 청구 금액을 섞지 않는다. 구독 비용을 임의의 API 가격으로 바꾸지 않는다. 압축 비용 미계측 조건은 전체 비용 우위 판정이 불가능하다. 판단 실패 뒤 RRF 대체 비용, 새 session의 cache 손실, 원문 재조회와 후속 재작업을 모두 포함한다. 출력 토큰 안에 포함된 추론 토큰을 다시 더하지 않는다.

Jev를 사용하지 않는 R에서도 기존 입력 관계 router가 사용될 수 있다. 그 호출량은 모든 조건에 따로 기록하며 이 비교를 Jev 전체 on/off로 부르지 않는다. 동일 요청 5회의 선택 집합 일치율은 과제 정답률과 구분한다. #544의 기존 90% 기준을 완화하지 않는다. 같은 결과 재사용은 목표·원문 해시·정책·모델 버전이 일치할 때만 허용하며, 일관성 측정에서는 캐시를 끈다.

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 기능 통과 | 새 경로가 정정 보존·원문 추적·오류 처리를 수행함을 확인한다. 기본 자동 적용은 변경하지 않는다. |
| 기능 실패 | 실패한 source→후보→계획→전송→작업 단계를 고친다. 다른 계층을 더해 실패를 숨기지 않는다. |
| 효과 후보 | 독립 프로젝트 계열과 실제 사용 모델에서 확인 평가를 새로 사전 등록한다. |
| 보류 | 계측 누락, 미지원 경로, 넓은 구간, 낮은 실제 적용률의 원인을 별도 기록한다. |

확인 평가의 품질 허용폭은 0을 유지한다. 유한 표본에서 차이 구간 하한이 0 이상이라는 조건은 동률만으로 통과하기 어렵다. 이 한계를 숨기거나 수집 뒤 허용폭을 넓히지 않는다. 표본 크기는 이 진단의 분산을 개발 자료로 사용해 별도 설계에서 고정하며, 그 뒤 새 자료로만 판정한다. 이번 문서는 그 확인 평가까지 실행하도록 승인하거나 효과를 주장하지 않는다.

## 탐색 분석

- 본문 보존이 늘린 토큰과 도구 선별이 줄인 토큰을 분리한다.
- 기억 검색, 유효 지시, 작업 LLM의 상태 기록은 이 실험에 함께 켜지 않는다. 각각 같은 기반의 추가 전후 비교로 별도 설계한다.
- 같은 session 기록 편집은 어댑터 지원 검증 뒤 별도 층으로 사전 등록한다. 새 session 결과를 같은 session 결과로 바꾸어 부르지 않는다.

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
| 내적 | provider 준비 출력과 캐시가 실행마다 다르다. | R/J source 해시를 맞추고 N의 전체 정책 비교는 별도로 보고한다. |
| 구성 | 실제 사용 모델과 합성 진단 모델이 다르다. | 실제 사용 모델의 확인 평가를 제품 채택 조건으로 남긴다. |
| 외적 | 여섯 합성 계열로 일반 대화를 대표할 수 없다. | 기능 진단만 판정하고 다른 프로젝트 계열로 확인 평가한다. |
