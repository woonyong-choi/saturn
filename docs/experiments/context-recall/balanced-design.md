# 원문 종류별 공간 배분: 후속 실험 설계

## 질문

사용자 입력·도구 결과와 과거 답에 각각 복원 공간을 배정하면 한 종류가 다른 종류의 근거를 밀어내는 실패를 줄일 수 있는가?

## 사전 데이터

첫 설계는 162실행 중 118개의 완결 결과를 얻은 시점에 중단했다. 새 질문의 `User { name: String }` 표기가 다른 질문의 답을 노출했다. 이 결과와 중단된 출력은 보존하며 확인 실험으로 채택하지 않는다. 수집 중단은 최초 중단 규칙에서 벗어난 변경이다. 완료된 복원 조건에서는 오래된 답에만 있는 이름을 놓쳤다.

기존 9기록은 개발 자료다. 새 자료로 별도 Claude 설계 대화 하나를 추가한다. 원본 식별자는 `9c8e827c`로 시작하며 마스킹한 사본과 원본 해시를 고정한다. 이 기록의 사용자 역할 항목 5개 중 2개는 실제 요청, 2개는 주입된 스킬 문서, 1개는 중단 표지다. 5개의 독립 사용자 요청으로 세지 않는다. 질문은 과거 답이 보고한 문서·브랜치·상태·수치·기록 칸을 묻는다. 보고 내용의 외부 사실 여부를 검증하는 실험은 아니다. 이 새 자료를 본 뒤 복원 알고리즘은 변경하지 않는다.

## 설계

| 항목 | 값 |
|---|---|
| 조건 | 원문 전체, 기존 4,000 추정 토큰 패킷, 같은 패킷과 최대 8,000자 원문 복원 |
| 복원 공간 | 머리말을 뺀 나머지를 사용자 입력·도구 결과와 과거 답에 반씩 배정한다. 한 종류의 남은 공간을 다른 종류로 넘기지 않는다. |
| 질문 | questions-balanced.json. 기존 자료 72문항은 개발 검증, 새 출처 8문항은 출처 보류 검증으로 구분한다. 이름·필드·타입을 질문에 직접 쓰지 않는다. |
| 표본 | 10기록 × 3조건 × 2provider × 1회 = 60실행. 각 실행 8문항. |
| 반복 근거 | 먼저 실패 수정을 전수 비교한다. 반복만 늘려 원자료 다양성을 부풀리지 않는다. 추가 반복은 별도 실행 묶음으로 기록한다. |
| 배정·모델·수집 | 최초 설계와 같은 seed 7108, CLI·모델·원응답 보존 방식. 실행 코드는 다시 고정한다. |
| 중단 | provider별 연속 프로세스 실패 3회. 평가 문항에 답 노출이나 원자료 오염이 발견되면 중단하고 해당 판정을 폐기한다. |

## 분석

정답·사용량 계산은 최초 설계와 같다. 두 provider 모두 복원 조건의 80문항이 정답이고, 원문 전체 대비 총 입력 토큰이 각각 10% 이상 줄어야 이 자료에서 개선을 채택한다. 새 출처 8문항은 별도로 보고한다. 부정확한 Ready 응답, 도구 실행, 프로세스 실패는 유효 정답에서 제외한다. 완료되지 않은 계획 행은 분모에 남긴다.

고정된 자료에서의 개선과 일반적인 신뢰도는 구분한다. 새 출처가 하나라서 모집단 신뢰구간이나 일반 무손실을 주장하지 않는다. 실제 engine 전송, 입력 보존, 모드 경계, 정상 router 자격증명 유무도 연구 결과와 함께 기록한다.
