## 결론

보류다. Jev 선별(확률 0.9 이상인 블록만 예산 안에서 담음)은 사전 기준의 세 조건 중 품질 이득 하나만 충족했다. 원문 전체와 비교한 품질 유지(허용폭 0)와 토큰·시간 이득은 충족하지 못했다. 품질 이득도 답 형식 위반에 크게 좌우됐다. 답 앞뒤의 설명 글을 허용하는 민감도 분석에서는 모든 조건이 98~100%로 모여 이득이 사라지는데, 이는 이 합성 과제가 너무 쉽다는 뜻이다. 자동 적용을 켜지 않는다.

## 판정

판정은 Claude 252계열이다. 구간은 과제 단위 부트스트랩 95%다.

| 가설 | 결과 | 판정 |
|---|---|---|
| H1 `jev - code` 성공률 하한 > 0 | +6.1%p [2.7, 9.4], 과제별 반복 평균이 높은 과제 59(jev) 대 25(code) | 충족(엄격 채점) |
| H2 `jev - full` 성공률 하한 >= 0 | -2.0%p [-5.0, +1.1] | 미충족 |
| H3 `jev`가 `full`과 `llm`보다 토큰과 시간이 모두 적음 | `jev - full` 토큰 +4,009 [+2,719, +5,097], 시간 +7.2초 [+5.8, +8.9]. `jev - llm` 토큰 -575 [-1,957, +573], 시간 -11.0초 [-12.6, -9.4] | 미충족 |
| H4 `none` 층 근거 없는 답 | 모든 조건 0/108(근거 없는 값을 답한 적 없음) | 보고만 |

사전 기준의 결과는 보류다(기각 조건인 `jev - code`나 `jev - full` 구간 상한 < 0도 아니다). 아래는 조건별 값이다(Claude 252계열, 756 trial).

| 조건 | 성공 | 의도한 선택기 적용 | 근거 블록 재현율 | 담은 바이트 | 전체 토큰 평균 | 선별 호출 토큰 | 중앙 시간 | p95 시간 |
|---|---|---|---|---|---|---|---|---|
| full | 650/756 (0.860) [0.833, 0.883] | 해당 없음 | 1.000 | 75,511 | 39,489 | 0 | 9.6초 | 17.7초 |
| code | 589/756 (0.779) [0.748, 0.807] | 해당 없음 | 0.981 | 8,784 | 5,425 | 0 | 8.9초 | 15.3초 |
| llm | 596/756 (0.788) [0.758, 0.816] | 0.767 | 0.931 | 5,191 | 44,073 | 40,464 | 25.9초 | 47.5초 |
| jev | 635/756 (0.840) [0.812, 0.864] | 0.567 | 0.993 | 4,861 | 43,498 | 40,080 | 14.1초 | 37.8초 |

- 적용률: Jev 0.567은 대체 327건의 결과다. `undecided` 285건(기준 이상인 블록이 없음. `none` 층 108건이 전부 여기 든다)과 `failed_or_invalid` 42건(Jev 호출 실패 14과제 x 3회). `llm`의 대체 176건은 모두 형식·개수 오류다.
- Jev 호출 실패 26건(HTTP 503 19건, 연결 오류 3건, 시간 초과 3건, 연결 끊김 1건)은 재시도하지 않고 그대로 두었다. 해당 과제의 `jev` 조건은 코드 검색으로 돌아갔고 그 trial은 분모에 있다.
- Jev 호출의 캐시 토큰은 보고되지 않아 `jev` trial 756건이 모두 미보고 호출을 가진다(1,890건). 토큰 값은 알려진 값의 합이다.
- 토큰은 가격을 곱하지 않은 개수다. Jev 토큰을 작업 LLM 토큰과 같게 셌으므로 Jev에 불리하다.

### Codex 56계열(방향 확인용)

| 조건 | 성공 | 의도한 선택기 적용 | 전체 토큰 평균 | 중앙 시간 |
|---|---|---|---|---|
| full | 167/168 | 해당 없음 | 52,688 | 17.8초 |
| code | 165/168 | 해당 없음 | 26,678 | 19.0초 |
| llm | 156/168 | 0.994 | 77,889 | 39.5초 |
| jev | 165/168 | 0.554 | 64,336 | 25.5초 |

`jev - code` 0.0%p [-5.4, +5.4], `jev - full` -1.2%p [-5.4, +1.8]. Codex 사용량은 `input_tokens`에 캐시 읽기(`cached_input_tokens`)가 포함돼 있을 수 있는데 네 필드를 그대로 더해 캐시 읽기를 중복해 셌을 수 있다. 캐시 생성은 보고되지 않아 미보고 호출로 센다. 모든 조건에 같은 방식이라 조건 사이 순서는 바뀌지 않지만 절댓값은 부풀 수 있다. 56계열은 반폭이 약 0.05~0.10이라 판정에 쓰지 않는다.

## 민감도 분석(수집 뒤에 추가, 판정에서 제외)

엄격 채점은 답이 JSON 하나뿐이어야 한다. `none` 층에서 모델이 `{"value": null}` 뒤에 설명 글을 덧붙이는 경우가 많아 엄격 채점의 `none` 성공률이 조건에 따라 25~46%였다(Claude: full 50/108, llm 43/108, jev 30/108, code 27/108). 답 앞뒤의 설명 글과 코드 펜스를 허용해 첫 JSON 객체를 꺼내 다시 채점하면 다음과 같다.

| 조건 | Claude 성공 | `jev` 대비 차이(Claude) |
|---|---|---|
| full | 1.000(756/756) | `jev - full` -0.9%p [-2.3, 0.0] |
| code | 0.984 | `jev - code` +0.7%p [-1.2, +2.7] |
| llm | 0.940 | `jev - llm` +5.0%p [+2.1, +7.9] |
| jev | 0.991 | |

엄격 채점에서 보인 `jev - code`의 이득은 형식 위반이 `jev`에서 덜 났을 뿐이고, 설명 글을 허용하면 사라진다. 이 과제는 코드 검색도 98%를 맞힐 만큼 쉽다. 이 분석은 설계에 없던 것이라 판정에 쓰지 않는다. 확인 평가의 기준은 엄격 채점이다.

## 층별 관찰(Claude, 엄격 채점, 칸이 작아 판정에 쓰지 않음)

| 층 | full | code | llm | jev |
|---|---|---|---|---|
| exact | 102/108 | 103/108 | 106/108 | 108/108 |
| none | 50/108 | 27/108 | 43/108 | 30/108 |
| other | 106/108 | 101/108 | 103/108 | 107/108 |
| stale | 81/108 | 69/108 | 83/108 | 86/108 |
| synonym | 103/108 | 90/108 | 92/108 | 100/108 |
| combine | 103/108 | 97/108 | 105/108 | 96/108 |
| middle | 105/108 | 102/108 | 64/108 | 108/108 |

- `middle`: `llm`이 64/108로 낮다. 선별 LLM과 Jev 질문 모두 블록 앞 2,000글자만 보는데 근거가 4,200글자 블록의 한가운데(영어)라 보이지 않는다(한국어는 2,600글자라 가운데가 보인다). `jev`가 108/108인 것은 Jev가 못 보고 `undecided`로 코드 검색으로 돌아가 코드 검색이 전체 본문의 단어를 맞췄기 때문이다. 즉 이 층의 `jev` 성공은 Jev의 기여가 아니다.
- 언어: 한국어에서 `jev` 309/378이 `code` 265/378보다 높고 영어에서는 326/378 대 324/378로 비슷하다. 한국어에서 `code`가 낮은 것은 단어 집합이 조사가 붙은 어절을 같은 단어로 보지 못하기 때문일 수 있으나 이 실험으로 가르지 못했다.
- 길이: 긴 맥락(96개)에서 `full` 339/378, `jev` 320/378, `code` 299/378이다.

## 관찰과 한계

- 선별 호출 토큰이 원문 전체보다 크다. Jev와 선별 LLM은 후보마다 본문 앞 2,000글자를 받아야 해서 후보 집합을 한 번 통째로 읽는다. 후보 전체가 중앙 약 60,000글자(약 2만 토큰)인 이 표본에서는 `full` 프롬프트가 이미 작아 선별 호출이 절감 이득을 만들지 못했다. 선별은 후보가 한 프롬프트에 들어가지 않거나 가격 차이가 클 때에만 이득이 날 수 있다.
- 토큰 개수를 모델 가격으로 가중하지 않았다. Jev 입력 가격이 작업 LLM보다 훨씬 싸다는 점은 판정에 넣지 않았다. 가격 가중 비교는 다음 실험에서 사전 등록해야 한다.
- 합성 후보는 단어 겹침이 강해 코드 검색이 쉬운 과제를 98% 맞힌다. 층에 동의어와 다른 프로젝트를 넣었지만 `synonym` 층도 코드 검색이 90/108이었다. 천장 효과로 선별기의 차이가 가려졌다.
- Jev 응답은 과제마다 한 번씩만 받아 반복에 재사용했다. 반복 3회의 변동은 작업 LLM 호출에서만 왔다.
- 작은 모델(haiku, gpt-5.6-luna) 결과다. 병렬 실행이고 같은 시각에 다른 작업자가 같은 provider를 쓰고 있어 시간은 상대 비교로만 읽는다.
- 실제 긴 대화 기록과 도구 결과의 분포가 아니다. 이 결과를 제품 효과로 읽지 않는다.
- 수집 뒤 분석 코드에 민감도 분석(`answer_lenient`)을 더했다. 원응답은 바꾸지 않았고 가공과 검증을 다시 실행했다.

## 다음 실험

선행 작업 없이 시작할 수 있는 것부터 적는다.

1. 후보를 한 프롬프트에 들어가지 않는 길이로 늘린다(수백 블록, 전체가 수십만 토큰). `full`이 불가능하거나 비싼 구간에서 선별의 토큰·시간 이득이 생기는지 본다. 같은 규칙, 같은 tau 고정 절차를 쓰고 후보 길이만 바꾼다.
2. 코드 검색이 어려운 층을 늘려 천장 효과를 없앤다(동의어만 있고 프로젝트 이름도 다르게 쓴 표기, 한국어 조사·표기 변형, 정정 문장이 구문으로만 구분되는 경우). 개발 계열에서 코드 검색 성공률이 90% 아래로 내려가는 칸만 확인 평가에 둔다.
3. 답 형식 위반을 줄인다. 채점을 JSON 하나로 엄격하게 하되 프롬프트를 바꾸거나, 추출 규칙을 수집 전에 사전 등록한다(이번처럼 수집 뒤에 추가하지 않는다).
4. Jev와 선별 LLM 질문이 블록의 앞 2,000글자만 보는 한계를 없앤다(긴 블록을 조각으로 나눠 묻는 규칙). 조각을 나누면 호출 수와 토큰이 늘므로 호출 상한을 다시 정한다.
5. 토큰을 가격으로 가중한 비용과 가중하지 않은 개수를 함께 판정에 쓴다. 가격표와 날짜를 설계에 고정한다.
6. 제품 채택 판정은 [#540](https://github.com/woonyong-choi/saturn/issues/540)의 온라인 경로로 실제 다중 턴 작업(B2)을 비교해야 한다. 그 전에 [#574](https://github.com/woonyong-choi/saturn/issues/574), [#576](https://github.com/woonyong-choi/saturn/issues/576), [#577](https://github.com/woonyong-choi/saturn/issues/577)을 닫고 engine에 Jev와 작업 LLM 선별 호출 연결을 더해야 한다.

실행 명령은 같은 폴더의 `run.sh`(`dev`, `lock`, `collect`, `process`, `analyze`, `verify`)이고 입력 계약은 [design.md](design.md)의 표본, 조건, 비용 귀속 절을 그대로 따른다.
