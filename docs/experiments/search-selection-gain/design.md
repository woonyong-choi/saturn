| 관련 설계 | [맥락 고르기](../../design/context-selection.md), [records](../../design/records.md) |

## 질문

같은 후보 집합과 같은 본문 예산에서 Jev가 확률 기준 이상인 블록만 골라 담는 선별이 코드 검색 순위, 작업 LLM 선별, 원문 전체보다 후속 작업의 품질을 유지하면서 전체 토큰과 완료 시간을 줄이는가. 선별 비용(Jev 호출, 작업 LLM 선별 호출), 선별이 판정하지 못해 코드 순위로 돌아간 경우, 근거를 못 담아 틀린 경우를 모두 분모에 넣는다.

앞선 대응 실행 검증기 수집에서 봉인한 낮은 확신 규칙(3번째 확률이 0.5 미만이면 코드 검색으로 대체)이 필요한 블록이 1개뿐인 과제 24건을 전부 대체해 Jev의 효과가 가려졌다. 이 실험은 그 규칙을 고친다. 순위의 마지막 칸이 아니라 블록마다 확률 기준을 넘는지만 보고, 넘는 블록만 예산 안에서 확률 순으로 담는다.

## 가설

| 가설 | 예측 | 판정에 쓰는 값 |
|---|---|---|
| H1 | 선별 이득: Jev 선별의 성공률이 코드 검색보다 높다. | `jev - code` 성공률 차이의 95% 구간 하한이 0 초과 |
| H2 | 품질 유지: Jev 선별의 성공률이 원문 전체보다 낮지 않다. 품질 허용폭은 0이다. | `jev - full` 성공률 차이의 95% 구간 하한이 0 이상 |
| H3 | 효율: Jev 선별의 과제당 전체 토큰과 완료 시간이 원문 전체와 작업 LLM 선별보다 적다. 선별 호출 비용을 포함한다. | `jev - full`, `jev - llm`의 토큰 차이와 시간 차이 구간 상한이 모두 0 미만 |
| H4 | 안전: 근거가 없는 과제(`none`)에서 Jev 선별이 근거 없는 값을 답하는 횟수가 코드 검색보다 많지 않다. | 층별 횟수(보고만) |

세 가설이 모두 맞아야 채택이다. 품질 허용폭을 임의로 완화하지 않는다. 구간이 넓어 하나라도 성립하지 않으면 자동 적용을 켜지 않는다.

## 설계

| 항목 | 값 |
|---|---|
| 조건 | `full`(후보 전체, 품질 상한 참고), `code`(단어 집합 교집합 순위로 예산 안에서 채움), `llm`(작업 LLM이 ID를 최대 5개 고르고 그 순서로 예산 안에서 채움), `jev`(아래 규칙) |
| 배정 | 시드 541001. 한 과제의 네 조건은 같은 후보 집합과 같은 본문 예산(9,000바이트)을 받고 선택 ID만 다르다. 과제마다 실행 순서를 섞는다. |
| 눈가림 | Jev와 선별 LLM의 요청에는 정답과 근거 위치를 넣지 않는다. 요청 상태에서 `expected`, `tests`, `gold`, `future`, `outcome`, `support_ids`, `support` 키를 재귀로 금지한다. |
| 실행 | 공식 Claude CLI(haiku)와 공식 Codex CLI(gpt-5.6-luna). 도구는 끄고 기록 블록은 프롬프트로만 준다. 작업 LLM 선별은 실행 모델과 같다. Jev는 TypeSafe Jev 1.13.0 HTTPS API. 재시도하지 않는다. |
| 반복 | 조합(과제, provider, 조건)마다 3회. 반복 사이에 작업 LLM 선별 호출도 새로 한다. Jev는 과제마다 한 번 부르고 같은 응답을 반복에 재사용한다. 같은 입력의 Jev 일관성은 [#544 측정](https://github.com/woonyong-choi/saturn/blob/main/docs/experiments/jev-decision-consistency/design.md)을 따르며 이 실험에서 다시 재지 않는다. |
| 비용 귀속 | Jev 호출 비용은 그 선택을 쓴 trial마다 전부 귀속한다(자동 적용에서는 입력마다 부르므로). 호출 ID에 `@provider-반복-조건`을 붙여 두 번 합산하지 않게 하고 실제 호출 수는 따로 보고한다. |

### Jev 선별 규칙

| 항목 | 값 |
|---|---|
| 질문 | 블록마다 한 질문(`noul`). 질문에 블록 본문 앞 2,000글자를 싣고 요청 문장은 state에 둔다. 질문 24개씩 나눠 보낸다(큰 요청은 질문 단위로 나눠 보내는 제품 규칙과 같다). |
| 담는 규칙 | 확률이 기준값 tau 이상인 블록만, 확률이 높은 순(같으면 코드 순위)으로 예산 안에서 담는다. 예산에 안 드는 블록은 건너뛰고 작은 블록을 계속 본다. |
| 대체 | 응답 실패, 스키마 오류, 담을 블록이 없음(`undecided`)이면 코드 검색 선택으로 돌아가고 추가 LLM은 부르지 않는다. 요청한 방법과 실제 적용한 방법을 따로 남겨 대체를 적용으로 세지 않는다. |
| tau | 개발 계열 28건의 Jev 응답으로 후보 {0.3, 0.5, 0.7, 0.9} 중 근거 블록 재현율이 가장 큰 값(같으면 더 큰 값)을 정해 `protocol-lock.json`에 고정하고 커밋한 뒤 확인 수집을 시작한다. 개발 정답은 tau 선택에만 쓰고 확인 평가 자료는 열지 않는다. 개발 수집에서 Jev 응답이 실패하거나 스키마가 틀린 과제는 재시도하지 않고 tau 선택에서만 빼며 그 과제 번호를 고정 파일에 남긴다. |

작업 LLM 선별과 코드 검색은 위 질문에 쓰는 같은 후보와 본문 예산을 쓴다. 코드 검색은 후보가 많을 때 단어 교집합 크기와 어휘가 맞지 않는 동의어에서 약하다. 이 약점이 표본 층에 들어 있다.

## 표본

| 항목 | 값 |
|---|---|
| 단위 | 계열 하나가 한 프로젝트의 한 질문과 후보 N개다. 계열은 서로 독립이며 같은 계열의 과제는 하나뿐이다. |
| 층 | `exact`(쉬운 정확 일치), `none`(후보에 근거 없음), `other`(같은 속성의 다른 프로젝트), `stale`(구버전과 정정), `synonym`(질문과 근거가 다른 단어), `combine`(두 근거 결합), `middle`(긴 블록 중간 근거) |
| 언어 | 영어, 한국어(영문 식별자가 섞임) |
| 길이 | 짧은 맥락 후보 24개, 긴 맥락 후보 96개. 블록 길이는 400~1,600글자(`middle`의 근거 블록은 영어 4,200, 한국어 2,600글자) |
| 크기 | 확인 평가 252계열(7층 x 2언어 x 2길이 x 9). 개발 28계열(칸마다 1). 칸마다 같은 수라 층이 한쪽으로 쏠리지 않는다. 쉬운 층도 포함해 유리한 과제만 고르지 않는다. |
| 정답 | 합성 사실이라 숨긴 기대 값과 근거 블록 위치(`support_ids`)가 생성 때 확정된다. 채점은 JSON 답이 기대 값과 정확히 같은지다. 근거가 없는 과제의 기대 값은 null이다. |
| 독립성 | 계열이 개발·평가에 걸치지 않고 fixture 해시와 블록 본문이 겹치지 않는다. 검증기가 매번 확인한다. |
| Codex 범위 | 확인 평가 중 칸마다 2계열(56계열)만 Codex도 받는다. Claude는 252계열 전부다. |

### 크기와 호출 상한의 근거

이슈의 요구는 계열 240개 이상과 조합당 3회 이상이다. 계열 252개와 조합당 3회를 Claude에서 지켰다. 대응 차이를 과제 단위로 부트스트랩하므로 한쪽만 맞는 과제 비율이 0.15라면 구간 반폭은 약 `1.96 x sqrt(0.15 / n)`이고 n=252에서 약 0.048이다. 0.15는 앞선 검증기 수집의 한쪽만 맞은 과제 비율(봉인 36과제 중 15개, 0.42)과 jev-role-efficiency 예비값(0.2 안팎)을 참고한 가정이며, 이 값보다 불일치가 많으면 구간이 더 넓어지고 그만큼 보류로 기운다.

Codex는 실행 한 번이 길고 구독 한도가 있어 계열을 56개로 줄였다. n=56이면 같은 가정에서 반폭이 약 0.10이므로 Codex는 방향 확인과 별도 보고용이고 단독 채택 근거로 쓰지 않는다. 이 조정은 이슈의 240계열 요구에 미달하는 부분이며 근거는 호출 상한과 한도다.

| 대상 | 호출 | 산식 | 상한 |
|---|---|---|---|
| Claude CLI | 3,780 | 252계열 x 반복 3 x (선별 1 + 실행 4) | 3,900 |
| Codex CLI | 840 | 56계열 x 반복 3 x (선별 1 + 실행 4) | 900 |
| Jev | 약 630 | 계열마다 조각 수(짧은 맥락 1, 긴 맥락 4). 개발 28계열은 약 70이고 별도 | 800 |

개발 수집(Jev 약 70회)은 같은 Jev 상한 800에 합산한다. 상한에 닿거나 인증 거절, 원자료 해시 불일치에서 중단한다. 개별 오류와 시간 초과는 보존하고 다음 과제를 진행한다. 자동 재시도하지 않는다. 호출 ID는 원장(`calls.jsonl`)에 선기록한다.

## 분석

| 지표 | 방법 |
|---|---|
| 성공률 | provider, 조건별 Wilson 95% 구간 |
| 대응 차이 | 과제 하나를 단위로 반복 3회를 평균한 값의 차이를 계열 부트스트랩(4,000회, 시드 고정)한 95% 구간. `jev-code`, `jev-full`, `jev-llm`, `llm-code`, `llm-full` |
| 토큰과 시간 | 같은 방법의 대응 차이. 시간은 평균과 중앙값, p95. 토큰은 전체(네 필드 합)를 판정에 쓰고 선별 호출 토큰은 따로 보고한다. 토큰 값은 가격을 곱하지 않은 개수이며 Jev 토큰을 작업 LLM 토큰과 같게 센다(Jev가 더 싸다는 가정을 판정에 넣지 않는다). |
| 선별 | 적용률, 대체 이유별 수, 근거 블록 재현율, 담은 바이트 평균 |
| 층별 | 층, 언어, 길이별 성공률(Wilson). 칸이 작아 판정에 쓰지 않고 어디서 갈리는지 본다. |
| 안전 | `none` 과제에서 근거 없는 값을 답한 횟수, 형식 오류 수 |
| 제외 | 제외와 재시도 수. 0이어야 하며 0이 아니면 보고한다. |

분석은 같은 원응답에서 두 번 실행해 같은 바이트를 내야 한다. 판정은 확인 평가(Claude 252계열)에서 한다. Codex와 개발 구간은 따로 보고한다.

## 판정

| 결과 | 조건 | 설계에 반영 |
|---|---|---|
| 채택 | H1, H2, H3가 모두 성립 | 근거로 `context.select.packet=jev`의 기본 적용 검토를 진행한다. 그래도 제품 채택은 실제 engine 연결을 쓰는 다중 턴 비교(B2)를 통과해야 한다. |
| 기각 | `jev-code` 또는 `jev-full` 구간 상한이 0 미만 | Jev 선별의 품질 이득이 없다고 보고 자동 적용을 켜지 않는다. |
| 보류 | 그 밖 | 자동 적용을 켜지 않고 부족한 증거와 다음 실험을 이슈에 남긴다. |

원문 전체와의 품질 비교는 허용폭 0이라 구간 하한이 0 이상이어야 한다. 즉 Jev 선별이 원문 전체보다 한 과제라도 많이 틀리고 이를 상쇄하는 과제가 없으면 구간이 0을 덮고 보류가 된다. 이는 의도한 엄격함이다. Jev confidence를 작업 성공 확률로 쓰지 않는다. 확률은 블록을 담을지 정하는 순서와 기준에만 쓴다. 이 실험은 효과 결론에 합성 후보를 쓰므로 어느 쪽 결과든 실제 긴 대화 기록에서의 제품 효과로 읽지 않는다.

## 재현

| 명령 | 하는 일 |
|---|---|
| `SEL_CALLER=stub run.sh dev; ... lock; ... collect; ... process; ... analyze; ... verify` | 모델을 부르지 않는 결정적 호출기로 전 과정을 한 번 돌려 파이프라인을 점검한다. 결과는 효과의 근거가 아니다. |
| `run.sh dev` | 개발 계열의 Jev 응답만 받는다. 설계와 실행기가 커밋된 뒤에만 시작한다. |
| `run.sh lock` | 개발 응답으로 tau를 정해 `protocol-lock.json`에 쓴다. 쓴 뒤 커밋한다. |
| `run.sh collect` | 설계와 고정값이 커밋된 뒤에만 확인 평가를 수집한다. |
| `run.sh process`, `analyze`, `verify` | 원응답에서 trial을 다시 만들고 집계하며 계약, 해시, 재계산, 두 번 분석의 일치, 주입 결함 8종 거절을 확인한다. |

원자료는 비공개 폴더에 두고 SHA-256 목록만 `data/SHA256SUMS`로 공개한다.

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
