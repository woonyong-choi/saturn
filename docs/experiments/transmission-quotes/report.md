# 전송 원문 중복: 실험 결과

## 요약

동일 메시지의 중복 문단을 참조로 바꾸는 공통 인코더를 구현했으나 실제 기록·문서의 재생 입력 80개가 기준선과 모두 같았다. 인코더를 적용하기 전후의 글자 수는 각각 786,565자로 절감이 없었다. 이 후보는 채택하지 않았고 이번 runtime 변경만 되돌렸다. 다음 단계의 구현·수집은 시작하지 않았다.

이는 모델 토큰 0% 절감을 실측한 결과가 아니다. 실제 provider 호출은 0건이다. 입력이 모두 같은 상태에서 모델 출력 변동을 압축 성과로 해석하지 않도록 계획한 240호출을 실행하지 않았다. 품질 유지와 실제 토큰 절감은 판정하지 않았다.

## 방법

| 항목 | 값 |
|---|---|
| 이슈 | [#624](https://github.com/woonyong-choi/saturn/issues/624) |
| 사전 설계 | [design.md](design.md), 커밋 `6037f8d8` |
| 상위 비교 | [#623](https://github.com/woonyong-choi/saturn/issues/623) |
| 자료 | 기존 대화·문서 18조건과 새 실제 문서 2조건 |
| 패킷 재생 | 20조건 × 1,000·4,000·16,000 예산 = 60개 |
| 질문별 복원 재생 | 20개 |
| 입력 기준 | 이번 작업 시작 시점의 recall-selection 후보 코드와 보존된 실행 파일 |
| 새 구현 | core의 동일 문단 인코더를 패킷 조립과 engine 원문 복원의 마지막 단계에서 함께 호출 |
| 원문 검증 | Rust가 생성한 후보를 별도 Python 전개기로 펼친 뒤 기준 입력과 바이트 대조 |

인코더는 256자 이상의 동일 문단이 같은 메시지에서 반복될 때 첫 본문을 정의하고 나머지 위치를 내부 참조로 표현했다. 원문에 없는 태그 이름을 골랐고 fenced code 내부를 나누지 않았다. 출처·역할·상태의 위치를 유지하며 안내 문구까지 넣어 길이가 줄지 않으면 원문을 반환했다. 선택한 근거를 바꾸거나 남는 공간을 다른 자료로 채우지 않았다.

추가 문서는 input-handling과 engine-lifecycle의 실제 원문이다. 대화처럼 감싼 입력은 합성이다. 기존 18조건은 개발에 사용했던 자료다. 추가 질문의 정답·원문 해시·근거 줄은 모델 수집 전에 고정했지만 이번에는 응답 평가에 사용하지 않았다.

## 설계와 다른 점

| 변경 | 시점 | 이유 | 결론에 미친 영향 |
|---|---|---|---|
| 계획한 240호출 미실행 | 전송 입력 생성 후, 모델 호출 전 | 모든 실제 자료 입력이 기존과 같았다. 생성 결과의 변동을 압축 효과로 보고하지 않기 위해 중단했다. | H2·H3의 모델 실측 판정은 보류한다. 채택이나 다음 단계 진입으로 해석하지 않는다. |
| 합성 대조 입력 추가 | 실제 자료에서 차이 0 확인 후 | 인코더가 연결되지 않았거나 오래된 실행 파일을 사용한 결과인지 구분했다. | 배선 검증에만 사용하며 제품 성능 표본으로 합치지 않는다. |
| 메시지 사이의 동일 구간 탐색 | 차이 0 확인 후 | 중복이 메시지 내부와 메시지 사이 중 어디에 있는지 구분했다. | 후속 설계 근거인 탐색 분석이며 토큰 절감량이 아니다. |

## 결과

모든 수치는 [summary.json](results/summary.json)과 보존한 원시 재생 결과에서 계산했다.

### 실제 자료 재생

| 대상 | 입력 수 | 기준 글자 수 | 후보 글자 수 | 바뀐 입력 | 원문 복원 일치 |
|---|---:|---:|---:|---:|---:|
| 인계 패킷 | 60 | 695,795 | 695,795 | 0 | 60/60 |
| 질문별 복원 | 20 | 90,770 | 90,770 | 0 | 20/20 |
| 합계 | 80 | 786,565 | 786,565 | 0 | 80/80 |

예산별 패킷은 같은 조건에서 파생된 입력이다. 80개를 독립 대화 80개로 세지 않는다. 모든 출력이 같으므로 이 자료에서 메시지 내부 문단 참조가 압축을 일으키지 않았다는 판단은 출력 파일의 직접 대조에 근거한다. 모델 토큰·출력·응답 품질을 측정한 것으로 대체하지 않는다.

### 합성 대조

| 입력 | 예산별 반복 수 | 기준 글자 수 | 후보 글자 수 | 원문 복원 |
|---|---:|---:|---:|---:|
| 긴 동일 문단 3회 | 3 | 각 5,124 | 각 3,452 | 3/3 |
| 같은 문단 1회 | 3 | 각 2,396 | 각 2,396 | 3/3 |

기준 실행 파일과 후보 실행 파일에 같은 합성 자료를 보냈다. 중복이 있는 입력에서만 결과가 바뀌었고 모두 원문으로 복원됐다. 실행 파일 해시와 Cargo가 반환한 경로를 보존했다. 따라서 실제 자료의 차이 0을 인코더가 연결되지 않은 결과로 설명할 수 없다. 합성 입력의 감소를 실제 대화의 절감률로 사용하지 않는다.

### 메시지 사이의 중복

4,000 예산의 패킷과 해당 질문의 복원 원문을 비교했다. `difflib.SequenceMatcher`에서 `autojunk=False`로 두고 길이 64자 이상의 순서가 대응하는 동일 구간을 합산했다. 20조건에서 합계 24,503자였다. 이는 이 비교 알고리즘이 찾은 구간의 합이며 모든 중복의 완전한 상한이나 토큰 환산값이 아니다.

현재 engine은 패킷을 session 열기의 첫 턴으로 보내고, 질문별 복원은 후속 사용자 턴에 붙인다. 같은 문단이라도 서로 다른 메시지에 있으면 이번 인코더가 합치지 않았다. 이전 턴의 근거가 provider 자동 압축 뒤에도 남아 있다고 가정하지 않기 위해서다. 메시지 사이의 중복을 없애려면 전송 경계와 전달 완료 기록을 함께 다뤄야 한다. 이번 결과만으로 첫 요청 통합이나 작업 상태 분리를 검증했다고 보지 않는다.

## 구현 검증과 복원

후보 상태에서 자동 테스트 1,925개가 통과했고 실패는 0개, 기본 제외는 5개였다. Clippy 경고 금지 검사도 통과했다. 새 인코더의 계약 시험은 중복·서로 다른 문단·역할·부정·태그 충돌·fenced code를 검사했다. 두 재생 exporter는 별도로 실행했다.

효과 없는 runtime 변경을 제거한 뒤 바꿨던 기존 파일 세 개가 작업 시작 시점과 같은 해시인지 확인했다. 이번에 만든 인코더 모듈도 기본 코드에서 제거했다. 이전 작업의 미커밋 변경은 유지했다. 후보 소스·패치·실행 파일은 원자료와 함께 보존했으며 [후보 패치](data/candidate.patch)로 구현 내용을 검토할 수 있다.

복원 뒤 검사 결과는 `summary.json`의 `preflight.tests.final-tests`에 있다. 후보 시험 통과를 제품 채택이나 원문 이해 품질의 증거로 사용하지 않는다.

## 판정

| 기준 | 판정 | 근거 |
|---|---|---|
| H1: 원문 일치 | 관측 입력에서 충족 | 실제 자료 80/80, 별도 합성 대조 6/6 |
| H2: 실제 입력 5% 이상·전체 토큰 감소 | 보류 | 실제 자료 입력 변화 0, provider 호출 미실행 |
| H3: 대응 품질 유지 | 보류 | provider 호출 미실행 |
| 후보 채택 | 미채택 | 실제 자료에서 압축 효과가 없는 코드 |
| 다음 단계 진입 | 진입 보류 | H2·H3 미충족 |

정확히 같은 메시지를 받더라도 모델 출력·사용량은 실행마다 달라질 수 있다. 그 차이는 이번 인코더의 압축 성과가 아니다. 중복이 많은 다른 자료에서의 효과와 메시지를 통합했을 때의 효과는 이 결과로 판정할 수 없다. 채택되지 않은 이전 recall-selection 후보의 품질 문제도 해결됐다고 주장하지 않는다.

## 재현과 보관

```sh
bash docs/experiments/transmission-quotes/run.sh analyze
bash docs/experiments/transmission-quotes/run.sh verify
```

재생된 입력과 계획 파일, 원문 해시, 새 정답표, 합성 대조, source snapshot, 기준·후보 실행 파일, 검사 로그를 비공개 아카이브에 보존했다. 모델 원응답은 생성하지 않았으므로 보관 건수도 0이다. [데이터 설명](data/README.md), [파일 해시](data/SHA256SUMS), [보관 영수증](data/archive.json)에 재현 범위가 있다.
