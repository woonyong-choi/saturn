# router 키 OS 수준 방어 설정 실측: 실험 결과

## 요약

Codex 명령 샌드박스(`:read-only`, `:workspace`)는 시험 항목 조회를 세 호출 형태(직접, `sh -c` 감쌈, API 클라이언트) 모두에서 0/3 접근됨으로 막았다. Claude Code 샌드박스는 켜기만 해서는 막지 못했고(직접 3/3, 감쌈 3/3 접근됨), 키체인 폴더를 `filesystem.denyRead`에 더하면 직접 조회가 0/3 접근됨이었다. 키체인 항목 접근 제어는 호출 프로세스를 가려 신뢰 앱이 아닌 프로세스에 확인 창을 띄웠지만, 이 환경에서는 창이 스크립트 밖의 클릭으로 2.6~4.2초 안에 허용되어 값이 읽혔다. 설계에는 Claude 실행별 설정에 샌드박스와 키체인 폴더 `denyRead`를 넣는 안을 권고하고, 훅(수정 전)은 보조로 둔다.

통제는 성립했다. 샌드박스 밖 세 형태는 모두 종료 코드 0으로 접근됨이었고, 샌드박스 안 `/usr/bin/true`는 두 프로필에서 실행되었다. 신뢰구간 상한이 70.8%인 것은 n이 3이기 때문이다. 이 동작은 결정적이라고 가정해 판정했고 반복 간 불일치는 없었다.

H3의 창은 스크립트가 누르지 않았다. `securityd` 로그에는 시험 네 곳에서 창 표시와 `always allow`, `allow` 응답 사건이 한 쌍씩 있고, 응답은 표시 뒤 2.6~4.2초에 왔다. 누가 눌렀는지는 이 데이터로 알 수 없다. 사용자가 직접 눌렀거나 사용자 환경의 자동화가 눌렀을 수 있다. 같은 이유로 Codex 통제의 샌드박스 밖 API 클라이언트 조회에서도 창이 2회 표시되고 허용되었다. Claude 호출 시간대에는 창 표시가 없었다(0건).

### 탐색 분석

판정 대상 Claude 호출 9회는 모두 Bash를 1회 실행했고(통제만 2회), `dangerouslyDisableSandbox`를 쓴 호출은 0회였다. 샌드박스 켬 조건에서 모델이 샌드박스를 해제하려고 시도한 기록은 없다. 이 관측은 판정에 쓰지 않았다.

## 논의

### 해석

Codex 샌드박스는 명령 이름이나 감싸기 형태와 무관하게 키체인 서비스에 닿지 못하게 했다. 명령 이름 목록을 보는 훅이 놓친 감싼 조회([#423](https://github.com/woonyong-choi/saturn/issues/423))를 OS 층에서 막는다는 뜻이다. 반면 Claude Code 샌드박스는 기본 설정에서 키체인 서비스 호출을 막지 않았다. 공식 문서도 읽기는 기본으로 기기 대부분에 열려 있다고 적고 `denyRead`로 좁히게 한다. 키체인 폴더를 읽기 금지에 더하자 거부되었다. 이 효과가 폴더 읽기 금지에서 왔는지 서비스 호출 차단에서 왔는지는 이 실험으로 가르지 않았다.

접근 제어는 호출 프로세스를 구분해 창을 띄웠다. 그러나 허용은 클릭 한 번이었고 응답이 `always allow` 사건으로 남았다. 창은 방어의 마지막 선이 아니라 사람이나 자동화가 누르면 열리는 문이다. 따라서 키체인 접근 제어는 샌드박스 같은 OS 격리 아래의 보조층으로 보는 것이 맞다.

### 타당성 위협

| 종류 | 위협 | 이 실험에서 |
|---|---|---|
| 내적 | 샌드박스 안 조회가 항목 없음(44)으로 나와 거부와 구분되지 않는다. | 샌드박스 밖 같은 형태가 접근됨(0)이었고 조회 전후 항목이 있었다. 항목 없음과 같은 종료 코드라 거부 사유의 종류는 구분하지 못했다. |
| 내적 | 모델이 명령을 바꾸거나 실행하지 않는다. | 판정 대상 9회는 Bash를 1회 실행했고 도구 결과의 종료 코드로 판정했다. 통제 1회는 표식이 없어 무효였다. |
| 구성 | `codex sandbox`가 실제 Codex 실행 때의 샌드박스와 같은지 보장하지 않는다. | 같은 CLI 하위 명령으로 확인했지만 app-server 경로로 실행한 Codex 명령은 재지 않았다. 사용자 승인 뒤 샌드박스 밖으로 실행되는 경로는 측정하지 않았다. |
| 구성 | `security`로 만든 항목이 `keyring`이 OS API로 만든 항목과 접근 제어가 다를 수 있다. | `keyring` 항목은 직접 재지 않았다. 같은 신뢰 앱 구조라는 가정이다. |
| 외적 | 한 대의 macOS 26.5.2와 한 로그인 키체인, 한 사용자 세션이다. | 일반화하지 않았다. 다른 OS 버전의 샌드박스 정책은 재지 않았다. |
| 외적 | engine 전체를 기동하지 않고 단위 테스트로 H4를 봤다. | engine 기동은 router 확인이 필요해 하지 못했다. 두 테스트는 실제 `Supervisor`와 채팅 환경 경로로 변수 존재를 확인한다. |

### 한계

- 표본이 작고(조건마다 3, 접근 제어는 1) 결정적 동작을 가정했다.
- 확인 창의 응답 주체를 알 수 없다.
- 확인 창 사건을 시험에 맞추는 규칙은 초 단위 시각에 기댄 근사다.
- Claude 호출은 모델이 명령을 실행하는 경로를 거쳐 모델 변동이 있다.
- Claude 샌드박스 끔 통제가 없다.

### 여러 겹을 합쳤을 때 남는 경로

Codex 샌드박스, Claude 샌드박스와 키체인 폴더 읽기 금지, 키체인 접근 제어, 환경 격리, 훅을 모두 합쳐도 남는 경로는 일반적으로 다음과 같다. 구체적 방법은 적지 않는다.

- 샌드박스 밖에서 도는 것. Claude의 파일 도구, MCP 서버, 훅은 Bash 샌드박스 밖이다. 사용자 승인 뒤 샌드박스 밖에서 실행되는 명령과 샌드박스 예외 설정도 같다.
- 확인 창을 사람이나 자동화가 허용하는 경우.
- 같은 사용자 권한으로 도는, provider와 무관한 프로세스. OS 사용자 단위 격리가 없으면 키체인은 같은 사용자에게 열린 저장소다.
- 키체인을 쓸 수 없을 때의 대체 파일(0600). 같은 사용자 읽기는 막지 못하고 샌드박스의 파일 읽기 금지에 기대야 한다.
- engine이 키를 메모리에 두는 동안의 프로세스 단위 노출.

## #423, #2, #102를 닫는 데 필요한 것

- #423: 수정 브랜치에 커밋이 없다. 훅 수정(셸 인자 해석)과 그 단위 테스트, 그리고 Saturn이 띄운 실제 Claude session에서 감싼 조회가 거부되는 실측이 필요하다. 이 실험은 방어 설정의 가능성을 보였을 뿐 Saturn 코드의 수정이 아니라서 닫는 근거가 되지 못한다.
- #2: `keyring`이 OS API로 만든 항목을 다른 프로세스가 확인 창 없이 읽는지 직접 재야 한다. 이 실험은 `security`로 만든 항목만 쟀다. 이슈가 가리키는 `keychain-direct-access/design.md`는 main에 없다. 창을 사람이 누르는지 자동화가 누르는지 가르는 시험도 필요하다.
- #102: API 선택이 남았다. 신뢰 앱 목록이 빈 항목은 다른 프로세스에 창을 띄웠고, 서명 없는 개발 빌드에서도 같은지와 `SecAccess` 경로로 만든 항목의 동작을 재야 정할 수 있다. 키체인 접근 제어를 보조층으로 둔다는 이 실험의 결론이 선택지를 줄인다.
