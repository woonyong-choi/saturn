# 후보 순위와 judge 결합의 전환 품질: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#117](https://github.com/woonyong-choi/saturn/issues/117) |
| 관련 설계 | [맥락 고르기](../../design/context-selection.md), [맥락 정리](../../design/context-management.md) |
| 사전 데이터 | 없음 |

## 질문

맥락 고르기는 후보를 RRF 상위 N개로 좁힌 뒤 judge에 묻는데, 이 결합이 judge 단독보다 전환 품질을 낮추지 않는지 정해야 한다. 같은 기록에서 세 조건으로 만든 패킷을 새 provider session에 넘기고, 이전 작업 질문의 정답률을 같은 질문 쌍으로 비교한다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | RRF 상위 N + judge의 정답률은 judge 단독보다 5%p 넘게 낮지 않다. | 합성 시나리오 24개, Codex와 Claude Code 새 session, Jev, N=10, `k`=60, 패킷 예산 8,000토큰 |
| H2 | RRF 상위 N + judge의 정답률은 RRF 단독보다 높다. | H1과 같다 |

## 설계

| 항목 | 값 |
|---|---|
| 조건 | `judge-only`: 후보 전체를 기록 번호 순으로 64K 이하 요청으로 나눠 `compact`로 묻는다(기준 조건). `rrf-only`: judge 없이 RRF 순서로 채운다. `rrf-judge`: RRF 상위 N개만 묻는 설계 규칙 그대로다. 세 조건 모두 고정 구역과 경쟁 구역 채우기 규칙은 같다. |
| 배정 | 모든 조건이 같은 시나리오와 질문을 받는 대응 설계다. 세션 144개(시나리오 24 × provider 2 × 조건 3)의 실행 순서와 시나리오별 질문 순서는 시드 117로 섞는다. 질문 순서는 세 조건에서 같다. |
| 눈가림 | provider는 조건을 모른다. 패킷과 프롬프트에 조건 이름을 넣지 않는다. 채점은 `02-process`가 정답 목록으로 하고 조건 이름을 보지 않는다. |
| 환경 | macOS, Python 3.9 이상(표준 라이브러리), Codex CLI(`codex exec`), Claude Code(`claude -p`), Jev(`judge.model` 기본값). 모델 이름과 버전은 수집 때 `env.json`에 적는다. provider와 judge의 LLM 샘플링은 시드로 고정할 수 없다. |
| 실행 조건 | [#126](https://github.com/woonyong-choi/saturn/issues/126) 머지, `SATURN_JUDGE_KEY`에 Jev 키, 로그인된 `codex`와 `claude`, `SATURN_PACKET_CMD`에 패킷 생성 명령. 하나라도 없으면 `01-collect`는 원인 한 줄을 쓰고 종료한다. |

- 패킷 생성 명령은 #126의 `sessions` 후보 순위와 `build_packet`을 부르는 명령이다. 입력은 시나리오 파일과 id, 조건, N, `k`, 예산이다. 출력은 패킷 글, 넣은 항목, RRF 전체 순서, judge 호출과 실패 수를 담은 JSON이다.
- 새 session은 도구를 끈 채로 연다. Codex는 `--ephemeral --ignore-user-config --ignore-rules --sandbox read-only`, Claude Code는 `--safe-mode --tools "" --no-session-persistence`로 실행한다. provider가 패킷 밖 파일을 읽지 않게 하기 위해서다.

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `condition` | 조작 | `judge-only`, `rrf-only`, `rrf-judge` | 없음 |
| `provider` | 조작 | 패킷을 받는 새 session의 provider. `codex`, `claude` | 없음 |
| `qtype` | 조작 | 질문 유형. `extract`(정보 추출), `multi-session`(여러 session 추론), `temporal`(시간 추론), `update`(지식 갱신), `abstain`(모르면 모른다고 답하기) | 없음 |
| `correct` | 측정 | 답이 정답 규칙에 맞으면 1, 아니면 0 | 없음 |
| `packet_tokens` | 측정 | 패킷 글자 수를 4로 나눈 추정 토큰 수 | 토큰 |
| `judge_failures` | 측정 | 패킷을 만드는 동안 답하지 못한 judge 요청 수 | 회 |
| `accuracy` | 파생 | 조건별 `correct` 합 / 시행 수 | % |
| `diff_h1` | 파생 | 같은 시행 쌍에서 `accuracy(rrf-judge) - accuracy(judge-only)` | %p |
| `diff_h2` | 파생 | 같은 시행 쌍에서 `accuracy(rrf-judge) - accuracy(rrf-only)` | %p |
| `rrf_missed` | 파생 | 질문의 근거 항목 중 RRF 상위 N개에 들지 않은 항목 | 개 |
| `missed_semantic` | 파생 | `rrf_missed` 중 근거 항목이 마지막 입력과 같은 뜻의 다른 말이나 번역어로만 이어진 항목 | 개 |

정답 규칙은 다음과 같다.

| 질문 유형 | 정답 |
|---|---|
| `extract`, `multi-session`, `temporal` | `unknown`이 거짓이고 답에 정답 값 중 하나가 있다. 정답 값이 여럿이면 모두 있다. |
| `update` | `unknown`이 거짓이고 답에 새 값이 있으며 옛 값이 없다. |
| `abstain` | `unknown`이 참이다. |

- 답의 비교는 소문자로 바꾸고 공백과 쉼표를 지운 글로 한다.

## 표본

| 항목 | 값 |
|---|---|
| 출처 | `01-collect`가 시드 117로 만드는 공개 합성 시나리오 24개. 가상의 쇼핑 서비스 저장소에서 4개 session에 걸쳐 일한 기록이다. 시나리오마다 도구 호출 128개, 질문 10개(유형마다 2개), 정답과 근거 항목 번호가 있다. |
| 크기 | 조건마다 480 시행(시나리오 24 × provider 2 × 질문 10) |
| 크기 근거 | 검정력. 비열등 한계 5%p, 불일치 비율 15% 가정, 단측 α=0.025, β=0.2에서 n = (1.96 + 0.84)² × 0.15 / 0.05² = 471이므로 480으로 정한다. |
| 중단 규칙 | 세션 144개를 모두 실행하면 멈춘다. 연속 5개 세션이 실패하면 환경 문제로 보고 멈추며, 고친 뒤 새 실행 id로 처음부터 다시 수집한다. |
| 반복과 예열 | 세션마다 1회, 예열 없음 |

- 시나리오의 근거 항목은 마지막 입력과 같은 낱말, 번역어, 같은 뜻의 다른 말 중 하나로 이어진다. 세 관계를 시나리오마다 섞고, 실제 비율은 보고서에 적는다. 단어 겹침 채널이 놓치는 경우를 표본에 넣기 위해서다.
- 근거 항목은 최근 3턴보다 앞의 도구 결과에만 둔다. 에이전트 답 글은 사실을 다시 말하지 않는다. 고정 구역만으로 답할 수 없게 하기 위해서다.

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | `diff_h1` | 2×2 표와 불일치 수 b, c. 한계 5%p의 Tango 비열등 점수 검정(단측)과 Newcombe 대응 차이 신뢰구간 | Holm 보정 p ≤ 0.05이고 차이의 95% 신뢰구간 하한 > -5%p |
| H2 | `diff_h2` | 2×2 표와 불일치 수 b, c. McNemar 검정, b+c < 25면 정확 이항 검정. Newcombe 대응 차이 신뢰구간 | Holm 보정 p ≤ 0.05이고 차이의 95% 신뢰구간 하한 > 0 |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | provider가 도구를 한 번이라도 부른 세션, 답 JSON을 읽을 수 없는 세션. 제외는 시나리오와 provider 단위로 세 조건에서 함께 한다. |
| 실패한 실행 | provider 종료 코드가 0이 아니거나 300초를 넘으면 한 번 다시 실행한다. 다시 실패하면 그 시나리오와 provider 단위를 세 조건에서 빼고 흐름 표에 센다. 패킷을 만드는 중의 judge 실패는 조건의 일부로 보고 빼지 않는다. |
| 다중 비교 | 확인 가설 둘에 Holm-Bonferroni |

- 기각은 H1에서 차이의 95% 신뢰구간 상한 ≤ -5%p, H2에서 상한 ≤ 0일 때다. 채택도 기각도 아니면 보류다.
- 정답률은 조건마다 `k/n`, 비율, 95% Wilson 신뢰구간으로 쓴다.

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | 맥락 고르기의 `judge에 넘기기` 규칙과 N 기본값을 유지하고, 요구사항 표의 #117 행 검증 계획을 보고서 링크로 바꾼다. |
| 기각 | H1 기각이면 [#116](https://github.com/woonyong-choi/saturn/issues/116) 결과와 함께 N을 키우거나 judge 단독으로 돌아가는 설계 이슈를 연다. H2 기각이면 패킷의 `compact` 질문을 빼고 RRF만 쓰는 설계 이슈를 연다. |
| 보류 | 시나리오를 늘려 새 실행 id로 다시 수집하고, 질문 유형별 탐색 결과로 차이가 나는 유형을 확인한다. |

## 탐색 분석

- 질문 유형별, provider별 조건 정답률과 차이
- `judge-only`와 `rrf-only`의 대응 비교
- `missed_semantic` / `rrf_missed` 비율과 95% Wilson 신뢰구간. 신뢰구간 하한이 50%를 넘으면 [후보 순위는 임베딩 없이 단어 기반과 용어 카탈로그로 시작한다](../../decisions/2026-10-01-lexical-ranking-with-term-catalog.md)의 다시 볼 조건에 해당한다고 본다.
- 시나리오 단위 군집 부트스트랩(2,000회, 시드 117)으로 구한 `diff_h1`, `diff_h2`의 95% 신뢰구간
- 조건별 `packet_tokens`, `judge_failures`, judge 호출 수

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
| 내적 | 한 세션에서 질문 10개를 함께 물어 같은 세션의 답이 서로 기대므로 시행이 독립이 아니다. | 시나리오 단위 군집 부트스트랩 신뢰구간을 탐색 분석으로 함께 보고한다. |
| 내적 | provider와 judge의 샘플링이 고정되지 않아 같은 패킷도 다른 답을 낼 수 있다. | 세 조건을 같은 시간대에 무작위 순서로 섞어 실행한다. |
| 구성 | 질문 정답률은 전환 품질의 일부만 잰다. 이어 할 작업을 실제로 해내는지는 재지 않는다. | 질문 유형을 다섯으로 나눠 사실, 결합, 시간, 갱신, 모름을 따로 본다. |
| 구성 | 문자열 포함 채점은 맞는 답을 다른 표기로 쓰면 틀림으로 센다. | 정답 값마다 별칭을 두고, 숫자와 날짜는 한 가지 형식으로 답하라고 지시한다. |
| 외적 | 합성 시나리오의 낱말 관계 비율이 실제 기록과 달라 `missed_semantic` 비율이 생성 규칙에 기댄다. | 이 비율은 탐색 분석으로만 보고, 생성 규칙의 관계 비율을 보고서에 함께 적는다. |
| 외적 | 한 가상 서비스와 두 provider의 한 버전에서만 잰다. | 적용 범위를 가설 표에 적고 버전을 `env.json`에 남긴다. |
