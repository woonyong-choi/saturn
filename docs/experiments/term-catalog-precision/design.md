# 용어 카탈로그 짝 정밀도와 묶음 확인 비용: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#127](https://github.com/woonyong-choi/saturn/issues/127) |
| 관련 설계 | [용어 카탈로그](../../design/term-catalog.md) |
| 사전 데이터 | 설계 문서 `term-catalog.md`, `judge.md`, `context-selection.md`를 규칙 확인용으로 읽었다. 이 문서들은 괄호 표기 말뭉치의 일부지만 짝 후보를 뽑거나 세지 않았다. 함께 나옴 출처의 대화 기록은 열지 않았다. |

## 질문

용어 카탈로그의 세 출처(괄호 표기, 같은 턴 함께 나옴, 주석 아래 식별자)가 만든 짝 후보가 실제로 같은 대상을 가리키는 비율을 출처별로 잰다. 그 결과로 짝 점수의 가중치(3, 2)와 확인 대기 기준(점수 2.0, 증거 3번)을 유지할지 정하고, 묶음 확인의 요청 수와 입력 토큰을 계산으로 비교한다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | 괄호 표기 짝 후보의 정밀도는 80% 이상이다. | Saturn 저장소의 한국어 문서, 수집 시점 `main` 커밋 |
| H2 | 주석 아래 식별자 짝 후보의 정밀도는 80% 이상이다. | Saturn 저장소의 소스 코드, 수집 시점 `main` 커밋 |
| H3 | 같은 턴 함께 나옴 짝 후보 중 함께 나온 턴이 3번 이상이고 한글 말마다 Dice 상위 5개인 짝의 정밀도는 50% 이상이다. | 이 컴퓨터의 Claude Code 기록, 2026-10-01 00:00 UTC 이전 |
| H4 | 함께 나옴 짝 후보에서 Dice가 표본 중앙값 이상인 짝의 정밀도는 중앙값 미만인 짝보다 높다. | H3과 같은 표본 |
| H5 | 괄호 표기에서 증거가 3번 이상인 짝의 정밀도는 증거가 1~2번인 짝보다 높다. | H1과 같은 말뭉치 |
| H6 | 출처 정밀도의 순서는 가중치 순서와 같다. 괄호 표기는 주석보다 낮지 않고, 주석은 함께 나옴보다 높다. | H1~H3의 표본 |
| H7 | 짝 20개 묶음 judge 요청의 추정 입력 토큰 중앙값은 2,000~3,000이다. | 아래 토큰 추정 규칙, 괄호와 주석 출처의 확인 대기 짝 |
| H8 | 짝 20개 묶음 요청의 추정 입력 토큰은 같은 짝을 짝마다 한 요청씩 보낸 합보다 30% 이상 적다. | H7의 묶음 200개 |
| H9 | 묶음 확인은 유휴 시간 안에 끝나며 짝 하나 요청과 지연 차이가 작다. | Jev 키가 없어 이번 실험에서 재지 않는다. 판정은 `보류`다. |

## 설계

| 항목 | 값 |
|---|---|
| 조건 | 출처 세 개(`paren`, `comment`, `cooc`)가 조건이다. H7, H8은 묶음 요청(짝 20개)과 짝마다 한 요청을 비교하고, 짝마다 한 요청이 기준 조건이다. |
| 배정 | 라벨을 붙일 짝은 출처마다 시드 127로 무작위 추출한다. 라벨 시트의 행 순서는 세 출처를 섞어 시드 127로 정한다. 토큰 비교의 묶음 200개도 시드 127로 뽑는다. |
| 눈가림 | 라벨을 붙일 때 시트에는 행 번호, 한글 말, 영문 말만 보인다. 출처, 증거 수, Dice, 문맥은 라벨이 끝날 때까지 보지 않는다. |
| 환경 | macOS, Python 3(표준 라이브러리와 numpy), Git, 수집 시점 `main` 커밋. judge 호출은 하지 않는다. Jev 키가 이 환경에 없어 지연을 잴 수 없기 때문이다. 토큰은 tokenizer 없이 글자 수 규칙으로 추정한다. |

### 짝 후보 캐기 규칙

[용어 카탈로그](../../design/term-catalog.md)의 출처 표를 아래처럼 코드로 옮긴다.

| 출처 | 입력 | 규칙 |
|---|---|---|
| `paren` | `git ls-tree`로 고른 `README.ko.md`, `AGENTS.md`, `docs/**/*.md`. 비공개 기록 폴더와 `docs/experiments/**`는 뺀다. | 세 모양을 찾는다. `한글(식별자)`: 괄호 바로 앞 한글 구간과 괄호 안 식별자 하나. `식별자(한글)`: 괄호 바로 앞 식별자와 괄호 안 한글 구간(띄어쓰기로 3단어까지). `` `식별자` `` 앞뒤: 코드 표시 바로 앞과 바로 뒤(공백 하나까지)의 한글 구간 |
| `comment` | `git ls-tree`로 고른 `*.rs`, `*.py`, `*.js`, `*.ts`, `*.sh`, `*.toml` 파일 | 주석 기호(`//`, `#`, `/*`) 뒤 첫 단어가 한글인 줄을 찾는다. 바로 다음 줄에 정의 키워드(`fn`, `def`, `function`, `class`)가 있으면 그 키워드 뒤 이름과 주석의 첫 한글 단어를 짝으로 삼는다. |
| `cooc` | `~/.claude/projects/**/*.jsonl`. `subagents/` 아래 파일과 `isSidechain` 기록은 뺀다. | 사용자 글 입력 하나부터 다음 사용자 글 입력 전까지를 턴 하나로 본다. 사용자 입력의 한글 단어와, 같은 턴 도구 호출 인자(`file_path`, `path`, `notebook_path`, `pattern`, `glob`, 셸 명령 안 경로 모양 글자)의 영문 조각을 짝으로 삼는다. |

- 식별자는 `[A-Za-z_][A-Za-z0-9_.:/<>-]*`이고 2~40자다.
- 한글 구간은 한글 음절이 이어진 것이다. 끝 조사(`에서`, `으로`, `은`, `는`, `이`, `가`, `을`, `를`, `의`, `에`, `로`, `와`, `과`, `도`, `만` 등)는 떼어도 2글자 이상 남을 때만 뗀다. 2~10글자만 쓴다.
- 영문 말은 소문자로 바꾼다. `cooc`의 영문 조각은 [맥락 고르기](../../design/context-selection.md)의 단어 조각 규칙대로 camelCase, snake_case, kebab-case, 기호 경계에서 나누고 알파벳 3글자 이상만 쓴다.
- 사용자 입력은 `isMeta` 기록, 도구 결과, `<command-`, `<local-command-`, `<system-reminder>`, `Caveat:`로 시작하는 글을 뺀다.
- 짝 하나는 `paren`, `comment`에서 `(한글, 영문)`이고 `cooc`에서 `(프로젝트, 한글, 영문)`이다. 카탈로그가 프로젝트마다 자라기 때문이다.
- `cooc`의 Dice는 프로젝트마다 `2 × 함께 나온 턴 ÷ (한글이 나온 턴 + 영문이 나온 턴)`으로 센다.

### 라벨 판정 기준표

라벨은 한 사람(실험자)이 아래 기준표로 붙인다. 두 말만 보고 개발 상식으로 판정한다.

| 라벨 | 기준 | 예 |
|---|---|---|
| `same` | 두 말이 같은 대상이나 개념을 가리킨다. 번역, 음차, 약어, 그 식별자가 정의하는 대상의 한국어 이름을 포함한다. | `로그인`과 `login`, `세션`과 `session`, `설정`과 `config` |
| `different` | 관련은 있어도 다른 대상이거나 무관하다. 상위와 하위 개념, 부분과 전체, 동작과 그 동작을 하는 모듈이 여기에 든다. | `실패`와 `login`, `파일`과 `rs` |
| `unclear` | 두 말만으로 판정할 수 없다. | 뜻을 알 수 없는 약어 |

- 확인 분석에서 `unclear`는 `same`이 아닌 것으로 센다.

### 토큰 추정 규칙

- 묶음 요청 본문은 `{"model": "jev", "question_set": "term@1.0", "state": {"project": 설명, "pairs": [...]}, "questions": [...]}` 모양의 JSON이다.
- 짝마다 state에 `a`(한글), `b`(영문), `evidence`(증거 문장 2개까지, 각 160자까지)를 넣는다.
- 질문은 짝마다 하나이고 id는 `same_{n}`, 종류는 `noul`이다. 문장은 `이 프로젝트에서 A와 B는 같은 대상을 가리킨다.`이고 A, B 자리에 state 경로 `pairs[{n}].a`, `pairs[{n}].b`를 코드 표시로 넣는다.
- 프로젝트 설명은 `README.md` 첫 소개 문단이다.
- 짝마다 한 요청은 같은 모양에 짝 하나만 넣은 것이다.
- 토큰은 ASCII 글자 4개당 1, 한글 음절과 그 밖의 글자 1개당 1로 추정하고 올림한다.

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `source` | 조작 | 짝 후보를 만든 출처: `paren`, `comment`, `cooc` | 없음 |
| `pattern` | 측정 | `paren`의 모양: `ko_paren_en`, `en_paren_ko`, `code_adjacent` | 없음 |
| `evidence` | 측정 | 짝이 나온 횟수(`paren`, `comment`) 또는 함께 나온 턴 수(`cooc`) | 회 |
| `dice` | 파생 | `cooc` 짝의 Dice 계수 | 비율 |
| `label` | 측정 | 기준표에 따른 라벨: `same`, `different`, `unclear` | 없음 |
| `precision` | 파생 | `same` 수 ÷ 라벨을 붙인 짝 수 | % |
| `batch_tokens` | 파생 | 짝 20개 묶음 요청의 추정 입력 토큰 | 토큰 |
| `single_tokens` | 파생 | 같은 20개를 짝마다 한 요청으로 보낼 때 추정 입력 토큰의 합 | 토큰 |
| `token_reduction` | 파생 | `1 - batch_tokens ÷ single_tokens` | % |

## 표본

| 항목 | 값 |
|---|---|
| 출처 | `paren`, `comment`는 Saturn 저장소의 수집 시점 `main` 커밋, `cooc`은 이 컴퓨터의 Claude Code 기록이다. |
| 크기 | 출처마다 무작위 200개. 후보가 200개 이하면 전수다. H5를 위해 `paren`의 증거 3번 이상 짝은 전수를 더한다. 토큰 비교는 묶음 200개다. |
| 크기 근거 | 정밀도. n = 200이면 정밀도 50%에서 95% Wilson 신뢰구간 반폭이 약 6.9%p, 80%에서 약 5.5%p다. 라벨 예산은 한 사람이 하루에 붙일 수 있는 600개 안팎이다. |
| 중단 규칙 | 수집은 한 번 실행하고 끝낸다. 라벨은 시트의 모든 행에 붙인 뒤 멈춘다. |
| 반복과 예열 | 해당 없음. 수집과 토큰 계산은 결정적이다. |

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | `precision` (`paren`) | 비율과 95% Wilson 신뢰구간, 한쪽 정확 이항 검정(기준 80%) | 하한 ≥ 80%면 채택, 상한 < 80%면 기각, 그 밖은 보류 |
| H2 | `precision` (`comment`) | H1 방법 | H1 기준 |
| H3 | `precision` (`cooc`) | 비율과 95% Wilson 신뢰구간, 한쪽 정확 이항 검정(기준 50%) | 하한 ≥ 50%면 채택, 상한 < 50%면 기각, 그 밖은 보류 |
| H4 | `precision` 차이(Dice 위 절반 − 아래 절반) | 차이와 95% Newcombe 신뢰구간(Wilson 결합), 한쪽 두 비율 z 검정 | 차이 하한 > 0이면 채택, 상한 < 0이면 기각, 그 밖은 보류 |
| H5 | `precision` 차이(증거 3번 이상 − 1~2번) | H4 방법. 증거 3번 이상은 전수, 1~2번은 무작위 표본에서 센다. | H4 기준 |
| H6 | `paren − comment`, `comment − cooc` 차이 | H4 방법을 두 쌍에 적용한다. p값은 채택 후보면 `comment − cooc`의 한쪽 p값, 기각 후보면 상한 < 0인 차이의 한쪽 p값 중 작은 값이다. | `comment − cooc` 하한 > 0이고 `paren − comment` 상한 ≥ 0이면 채택. 어느 한 차이의 상한 < 0이면 기각. 그 밖은 보류 |
| H7 | `batch_tokens` | 묶음 200개의 평균, 표준편차, 중앙값, p5, p95 | 중앙값이 2,000~3,000이면 채택, 아니면 기각 |
| H8 | `token_reduction` | 묶음 200개의 평균, 표준편차, 중앙값, p5, p95와 정확한 토큰 수 | 중앙값 ≥ 30%면 채택, 아니면 기각 |
| H9 | 요청 지연 | 재지 않는다. | `보류` |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 한글이나 영문 말이 길이 규칙을 벗어나는 후보는 캐는 단계에서 뺀다. 라벨이 빈 행은 분석에서 빼고 흐름 표에 센다. |
| 실패한 실행 | 읽지 못한 파일과 JSON으로 읽히지 않는 줄은 건너뛰고 수를 `summary.json`에 남긴다. |
| 다중 비교 | H1~H6의 한쪽 p값에 Holm-Bonferroni 보정을 한다. 채택과 기각은 신뢰구간 기준을 만족하고 보정한 p값이 0.05 미만일 때만 하고, 아니면 보류다. H7, H8은 결정적 계산이라 보정하지 않는다. |

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | H1, H2, H6이 채택이면 가중치 3과 2를 유지한다. H3이 채택이면 Dice만으로도 확인 대기에 오르도록 기준을 다시 정한다. 지금은 Dice 최댓값 1이 기준 2.0보다 작아 함께 나옴만으로는 대기에 오르지 못한다. H5가 채택이면 증거 3번 규칙을 유지한다. H7, H8이 채택이면 묶음 확인 문장의 추정치를 측정값으로 바꾼다. |
| 기각 | H6이 기각이면 가중치를 정밀도 순서로 바꾼다. 주석 가중치는 `3 × logit(주석 정밀도) ÷ logit(괄호 정밀도)`를 0.5 단위로 반올림해 0~3으로 자른다. H1이나 H2가 기각이면 그 출처의 모양 중 정밀도가 낮은 모양을 출처 표에서 뺀다. H3이 기각이면 함께 나옴은 다른 출처의 점수를 거드는 보조 증거로만 둔다고 적는다. H5가 기각이면 증거 3번 규칙을 출처별로 다시 정하는 이슈를 연다. H7, H8이 기각이면 추정 문장을 측정값으로 고친다. |
| 보류 | 표본을 늘리거나 사람 두 명의 라벨로 다시 재는 이슈를 연다. H9는 Jev 키가 생긴 뒤 실제 호출로 재는 이슈를 연다. |

## 탐색 분석

- `paren`의 모양별 정밀도
- `comment`에서 정의 키워드를 `struct`, `enum`, `trait`, `type`, `const`까지 넓히고, 주석의 모든 한글 단어를 짝으로 삼을 때의 후보 수와 정밀도
- `unclear`를 빼고 센 정밀도
- 같은 말뭉치에서 `paren`과 `comment`가 찾은 `same` 짝의 겹침(상대 재현율)
- `cooc`의 Dice 구간별 정밀도
- 한글 1글자당 토큰을 0.6과 1.6으로 바꿨을 때 H7, H8의 값
- 확인 대기 규칙(점수 2.0, 증거 3번)을 통과한 짝 수와 그 정밀도

## 타당성 위협

| 종류 | 위협 | 대응 |
