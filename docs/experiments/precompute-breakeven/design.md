# 도구 결과 미리 판단의 손익분기: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#119](https://github.com/woonyong-choi/saturn/issues/119) |
| 관련 설계 | [맥락 정리](../../design/context-management.md), [맥락 고르기](../../design/context-selection.md), [judge](../../design/router.md) |
| 사전 데이터 | 없음. 기록 파일은 설계 머지 전에 열지 않았고, 기록 형식은 provider 기록 형식에 대한 사전 지식으로 정했다. |

## 질문

`compact` 판단을 턴마다 미리 할지, 맥락 정리 때 한 번 할지와 미리 판단을 시작할 맥락 크기를 정한다. 이를 위해 실제 채팅 길이 분포 위에서 두 방식의 judge 질문 수, 추정 입력 토큰, 정리 시점에 남는 질문 수를 비교한다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | 첫 턴부터 미리 판단하면 judge 질문 수는 정리 때 한 번 판단할 때의 3배 이상이다. | 이 컴퓨터의 Claude Code와 Codex 기록, `T`=100,000토큰, N=10 |
| H2 | 활성 맥락이 `T`의 50%를 넘은 뒤부터 미리 판단하면 정리 시점에 남는 질문 수가 50% 이상 줄어든다. | H1과 같은 범위 |
| H3 | 활성 맥락이 `T`의 50%를 넘은 뒤부터 미리 판단하면 judge 추정 입력 토큰은 정리 때 한 번 판단할 때의 1.5배 이하다. | H1과 같은 범위. 토큰 추정 규칙은 변수 절 |

## 설계

| 항목 | 값 |
|---|---|
| 조건 | 기준 조건 `lazy`: 정리 때 한 번 판단. 비교 조건 `pre@s`: 활성 맥락이 `s×T` 이상인 턴부터 턴마다 그 턴의 도구 호출을 판단. `s`는 0, 0.25, 0.5, 0.6, 0.7, 0.8, 0.9 |
| 배정 | 해당 없음. 모든 session에 모든 조건을 결정적 시뮬레이션으로 적용한다. 신뢰구간의 bootstrap 시드는 119다. |
| 눈가림 | 해당 없음. 시뮬레이션 규칙과 채택 기준을 수집 전에 고정한다. |
| 환경 | macOS, Python 3과 numpy. 수집 시점의 운영체제, CPU, 메모리, 도구 버전은 `env.json`에 기록한다. LLM 호출은 없다. |

### 시뮬레이션 규칙

1. session마다 턴 `t`의 맥락 크기 `A_t`, 도구 호출 수 `c_t`, 도구 입출력 글자 수 `b_t`를 읽는다.
2. 모의 맥락 `S`는 첫 턴에 `A_1`, 이후 `S_t = S_{t−1} + max(0, A_t − A_{t−1})`이다. `A_t`가 없으면 증가량을 0으로 둔다.
3. 턴 끝에서 `S_t ≥ T`면 그 턴을 정리 사건으로 보고, 사건 뒤 `S_t`를 패킷 크기 `P = T/10`으로 되돌린다.
4. 정리 사건의 후보는 직전 사건 뒤(첫 사건은 session 시작 뒤)의 도구 호출이다. 앞 사건에서 판단한 호출의 판단은 두 조건 모두 재사용한다고 본다.
5. `lazy`는 사건마다 요청 하나로 `min(N, 후보 수)`개 호출을 묻는다.
6. `pre@s`는 사건이 아닌 턴의 끝에서 `S_t ≥ s×T`면 그 턴의 호출 `c_t`개를 요청 하나로 묻는다.
7. `pre@s`의 사건 요청은 순위 상위 N개 중 아직 판단하지 않은 호출만 묻는다. 순위는 기록에 없으므로 상위 N개를 후보에서 고르게 뽑는다고 보고 기댓값 `min(N, 후보 수) × 미판단 후보 수 ÷ 후보 수`를 쓴다.
8. 호출 하나는 `call_<id>_keep`과 `result_<id>_keep` 두 질문이다([judge](../../design/router.md)).

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `condition` | 조작 | `lazy`, `pre@s` | 없음 |
| `s` | 조작 | 미리 판단을 시작하는 `S`의 `T` 대비 비율 | 비율 |
| `A_t` | 측정 | 턴의 마지막 모델 응답이 보고한 입력 토큰(캐시 읽기와 쓰기 포함)과 출력 토큰의 합 | 토큰 |
| `c_t` | 측정 | 턴 안의 메인 에이전트 도구 호출 수. subagent 내부 호출 제외 | 개 |
| `b_t` | 측정 | 턴 안 도구 호출 인자와 결과의 글자 수 합 | 글자 |
| `compacted_t` | 측정 | 턴 안에서 provider 압축이 일어났는지 | 참, 거짓 |
| `q_total` | 파생 | 조건별 전체 judge 질문 수 | 개 |
| `q_pending` | 파생 | 정리 사건 시점에 묻는 질문 수의 합. 시뮬레이션 규칙 7의 기댓값 | 개 |
| `tok_total` | 파생 | 요청마다 `500 + Σ min(호출 글자 수/4, 1000)`의 합. 호출 글자 수는 그 턴의 `b_t/c_t`다. | 토큰 |
| `tok_pending` | 파생 | 정리 사건 요청의 `tok_total` 몫 | 토큰 |
| `q_ratio(s)` | 파생 | `pre@s`의 `q_total` ÷ `lazy`의 `q_total` | 배 |
| `tok_ratio(s)` | 파생 | `pre@s`의 `tok_total` ÷ `lazy`의 `tok_total` | 배 |
| `pending_cut(s)` | 파생 | `1 − pre@s의 q_pending ÷ lazy의 q_pending` | % |

- `T`는 100,000토큰, N은 10, 요청 기본 토큰은 500, 호출 하나의 토큰 상한은 1,000으로 둔다.
- `T`는 아직 실측 전이다([#7](https://github.com/woonyong-choi/saturn/issues/7)). N=10은 [맥락 고르기](../../design/context-selection.md)의 초안 값이다.

## 표본

| 항목 | 값 |
|---|---|
| 출처 | 이 컴퓨터의 Claude Code 기록과 Codex 기록. 채팅 길이 분포의 대리 표본으로 쓴다. |
| 크기 | 수집 시점의 모든 session, 조건마다 같은 session 전체 |
| 크기 근거 | 전수. 추가 수집 비용이 없으므로 있는 기록을 모두 쓴다. |
| 중단 규칙 | 수집 명령 한 번으로 그 시점의 파일을 모두 읽고 멈춘다. |
| 반복과 예열 | 해당 없음. 시뮬레이션은 결정적이다. |

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | `q_ratio(0)` | session 단위 bootstrap 10,000회의 합 비율 95% 백분위 신뢰구간 | 신뢰구간 하한 ≥ 3 |
| H2 | `pending_cut(0.5)` | H1과 같은 bootstrap | 신뢰구간 하한 ≥ 50% |
| H3 | `tok_ratio(0.5)` | H1과 같은 bootstrap | 신뢰구간 상한 ≤ 1.5 |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 턴이 없는 session, 모든 턴의 `A_t`가 없는 session, subagent 기록 파일, 같은 첫 입력 id를 가진 중복 session 중 턴이 적은 쪽 |
| 실패한 실행 | 읽지 못한 파일과 해석하지 못한 줄은 수를 세어 흐름 표에 적고 분석에서 뺀다. |
| 다중 비교 | 가설마다 기준값 반대쪽에 떨어진 bootstrap 비율을 단측 p값으로 쓰고 Holm-Bonferroni로 α=0.05에서 판정한다. |

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | H2와 H3이 채택이면 `tok_ratio(s)` 신뢰구간 상한이 1.5 이하인 가장 작은 `s`를 시작 조건 `S ≥ s×T`로 [맥락 정리](../../design/context-management.md)에 넣는다. H1만 채택이면 첫 턴부터 미리 판단하지 않는다고 적는다. |
| 기각 | H2가 기각이면 미리 판단을 넣지 않고 정리 때 한 번 판단을 유지한다. H3이 기각이면 `tok_ratio(s)` 상한이 1.5 이하인 `s`가 있고 그 `s`의 `pending_cut` 하한이 50% 이상일 때만 그 `s`로 넣고, 아니면 한 번 판단을 유지한다. |
| 보류 | 정리 사건이 30개 미만이면 판정을 보류하고, `T`가 정해진 뒤([#7](https://github.com/woonyong-choi/saturn/issues/7)) 같은 스크립트로 다시 분석한다. |

## 탐색 분석

- `T`를 60,000토큰과 150,000토큰으로 바꾼 결과
- 호출 하나의 토큰 상한을 75와 4,000으로 바꾼 결과
- 상위 N개가 미판단 호출부터 차는 상한과, 가장 최근 호출 N개라는 가정의 `pending_cut(s)`
- provider별 결과
- 정리 사건에 닿는 session 비율과 provider 압축이 실제로 일어난 session 비율
- `s ≥ 0.5`에서 미리 판단한 질문 중 사건에 닿지 않아 버려진 몫

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
| 내적 | `A_t`가 캐시 계산 방식과 provider 압축 때문에 실제 활성 맥락과 다르다. | 증가량만 쓰고 음수 증가량은 0으로 둔다. provider 압축 발생 비율을 따로 보고한다. |
| 내적 | 같은 session이 이어 쓰기로 두 파일에 나뉘어 중복으로 셀 수 있다. | 첫 입력 id가 같은 session은 턴이 많은 쪽 하나만 남긴다. |
| 구성 | 남는 질문 수는 전환 지연의 대리 지표이고, 실제 지연은 judge 응답 시간에 달렸다. | 남는 질문 수와 남는 추정 토큰을 함께 보고한다. |
| 구성 | 후보 순위를 모르므로 `pre@s`의 남는 질문 수는 고른 추출 가정의 기댓값이다. | 상한 가정과 최근성 가정의 결과를 탐색 분석으로 함께 보고한다. |
| 구성 | 미리 한 판단은 그 턴의 목표 기준이라 정리 시점 목표와 어긋날 수 있다. | 이 실험은 요청량만 재고, 판단 품질은 [#117](https://github.com/woonyong-choi/saturn/issues/117)에 남긴다. |
| 외적 | 사용자 한 명의 Claude Code와 Codex 기록이며 Saturn 채팅이 아니다. | 적용 범위를 이 표본으로 한정하고, Saturn 기록이 쌓이면 같은 스크립트로 다시 분석한다. |
| 외적 | 기록에 provider 전환이 없어 전환 사건을 셀 수 없다. | 정리 사건만으로 판정하고, 전환은 탐색 분석 없이 한계로 적는다. |
