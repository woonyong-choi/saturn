# 실제 과제의 Jev 선별 순효과: 실험 결과

## 요약

2026-10-07의 사전 검사에서 독립 실제 과제 source 스냅샷은 0개였고 실행 가능한 대응쌍도 0쌍이었다. `collect`는 외부 호출 0회 상태에서 중단했다. H1~H4와 80쌍 확인 평가는 측정하지 않았다.

## 방법

| 항목 | 값 |
|---|---|
| 설계 | [실험 설계](design.md). 사전 검사 당시 설계와 수집기는 커밋 전이었고 외부 수집을 시작하지 않았다 |
| 실행 id | 해당 없음. 원자료 수집을 시작하지 않았다 |
| 환경 | [env.json](env.json) |
| 표본 | 독립 확인 평가 계획 80쌍, 실제 등록 0쌍 |

기존 #540 작업 트리의 `.runtime`과 `.local`에서 source manifest·스냅샷을 조사했다. 발견한 `saturn.db` 94개는 기존 합성·기능 진단의 `ar`, `preserve`, `sc`, `so`, `q` 계열 폴더에 있었다. 독립 실제 과제의 source 대화와 작업 폴더 스냅샷, 숨긴 검사를 함께 갖춘 등록 사례는 없었다. GitHub의 공개 이슈만으로는 같은 출발 기록을 두 조건에 복제할 수 없으므로 대응쌍으로 세지 않았다.

`./run.sh inventory`를 실행해 manifest 없음, 실제 source 0개, 실행 가능 0쌍, provider 호출 0회를 확인했다. `./run.sh collect`는 `preflight failed: no sealed real-task source snapshots; provider calls: 0`으로 종료했다. 이 종료는 source 없는 provider 호출을 막는 예상한 동작이다. `seal`, raw collector, `process`, `analyze`, `verify`는 실행하지 않았다.

## 설계와 다른 점

처음에는 80쌍을 즉시 수집하는 초안을 작성했으나, 수집 전에 실제 source 가용성을 확인하고 자료 확보·기능 진단·독립 확인 평가를 분리했다. 효과 자료를 열람하기 전의 수정이며 H1~H4의 품질 허용폭과 판정 기준은 완화하지 않았다.

## 논의

### 해석

이 결과는 Jev의 품질이나 비용 효과를 말하지 않는다. 현재 있는 DB와 원자료는 앞선 장치 또는 합성 사례여서 독립 실제 과제의 source로 재사용하지 않는다. #540의 기능 진단을 다시 확인해도 #7의 실과제 순효과 측정으로 바꾸어 부르지 않는다. 발신 패킷 캡처가 생기더라도 provider가 받은 본문이라는 증거는 아니며, 수신을 관측하지 못하면 H4를 보류한다.

### 타당성 위협

| 종류 | 위협 | 이 실험에서 |
|---|---|---|
| 내적 | provider 응답과 캐시가 순서에 따라 변한다. | provider를 호출하지 않아 영향이 없다 |
| 구성 | 실과제의 숨긴 검사가 요구 품질을 모두 포착하지 못한다. | 등록한 과제가 없어 평가하지 않았다 |
| 외적 | 공개 저장소 과제와 두 모델은 Saturn 전체 사용자를 대표하지 않는다. | 표본이 없어 일반화하지 않았다 |
| 계측 | CLI 구독 사용량과 API 단가 환산액은 실제 청구액이 다르다. | 사용량과 비용을 계산하지 않았다 |

### 한계

- 실제 source를 준비하고 사전 등록하기 전에는 기능 진단과 확인 평가를 실행할 수 없다.
- 수집기의 raw 기록, 패킷 대조, 호출 상한, 독립 채점, 비용 분석은 실제 source로 검증되지 않았다.
- 기존 합성 결과의 유리한 사례만 뽑아 새 확인 평가의 효과로 쓰지 않는다.

## 재현

```sh
./run.sh inventory
./run.sh collect
```

첫 명령은 source 0개를 출력한다. 둘째 명령은 외부 호출 전에 종료 코드 1로 끝난다. 실행 가능한 사례가 생겨도 설계·실행기 커밋과 비공개 manifest 봉인 전에는 provider를 호출하지 않는다.

## 결론

| 가설 | 판정 | 반영한 문서 |
|---|---|---|
| H1~H4 | 미평가. 실제 과제 0쌍 | 없음 |

실제 source의 확보와 원자료 계약 검증을 먼저 마친 뒤 기능 진단을 별도로 수행한다. 80쌍 독립 확인 평가는 그 뒤에 새 source로만 진행한다.
