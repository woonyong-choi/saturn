# 실제 과제의 Jev 선별 순효과: 실험 결과

## 요약

2026-10-07의 최초 사전 검사에서 독립 실제 과제 source 스냅샷은 0개였고 `collect`는 외부 호출 0회 상태에서 중단했다. 이후 별도 기능 진단용 공개 이슈 #577의 새 source를 s1과 s2로 각각 재생했다. 첫 J target은 작업 경로 오염으로 무효였고 s2의 R/J target은 아직 호출하지 않았다. 유효 대응쌍은 0쌍이다. H1~H4와 80쌍 확인 평가는 측정하지 않았다.

## 방법

| 항목 | 값 |
|---|---|
| 설계 | [실험 설계](design.md). s1은 `32797cbf`, 첫 target은 `655897a8`, s2는 `c86e3473` 사전등록 뒤 실행했다 |
| 실행 id | 최초 사전 검사, 미봉인 s0 실패, s1 source, 무효 t1J, s2 source |
| 환경 | [env.json](env.json) |
| 표본 | 독립 확인 평가 계획 80쌍과 등록 0쌍. 별도 기능 진단 source 2건, 무효 J 1건, 유효 target 대응쌍 0쌍 |

기존 #540 작업 트리의 `.runtime`과 `.local`에서 source manifest·스냅샷을 조사했다. 발견한 `saturn.db` 94개는 기존 합성·기능 진단의 `ar`, `preserve`, `sc`, `so`, `q` 계열 폴더에 있었다. 독립 실제 과제의 source 대화와 작업 폴더 스냅샷, 숨긴 검사를 함께 갖춘 등록 사례는 없었다. GitHub의 공개 이슈만으로는 같은 출발 기록을 두 조건에 복제할 수 없으므로 대응쌍으로 세지 않았다.

최초 `./run.sh inventory`는 manifest 없음, 실제 source 0개, 실행 가능 0쌍, provider 호출 0회를 확인했다. `./run.sh collect`는 `preflight failed: no sealed real-task source snapshots; provider calls: 0`으로 종료했다. 이 종료는 source 없는 provider 호출을 막는 예상한 동작이다. 확인 평가의 `seal`, raw collector, `process`, `analyze`, `verify`는 실행하지 않았다.

그 뒤 공개 실과제 #577의 source 대화를 만들려고 미커밋 예비 runner를 한 번 호출했다. engine은 router 키가 없어 `RouterKey`로 입력을 접수 전에 확정 거절했다. provider 작업은 0건이고 작업 폴더 해시는 전후 동일했다. 실패한 홈·원응답은 무시 대상 로컬 경로에 보존했다. 이 시도는 봉인 전이므로 기능 진단이나 확인 평가 자료가 아니다. 키 값은 출력하거나 원응답에 저장하지 않았다.

사전등록 커밋 `32797cbf` 뒤 새 시도 ID `s1`로 같은 공개 과제의 source를 재생했다. 시작 파일은 수정 직전 커밋 `7f533049a32233332e70020aff05f2bbf98702ad`의 고정 스냅샷이다. Codex `gpt-5.6-luna`가 읽기 전용 선행 요청을 완료했고, `ToolResult` 13건의 본문 합계는 1,219,097바이트였다. source 작업 폴더의 전후 해시가 같았다. 원자료와 DB의 SHA-256은 각각 `5fff75d94e6eef6aa9a9083074d4357a5db420c7cea71f49a504b20d5c469781`, `f9e6ce63d7c1abc9612b824d902cdc36ae4d1268e135aece264534581fcdc027`이다. 홈·작업 트리 해시는 [summary.json](results/summary.json)에 기록했다. 원자료는 Git 무시 대상 `.runtime/jr/s1`에 보존하고 키 일치 문자열 0건을 확인했다. 이 source는 실제 역사 대화가 아니라 공개 실과제를 새로 재생한 대화다. 이 단계에는 아직 R/J target 자료가 없었다.

이후 사전등록 커밋 `655897a8`의 첫 대응 진단을 한 번 실행했다. J는 첫 입력과 봉인한 피드백을 각각 한 번 보내 원자료를 보존했다. R은 복제 단계에서 source 작업 폴더 해시가 달라져 입력 전에 중단했다. 확인 결과 복제 DB의 `chats.workdir`이 여전히 s1 원본의 절대 경로였고, J의 작업 변경은 target 복제본이 아니라 s1 원본에 생겼다. s1 원본에 `target/` 아래 파일 7,017개가 추가되고 코드·문서 파일 4개가 수정됐다. 삭제는 없었다. t1J 작업 복제본은 봉인 해시 그대로이며 t1R의 시도 장부와 입력은 없다. J 원자료와 변경 경로 목록은 Git 무시 대상에 보존했다. 이 J 실행은 올바른 복제 작업 폴더의 결과가 아니므로 기능 진단의 성공이나 Jev 효과로 세지 않는다.

사전등록 커밋 `c86e3473` 뒤 공통 실제 작업 경로의 `source-preflight`가 외부 호출 0회로 통과했다. `source`를 정확히 한 번 실행해 s2를 봉인했다. Codex `gpt-5.6-luna`의 읽기 전용 선행 작업에서 후보 `ToolResult` 13건이 나왔다. source 작업 트리 SHA-256은 시작 baseline과 같은 `84c42ce600424c2d3c9b88b1e1a4b700c6b078c1b315ef6e51045504134489d9`이다. 원자료·DB·홈 트리 SHA-256은 각각 `da36bffd20d554b411b30277530756635f013b9e8ff806b1ffd7b333040b3d74`, `9621e528600143795ef447d1a15f1ac065853699eebfa8db456e1e03eb7ede55`, `9075b34d5bbb2b5c6d0ad863a8350b29164defd534514b510d9a61d1d5bee5fc`이다. 후보 기반 SHA-256은 `1b116004f6b4791eff311941922e3446e537e76ef4ad04f6d3929713d677605b`이다. 해시 재대조와 키 일치 0건을 확인했고, 활성 작업 경로는 비워 두었다. `target-j-preflight`는 통과했지만 target 입력은 보내지 않았다. s2도 역사적 대화가 아닌 공개 실과제의 새 재생 source이며 확인 평가에 넣지 않는다.

## 설계와 다른 점

처음에는 80쌍을 즉시 수집하는 초안을 작성했으나, 수집 전에 실제 source 가용성을 확인하고 자료 확보·기능 진단·독립 확인 평가를 분리했다. 효과 자료를 열람하기 전의 수정이며 H1~H4의 품질 허용폭과 판정 기준은 완화하지 않았다.

사전 검사 뒤 기능 진단의 별도 모집단을 2026-10-05~2026-10-06에 닫힌 공개 이슈로 정했다. #577의 새 재생 source가 가능한지 살피는 절차를 추가했으며, 2026-07-01~2026-09-30의 80쌍 확인 모집단에는 넣지 않는다. 기능 진단의 답과 비용을 H1~H4 판정에 넣지 않는다.

source 재생을 사전등록 커밋 뒤 추가로 실행해 최초 가용성 0개가 기능 진단 source 1개로 바뀌었다. 첫 target 실행은 작업 경로 오염으로 무효가 되어 유효 대응쌍과 확인 평가 분모는 여전히 0이다.

첫 대응 진단 뒤 DB가 이전 채팅의 작업 폴더를 우선한다는 원인을 확인했다. 실패한 시도를 보존한 채, 다음 시도는 source 생성부터 두 조건이 순차로 공유할 동일한 실제 작업 경로를 쓰도록 별도 사전등록한다. 이것은 기능 진단의 계측 수정이며 확인 평가의 사전 지정 가설·판정 기준을 바꾸지 않는다.

공통 실제 작업 경로의 s2 source 재생을 사전등록 뒤 완료했다. target을 보기 전에 source 해시와 후보 수를 보고서와 요약에 고정했다. s2 target 결과는 아직 열람하거나 판정하지 않았다.

## 논의

### 해석

이 결과는 Jev의 품질이나 비용 효과를 말하지 않는다. 기존 합성·장치 원자료와 #577의 무효 J 실행은 독립 확인 평가의 source나 결과로 재사용하지 않는다. #540의 기능 진단을 다시 확인해도 #7의 실과제 순효과 측정으로 바꾸어 부르지 않는다. 발신 패킷 캡처가 생기더라도 provider가 받은 본문이라는 증거는 아니며, 수신을 관측하지 못하면 H4를 보류한다.

### 타당성 위협

| 종류 | 위협 | 이 실험에서 |
|---|---|---|
| 내적 | provider 응답과 캐시가 순서에 따라 변한다. | s1·s2 source를 각 한 번 호출했고 유효 R/J 비교는 아직 없다 |
| 구성 | 실과제의 숨긴 검사가 요구 품질을 모두 포착하지 못한다. | 첫 target은 잘못된 작업 경로에서 실행돼 검사의 품질 판정에 쓰지 않았다 |
| 외적 | 공개 저장소 과제와 두 모델은 Saturn 전체 사용자를 대표하지 않는다. | 표본이 없어 일반화하지 않았다 |
| 계측 | CLI 구독 사용량과 API 단가 환산액은 실제 청구액이 다르다. | source 사용량 원행만 보존했고 비용을 계산하지 않았다 |

### 한계

- 첫 기능 진단 source와 target은 경로 오염으로 유효 대응쌍을 만들지 못했다. s2 source는 공통 실제 작업 경로에서 봉인했지만 target은 아직 미실행이다.
- 무효 J의 raw는 보존했지만 올바른 작업 폴더의 패킷 대조, 독립 채점, 비용 분석은 검증되지 않았다.
- 기존 합성 결과의 유리한 사례만 뽑아 새 확인 평가의 효과로 쓰지 않는다.

## 재현

```sh
./run.sh inventory
./run.sh collect
```

두 명령은 독립 확인 평가 manifest가 없어 외부 호출 전에 종료한다. 위의 source 0개는 `s1` 생성 전의 최초 사전 검사 기록이다. 첫 재생 절차는 [s1 스크립트](scripts/02-source-replay.py), 경로 격리 재생 절차는 [s2 스크립트](scripts/04-physical-workdir.py)에 고정한다. 로컬 원자료는 공개하지 않는다. s2 source는 사전등록 뒤 생성했고 target은 아직 호출하지 않았다.
