# 기록 변환 충실도와 전환 품질: 실험 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#199](https://github.com/woonyong-choi/saturn/issues/199) |
| 관련 설계 | [provider 연결과 session](../../design/providers-and-sessions.md), [맥락 고르기](../../design/context-selection.md), [맥락 정리](../../design/context-management.md) |
| 사전 데이터 | 작업 3개(시드 1990, 이 실험의 24개와 다른 작업)를 두 provider로 한 번씩 실행해 근거 사실 수와 사용률 증가를 쟀다. 작업마다 두 provider가 모두 거친 근거 사실이 13개 중 13개였고, 사용률은 Claude 주간 24%에서 24%, 5시간 창 40%에서 41%, Codex 주간 9%에서 9%였다. 수집 도구를 맞추려고 이 실행의 Saturn 이벤트 일부를 읽었고, 패킷 예산을 정하려고 예산 450, 550, 650, 800토큰에서 근거 사실이 패킷에 든 비율을 봤다. 이 자료는 저장소에 두지 않고 분석에 쓰지 않는다. |

## 질문

받는 쪽을 고정했을 때 Codex(GPT-6 Sol)로 진행한 기록의 패킷이 Claude Code(Opus 5.5)로 진행한 기록의 패킷보다 전환 품질이 낮은지, 낮다면 Saturn의 변환(이벤트 받기, 도구 종류 변환, 경로 추출, 메모) 때문인지 정해야 한다. 1단계는 받는 쪽 없이 변환 충실도를 기계로 재고, 미리 정한 조건을 채울 때만 2단계에서 받는 쪽을 고정한 2×2로 정답률을 잰다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| C1 | Codex 기록의 근거 항목 포착률, 도구 종류 변환 정확도, 파일 경로 추출 정확도, 메모 필드 정확도는 각각 Claude 기록보다 5%p 넘게 낮지 않다. | 합성 작업 24개, 두 provider가 모두 거친 근거 사실과 항목, engine 변환 코드와 provider 버전은 `env.json`에 적는다. |
| C2 | 같은 받는 쪽에서 Codex 기록 패킷의 정답률은 Claude 기록 패킷보다 10%p 넘게 낮지 않다. | C1 판정 뒤 2단계 진행 조건을 채울 때만, 받는 쪽 Opus 5.5와 GPT-6 Sol 새 session(도구 끔) |

## 설계

| 항목 | 값 |
|---|---|
| 조건 | 1단계: 기록을 만든 provider(`codex`, `claude`). 같은 작업과 지시문을 두 provider가 각각 실제로 진행한다. 2단계: 기록을 만든 provider × 받는 쪽(`claude`, `codex`) 2×2 |
| 배정 | 작업 24개는 시드 199로 만든다. 1단계는 두 provider에 같은 작업을 주는 대응 설계이고, 2단계의 세션 실행 순서는 시드 199로 섞는다. |
| 눈가림 | 받는 쪽은 패킷을 만든 provider를 모른다. 패킷과 지시문에 provider 이름을 넣지 않는다. 채점은 `02-process`와 `03-analyze`가 정답 값 포함 여부로 하고 조건 이름을 보지 않는다. |
| 환경 | macOS, Python 3.9 이상(표준 라이브러리), Rust(`cargo`), Codex CLI의 `app-server`, Claude Code `-p`. 모델은 `gpt-6-sol`과 `claude-opus-5-5`. provider의 LLM 샘플링은 시드로 고정할 수 없다. |

수집과 처리 방식은 다음과 같다.

- 기록 수집은 engine의 provider 연결 코드를 그대로 쓴다. 예제 `saturn-terminal/engine/examples/record-fidelity`가 `ProviderConnection`으로 session을 열고 지시문을 한 번 보낸다. engine 라이브러리 코드는 바꾸지 않는다.
- provider 실행 파일 자리에 `scripts/shim.py`를 끼워 engine과 provider 사이에 오가는 줄을 `raw/`에 저장한다. Claude Code는 `claude -p --input-format stream-json --output-format stream-json --verbose`(engine이 쓰는 인자)로 실행하고 `--dangerously-skip-permissions --setting-sources project`를 더한다. Codex는 `codex app-server`로 실행하고 `-c approval_policy="never" -c sandbox_mode="workspace-write"`를 더한다.
- Codex는 `codex exec --json`이 아니라 `codex app-server`를 쓴다. `exec --json`의 항목에는 engine 변환이 읽는 `commandActions`가 없어 같은 변환 코드로 재생할 수 없기 때문이다. 두 provider 모두 engine이 실제로 쓰는 경로다.
- 재생은 같은 예제를 `SHIM_REPLAY`로 실행해 저장한 `out` 줄을 순서대로 돌려주는 방식이다. 재생한 Saturn 이벤트(`ProviderEvent`)가 분석의 Saturn 기록이다.
- 저장 전 `shim.py`의 `clean`이 개인 설정과 계정 줄(skills 목록, MCP 서버, 훅, 계정과 한도 알림, 설치 식별자)을 지우고 작업 폴더, 홈 경로, 호스트 이름, 사용자 이름을 바꾼다. Saturn 변환이 읽는 도구 항목, 사용량, 턴 시작과 끝, 모델, 권한 방식은 바꾸지 않는다.

작업 하나는 다음과 같다.

| 단계 | 내용 | 정답 근거 사실 |
|---|---|---|
| 1~4 | 파일 `notes/a.txt`~`d.txt`를 하나씩 읽는다. 파일마다 `이름: 값` 줄 2개를 심었다. | 값 8개 |
| 5 | `scripts/summary.py`를 실행한다. 출력에 값 2개가 있고 종료 코드는 0이다. | 값 2개 |
| 6 | `scripts/check.py`를 실행한다. 규칙 이름 1개를 출력하고 종료 코드 3으로 끝난다. | 값 1개 |
| 7 | `config/app.cfg`의 두 줄을 한 번에 고친다. 더한 줄 2, 지운 줄 2다. | 없음(종류, 경로, 줄 수만 잰다) |
| 8 | `python3 -m unittest tests.test_rules`를 실행한다. 실패 테스트 2개, 통과 2개, 종료 코드 1이다. | 실패 테스트 이름 2개 |

- 값은 `낱말_네자리숫자` 꼴 무작위 값이라 지시문과 파일 이름에서 짐작할 수 없다. 지시문은 `done`만 답하라고 해 에이전트 답 글에 사실이 다시 나오지 않게 한다.
- 정답 근거 사실은 작업당 13개다. 두 provider가 모두 거친 사실은 두 provider의 원시 줄에서 도구 결과에 그 값이 있는 것으로 정한다. 수정 항목은 두 provider가 모두 그 파일을 고친 경우에만 항목에 센다.

Saturn 기록과 측정 규칙은 다음과 같다.

| 이름 | 규칙 |
|---|---|
| 기록 | 재생한 이벤트에서 `ToolCall`과 `ToolResult`를 `call_id`로 이은 도구 기록, `Text`를 이은 에이전트 기록 |
| 도구 종류 | `ReadingFile`은 파일 읽기, `EditingFile`은 파일 수정, `RunningCommand`는 셸 명령. 테스트 실행은 이벤트로 구분할 수 없어 셸 명령이 된다. |
| 파일 경로 | 이벤트에 경로 필드가 없다. 정답 상대 경로가 기록의 명령 글이나 결과 글에 있으면 추출했다고 센다. |
| 메모 필드 | [맥락 고르기](../../design/context-selection.md)의 메모 틀에서 종류별 필드를 이벤트로 얻을 수 있는 만큼 얻어 정답과 대조한다. 셸 명령과 테스트 실행은 명령 글에 정답 명령이 있고 결과 글 첫머리 `Exit code N`의 N이 정답 종료 코드와 같아야 한다. 테스트 실행은 통과, 실패 수와 실패 이름도 같아야 한다. 파일 읽기는 경로를 얻어야 한다. 파일 수정은 경로와 더한 줄 수, 지운 줄 수를 모두 얻어야 하는데 이벤트에 줄 수가 없다. |
| 항목과 기록의 대응 | 근거 값이 든 첫 도구 기록이 그 항목의 기록이다. 수정 항목은 첫 `EditingFile` 기록이다. 대응하는 기록이 없으면 포착하지 못한 항목이고 종류, 경로, 메모는 틀린 것으로 센다. |
| 패킷 | `saturn-core`의 `packet` 예제로 만든다. 마지막 입력은 두 번째 사용자 입력으로 근거 사실 질문 목록을 준다. 예산 `P_max`는 800토큰이고 `k`=60이다. 조건은 `rrf-only`(RRF 순서)와 `oracle`(근거 값이 든 기록의 확률 1, 나머지 0으로 `judge-only`에 넣는다)다. 근거 사실이 패킷 글에 있으면 들어간 것으로 센다. |

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `provider` | 조작 | 기록을 만든 provider. `codex`, `claude` | 없음 |
| `receiver` | 조작 | 2단계에서 패킷을 받는 새 session. `claude`, `codex` | 없음 |
| `captured` | 측정 | 근거 사실의 값이 Saturn 기록의 도구 결과에 있으면 1, 아니면 0 | 없음 |
| `kind_ok` | 측정 | 항목에 대응한 기록의 도구 종류가 정답 종류와 같으면 1 | 없음 |
| `path_ok` | 측정 | 파일 읽기와 수정 항목에서 경로를 추출했으면 1 | 없음 |
| `memo_ok` | 측정 | 항목의 메모 필드를 모두 정답으로 얻었으면 1 | 없음 |
| `in_packet` | 측정 | 근거 사실의 값이 패킷 글에 있으면 1. `rrf-only`, `oracle` 두 가지 | 없음 |
| `correct` | 측정 | 2단계에서 받는 쪽의 답에 정답 값이 있으면 1 | 없음 |
| `diff` | 파생 | 같은 근거 사실이나 항목에서 Codex 기록의 값 - Claude 기록의 값의 평균 | %p |
| `mean_common_facts` | 파생 | 작업당 두 provider가 모두 거친 근거 사실 수의 평균 | 개 |

## 표본

| 항목 | 값 |
|---|---|
| 출처 | `scripts/tasks.py`가 시드 199로 만드는 공개 합성 작업 24개. 작업마다 작업 폴더, 지시문, 정답이 있다. |
| 크기 | 1단계 24개 작업 × 2 provider = 세션 48개. 근거 사실은 작업당 13개, 항목은 작업당 8개다. 2단계는 24개 작업 × 2 기록 × 2 받는 쪽 = 세션 96개이고 작업마다 두 provider가 모두 거친 근거 사실만 묻는다. |
| 크기 근거 | 예산. 사전 시험에서 작업 3개(세션 6개)가 Claude 주간 사용률을 올리지 않아(1%p 해상도 미만) 24개는 최대 약 8배다. 이 실험의 한도는 두 provider 주간 사용률 각각 시작 대비 +3%p다. 2단계 진행 조건의 크기 기준(공통 근거 사실 200개 이상)은 10%p 차이를 가르려고 정한 값이다. |
| 중단 규칙 | 배치(작업 4개 × provider 2개)마다 사용률을 읽는다. Claude나 Codex 주간 사용률이 시작 대비 +3%p를 넘으면 멈추고 수집한 작업만 분석한다. Claude 5시간 창이 85%를 넘으면 초기화까지 기다린다. |
| 반복과 예열 | 세션마다 1회, 예열 없음 |

사용량 한도는 다음 값에서 시작한다. 시작 전 Claude 주간 24%, 5시간 창 40%, Codex 주간 9%다(2026-10-02 확인). 두 실험이 같은 계정을 쓰므로 실제 증가에는 다른 실험의 사용이 섞인다. 동시 실행은 provider당 하나로 합쳐 둘 이하다.

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| C1 | `captured`, `kind_ok`, `path_ok`, `memo_ok` 각각의 `diff` | 두 provider가 모두 거친 근거 사실(포착률)과 항목(나머지)에 대한 2×2 대응 표, Newcombe 대응 차이 95% 신뢰구간. 작업 단위 군집 부트스트랩(2,000회, 시드 199) 구간을 함께 낸다. | 지표마다 차이의 95% 신뢰구간 하한 > -5%p면 채택, 상한 ≤ -5%p면 기각, 그 밖은 보류. 두 구간의 판정이 다르면 보류. 네 지표가 모두 채택이면 C1 채택, 하나라도 기각이면 C1 기각, 그 밖은 보류 |
| C2 | 받는 쪽마다 `correct`의 `diff` | 같은 근거 사실에서 Codex 기록 패킷과 Claude 기록 패킷의 대응 차이, 작업 단위 군집 부트스트랩 95% 구간(2,000회, 시드 199)과 Newcombe 구간 | 받는 쪽마다 하한 > -10%p면 채택, 상한 ≤ -10%p면 기각. 두 받는 쪽이 모두 채택이면 C2 채택, 하나라도 기각이면 C2 기각, 그 밖은 보류 |

2단계 진행 조건은 1단계 분석이 `results/stage1-gate.json`에 쓴다. 2단계는 `run.sh stage2`가 이 파일을 읽어 `run`일 때만 실행한다.

| 1단계 결과 | 2단계 |
|---|---|
| (가) C1 기각 | 하지 않고 변환 버그 이슈를 먼저 연다. 2단계는 그 수정이 머지된 뒤 수정 효과를 확인하는 새 실행으로만 정한다. |
| (나) C1 기각이 아니고 `mean_common_facts` ≥ 5, 공통 근거 사실 합계 ≥ 200, 평가할 수 있는 작업 ≥ 20 | 한다. 이 크기면 2단계에서 10%p 차이를 가를 수 있다. |
| 그 밖 | 하지 않고 이유를 보고서에 적는다. |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | 두 provider 중 하나가 실패한 작업은 두 provider에서 함께 뺀다. 2단계에서 답 JSON을 읽을 수 없는 세션은 틀린 답으로 센다. |
| 실패한 실행 | provider 종료 코드가 0이 아니거나 300초를 넘으면 한 번 다시 실행한다. 다시 실패하면 그 작업을 빼고 흐름 표에 센다. |
| 다중 비교 | C1은 네 지표의 교집합 판정이라 보정하지 않는다. C2도 받는 쪽 둘의 교집합 판정이다. |

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | C1과 C2가 모두 채택이면 현재 변환을 유지하고, 요구사항 표의 이 실험 행 검증 계획을 보고서 링크로 바꾼다. |
| 기각 | C1 기각이면 기각된 지표별 변환 버그 이슈를 연다(공통 이벤트가 버리는 값은 `ProviderEvent` 계약 변경 이슈). C2 기각이면 같은 이슈에 전환 품질 영향을 적는다. |
| 보류 | 작업을 늘려 새 실행 id로 다시 수집하고, 정밀도가 모자란 지표를 보고서에 적는다. |

## 탐색 분석

- 항목별(읽기, 셸, 테스트, 수정) 지표와 provider별 변환 손실 목록
- 근거 사실이 패킷에 든 비율의 `rrf-only`와 `oracle` 차이와 provider별 차이
- Codex 기록의 `Thinking` 항목처럼 도구가 아닌 이벤트가 기록 수와 패킷 예산에 미치는 영향
- 작업별 `Exit code` 문구, 명령 감싸기(`/bin/zsh -lc`) 같은 provider 출력 차이 목록

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
