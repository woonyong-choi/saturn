# 실제 기록의 맥락 보존: 실험 결과

## 요약

작은 패킷은 토큰을 줄였지만 필요한 근거도 잃었다. 수정한 수집기로 측정한 원문 조건은 두 provider 모두 질문을 모두 맞혔다. 추정 예산 16,000에서는 각각 36/36을 유지하면서 보고된 입력 토큰이 Claude 14.39%, Codex 10.17% 줄었다. 그러나 추정 예산 1,000과 4,000에서는 오답이 생겼다. 이 표본으로 일반적인 무손실 압축이나 높은 신뢰도의 종단 사용성을 입증할 수 없다.

구현에서는 오래된 대화가 선별 후보에서 누락되는 결함과 다른 실행의 도구 결과가 섞이는 결함을 수정했다. 실제 원자료, 모든 수신 응답, 사용량, 실패와 채점은 비공개 자료에 보존했다. 제거한 미구현 명령과 실제로 연결된 기능은 아래에서 구분한다.

## 방법

| 항목 | 값 |
|---|---|
| 설계 | [실험 설계](design.md), 수집 전 커밋 `184ba2e2` |
| 환경 | [env.json](env.json), 실제 호출 명령과 CLI 버전 포함 |
| 입력 | Saturn 폴더의 실제 Codex 대화 두 세션에서 여섯 구간, 실제 Saturn SQLite 실행 기록 세 개 |
| 독립성 | 출처 묶음 다섯 개. 같은 대화의 절단점과 질문은 독립 표본이 아니다. |
| 내용 | Rust 학습, Saturn 감사·실험 지시, 파일 이어쓰기, 중단 뒤 재개 기록 |
| 질문 | [questions.json](questions.json)의 문자열 정답·근거 위치. 과거 요청 실행이나 주관적 의도 판단을 요구하지 않았다. |
| 패킷 | 현재 `engine::handoff`의 실제 조립 함수를 호출. 질문·정답·oracle 순위는 주입하지 않았다. |
| 제약 경로 | 별도 저장 제약·수정 파일·끼워 넣기 목록은 이 재생에 주입하지 않았다. 그 경로의 종단 품질 근거로 쓰지 않았다. |
| Claude | 기록 인수와 후속 질문을 같은 프로세스에서 별도 턴으로 보냄. 도구 비활성화 |
| Codex | 기록과 후속 질문을 한 요청에 보냄. 읽기 전용 sandbox, 도구 사용 금지 지시, 반환 도구 이벤트 확인 |
| 공개 범위 | 집계·질문·재현 코드만 공개 경로. 개인 대화·모델 원응답은 `.local`에 보존 |

Claude가 반환한 모델 식별자는 `claude-haiku-4-5-20251001`이다. Codex는 `gpt-6-sol`을 요청했으며 반환 이벤트만으로 내부의 정확한 모델 revision을 확정하지 않았다. 두 provider의 점수와 토큰을 하나의 평균으로 합치지 않는다.

실제 DB는 읽기 전용으로 열었고 선택한 이벤트를 복사했다. 대화 원본의 SHA-256, 원본 행 위치, 가린 내용, 재생 행을 함께 보존했다. 비밀 문자열과 개인 경로를 가렸으므로 비공개 원본 파일 전체의 bytes와 재생 입력의 bytes는 다르다. 현재 연구가 전송한 입력과 실제로 받은 출력은 보존했지만 모델 내부의 비공개 추론에 접근했다고 주장하지 않는다.

## 설계와 다른 점

| 변경 | 시점 | 이유 | 결론에 미친 영향 |
|---|---|---|---|
| 수집 스크립트와 질문의 hash 봉인 | 첫 호출 전 | 설계만 먼저 커밋했고 구현 코드는 작업 트리에 있었다. 실제 실행 파일은 별도 보존했다. | 설계 커밋과 실행 코드 커밋이 같은 시점이라는 주장은 하지 않는다. |
| 원문 조건의 인수 지시문 통일 | 첫 수집 뒤 | 원문 조건이 패킷보다 짧은 지시를 받아 인수 동작 비교에 혼입이 있었다. | 첫 수집은 결함 있는 탐색 실행으로 보존하고 표의 주 결과에서 분리 |
| 실제 시각과 `phase=final_answer` 보존 | 첫 수집 뒤 | 대화 변환기가 시각을 영으로 두고 `channel=final`만 완료로 읽었다. | 수집기를 고쳐 전체 조건 재실행. 변환기 회귀 검사 추가 |
| 후속 답의 정답과 인수 포함 성공 분리 | 분석 중 | 올바른 후속 답도 Ready 위반이 있으면 사전 기준의 실패가 된다. | 사전 기준을 완화하지 않고 답만의 정답 수를 보조 지표로 추가 |
| 일반화 판정 | 변경 없음 | 목적 표본과 반복 구간은 독립적인 실제 개발 과제 표본이 아니다. | 모집단 신뢰구간·p값을 만들지 않는다. |

질문과 기대 답은 재측정에서도 바꾸지 않았다. 두 차례의 원응답을 모두 남겼으며, 첫 측정의 불리한 결과를 지우고 성공만 선택하지 않았다. 예비 합성 장문 시험은 질문을 탐색 중 바꿨으므로 확인 자료에서 제외했다. 그 초기 누락 실행의 전체 덤프는 보존되지 않았고 성공 재생 자료와 실제 두 결함의 수정 전 실패 로그는 남아 있다.

|---|---:|

| 수정한 수집기로 재측정 | 72 |

| 재측정에서 제외한 실행 | 0 |

각 Claude 조건 실행에는 인수와 질문이 각각 들어 있다. 표의 조건 실행 수를 독립 세션 수나 실제 개발 과제 수로 읽으면 안 된다. 실행 재시도는 하지 않았다.

### 재측정의 대응 비교

모든 수치는 [summary.json](results/summary.json)에서 계산했다. `답 정답`은 후속 JSON 답만 채점한 값이다. `인수 포함 정답`은 사전 기준대로 인수 위반도 실패로 센 값이며, `유효 실행`은 그 인수 조건을 통과한 실행 수다. 예산은 글자 수를 토큰으로 환산한 패킷 상한으로, provider가 실제 센 입력 토큰과 다르다.

| Provider | 예산 | 답 정답 | 인수 포함 정답 | 유효 실행 | 보고된 입력 토큰 합 | 원문 대비 감소 |
|---|---:|---:|---:|---:|---:|---:|
| claude | full | 36/36 | 32/36 | 8/9 | 565,969 | 0.00% |
| claude | 1000 | 24/36 | 24/36 | 9/9 | 216,920 | 61.67% |
| claude | 4000 | 32/36 | 32/36 | 9/9 | 321,009 | 43.28% |
| claude | 16000 | 36/36 | 36/36 | 9/9 | 484,552 | 14.39% |
| codex | full | 36/36 | 36/36 | 9/9 | 280,938 | 0.00% |
| codex | 1000 | 23/36 | 23/36 | 9/9 | 170,804 | 39.20% |
| codex | 4000 | 32/36 | 32/36 | 9/9 | 204,277 | 27.29% |
| codex | 16000 | 36/36 | 36/36 | 9/9 | 252,371 | 10.17% |

Claude의 원문 조건에서 `audit-26`은 과거의 읽기 전용 요청을 지금의 역할로 받아들여 Ready 대신 작업 제한 설명을 반환했다. 후속 질문은 모두 맞혔지만 인수 포함 기준에서는 실패다. 도구를 비활성화했으므로 이 시험으로 과거 작업의 실제 재실행 방지를 입증할 수 없다.

Claude 토큰 합은 각 턴 result의 input·cache creation·cache read 합이다. Codex input에는 cached input이 포함되므로 다시 더하지 않았다. 값에는 CLI 지시·도구 설명 등 고정 비용도 포함된다. 캐시와 준비 답 길이가 다르므로 이 감소율을 청구 비용 절감률로 바꾸지 않는다.

### 실패 사례

| 사례 | 관측 | 해석 |
|---|---|---|
| `learning-59`, 예산 4,000 | 두 provider 모두 예전 Greet 예제의 이름·구조체·인사말을 unknown으로 답했다. | 실제 과거 대화의 필요한 근거가 작은 패킷에서 빠짐 |
| `learning-30`, Claude, 예산 1,000 | 처음 예제의 `안녕하세요!` 대신 뒤 예제의 `안녕, {}!`을 답했다. | 다른 시점의 근거를 같은 질문에 잘못 연결함. 단순한 답 보류만의 문제가 아님 |
| `audit-26`, 예산 4,000 | 두 provider 모두 과거의 규칙 파일명을 회수하지 못했다. | 오래된 작업 지시를 후보에 넣어도 예산 안의 최종 보존은 보장되지 않는다. |
| `interruption`, Claude, 예산 1,000 | 읽었던 규칙의 백업 보관 기간을 unknown으로 답했다. | 최근 도구 결과도 축약 과정에서 필요한 세부사항을 잃을 수 있다. |
| 원문과 큰 예산의 성공 | 이 질문들은 원문과 큰 패킷에서 정답을 확인할 수 있었다. | 모든 미래 질문·정확한 시점·실제 작업 완료가 보장된다는 뜻은 아니다. |

답이 없는 항목의 unknown 대조군과 실제 값이 있는 항목의 unknown 실패는 구분했다. 질문별 답, 실패 종류와 원응답 hash는 집계 파일에 있다. 원응답을 다시 해석해 수치를 좋게 고치지 않았다.

## 구현 변경과 검증

| 변경 | 근거와 검증 |
|---|---|
| 오래된 일반 대화를 경쟁 후보에 포함 | 기존에는 최근 대화 범위 밖의 텍스트만 있는 턴이 아예 후보가 되지 않았음. 수정 전 실패와 수정 후 회귀 검사 보존 |
| 도구 결과의 식별 범위 수정 | `call_id`에 run·agent·subagent를 함께 사용. 서로 다른 실행과 하위 에이전트의 같은 호출 ID를 구분 |
| 선택된 기록이라는 지시 추가 | 빠진 세부사항을 만들어내지 말고 unknown으로 답하도록 패킷 지시를 보강. 실제 오귀속 사례가 있어 이것만으로 충분하다고 판단하지 않는다. |
| 미구현 학습·버전 전환 노출 제거 | training의 미완성 실행 코드, 대응 CLI·TUI 화면·프로토콜과 쓰이지 않는 번역 제거 |
| 전역 경고 억제 제거 | 실제로 쓰이지 않는 실행 경로는 제거하고 검사 전용 접근자는 테스트 빌드에 한정 |
| 프로토콜 갱신 | 삭제한 메시지 계약에 맞춰 버전을 올리고 스키마·TypeScript를 producer로 재생성 |

호환성 승인 처리, 파일 잠금 수명, 저장 스키마 이관과 기존 연구 증거는 사용 중인 계약 또는 보존 대상이므로 제거하지 않았다. 과거 테스트와 연구 문서는 삭제할 미사용 실행 코드로 취급하지 않았다. 기존 미커밋 문서와 실험 폴더도 유지했다.

| 검사 | 결과 |
|---|---|
| workspace 자동 검사 | 1,910 통과, 실패 없음. 별도 실행 조건 네 항목은 기본 실행에서 제외 |
| 하위 접속 부하 검사 | 제외되어 있던 세 부하 검사 모두 별도 통과. 가짜 provider와 실제 sleep 프로세스를 사용했으므로 외부 모델 처리량 근거는 아님 |
| 실제 기록 재생 | 생성한 27개 패킷을 다시 생성해 bytes 일치 확인 |
| 변환기 회귀 검사 | 세 검사 통과. 완료 표시의 두 형태와 원래 시각·미완료 상태 확인 |
| 번역 정리 후 TUI 검사 | 466 통과 |
| Rust 정적 검사·포맷 | Clippy 경고 없음, rustfmt 통과 |
| 프로토콜 생성물 | 재생성 전후 bytes 일치 |
| 실제 CLI | 빌드한 실행 파일의 도움말에서 제거된 명령이 노출되지 않는다. |

자동 검사 수는 사용성 평가 표본 수가 아니다. 재생은 engine의 실제 패킷 함수를 사용하지만, 이번 변경 후 정상 router 자격증명으로 TUI에서 양쪽 provider를 연속 전환한 종단 실행은 수행하지 않았다. 이번 결과를 그 경로의 완료 증거로 사용하지 않는다.

## 타당성 위협과 결론

| 종류 | 남은 한계 | 이번 판정 |
|---|---|---|
| 내적 | 샘플링·캐시·준비 답 길이와 provider 호출 방식이 다름 | provider별 대응 값만 제시. 청구 비용이나 provider 우열은 확정하지 않는다. |
| 구성 | 지식 회수 질문이고 실제 코딩 결과·사용자 만족도 검사가 아님 | 실사용 전체의 신뢰도를 입증했다고 판정하지 않는다. |
| 외적 | 사용자 한 명의 장문 대화와 짧은 기능 기록, 서로 겹치는 절단점 | 질문 수를 독립 표본 수로 삼는 신뢰구간 금지 |
| 누출 | 질문 작성자가 원문을 보았고 정답 일부는 흔한 식별자임 | 정확한 답만으로 해당 원문을 실제 이용했다는 인과를 확정하지 않는다. |
| 데이터 변환 | 대화는 텍스트 턴으로, DB는 이벤트로 재생했고 활성 제약 등 부가 상태는 제외 | 두 입력 유형을 실제 engine 저장 상태 전체와 동일시하지 않는다. |

현재 근거로는 작은 패킷의 무손실 사용성을 채택할 수 없다. 같은 자료에서 큰 예산이 더 많은 근거를 보존했지만 이를 운영 기본값 조정의 근거로 일반화하지 않는다. 확인한 결함 수정은 유지하고, 압축에서 빠진 원문을 후속 질문에 맞춰 다시 가져오는 경로와 독립적인 실제 개발 과제의 완료 검증을 다음 판단 조건으로 둔다. 그 경로는 이번 변경에 구현했다고 주장하지 않는다.
