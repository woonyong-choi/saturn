# 패킷 인수 순서: 추가 검증 설계

## 이유

[본 실험 설계](design.md)의 수집기는 패킷과 후속 질문을 한 요청에 합친다. 그러나 패킷에는 `Ready`로 답하고 다음 사용자 입력을 기다리라는 지시가 있고, 실제 engine은 패킷 인수와 사용자 입력을 나눠 보낸다. 본 실험의 정답률을 집계하기 전에 이 코드 차이를 발견했다. 원래 조건과 판정 기준은 바꾸지 않고 별도 자료로 추가 검증한다.

## 고정 조건

- 본 실험의 같은 48개 fixture, 패킷 출력, 후속 질문과 정답을 재사용한다. 새 정답이나 유리한 사례를 고르지 않는다.
- 본 실험 수집이 끝난 뒤 `sonnet` 모델과 같은 CLI 설정으로 새 session을 연다. 도구는 끈다.
- 패킷만 보내 첫 답을 저장하고, 같은 session에 후속 질문을 별도 턴으로 보낸다. 첫 답의 `Ready` 여부와 후속 답의 정확한 코드 포함 여부를 각각 센다.
- 모든 원응답, 실패, session ID를 별도로 보존한다. 세 번 연속 호출 실패 시 중단한다. 실패는 원인을 확인하기 전 재실행하지 않는다.
- 같은 48개 무축약 답과 대응 차이, 불일치쌍 수, 시드 20261007의 10,000회 bootstrap 95% 구간을 계산한다. 각 조건 비율에는 Wilson 95% 구간을 붙인다.
- 비용은 새 session의 마지막 누적 보고값을 쓴다. 패킷 인수 응답을 포함하고 Jev와 로컬 연산 비용은 포함하지 않는다.

## 해석 범위

이 추가 조건은 실제 패킷 인수 순서를 확인하는 탐색 분석이다. 본 실험의 H2 확인 분석을 바꿔 쓰지 않는다. 새 session의 선별 자료가 후속 답에 충분한지를 보며, 같은 session 안에서 Saturn 선별로 기록을 바꾸는 구현이나 실제 engine의 종단간 실행을 검증하지 않는다. 도구를 다시 읽어 작업을 복구하는 품질, 장기 작업 완료율, Codex 결과도 이 측정에 포함하지 않는다.
