# 같은 Claude session 축약 비교: 실험 결과

## 요약

프로세스를 유지한 추가 비교에서 기본 축약은 48/48 (100.0%), fast-jev는 12/48 (25.0%)였다. fast-jev에서 기본 축약을 뺀 대응 차이는 -75.0%p, bootstrap 95% 구간은 [-87.5, -62.5]%p다. 같은 자료를 새 session에 패킷으로 인수하고 별도 질문을 보낸 조건은 48/48 (100.0%)였다.

이 합성 코드 회수 과제에서는 같은 session의 기본 축약이 fast-jev 기본 삭제 규칙보다 우수하다. 새 session의 Saturn 패킷도 근거를 보존했다. 같은 session에는 provider 기본 축약, provider 전환에는 원본 기록 패킷이라는 두 경로를 유지한다. fast-jev의 기본 삭제 규칙을 제품 기본 경로로 추가하지 않는다. 이 결론은 실제 코드 수정 완료율이나 모든 긴 대화의 우열을 뜻하지 않는다.

## 방법

| 항목 | 값 |
|---|---|
| 본 설계 | [실험 설계](design.md), 수집 전 커밋 `116960c` |
| 패킷 인수 추가 설계 | [전달 순서](handoff-design.md), 실행 전 커밋 `7f8b01c` |
| 프로세스 유지 추가 설계 | [연결 유지](persistent-design.md), 실행 전 커밋 `dd24e0d` |
| 실행 환경 | [env.json](env.json), Claude Code 2.1.288 (Claude Code), 실제 모델 `claude-sonnet-5-5` |
| 원자료 | 같은 합성 시나리오 48개, 각 파일의 첫 줄에 독립 코드 |
| 채점 | 도구를 끈 첫 후속 답의 정확한 코드 포함 여부 |
| 불확실성 | 조건별 Wilson 95% 구간, 같은 시나리오 대응 bootstrap 10,000회 |

본 실험은 같은 사전 대화에서 두 축약 조건을 fork했고, 축약 뒤 CLI를 종료한 다음 같은 session ID로 질문했다. 추가 비교는 같은 사전 대화의 마지막 assistant 메시지까지 `--resume-session-at`으로 재개해 fork하고, 축약과 질문 사이에 같은 프로세스를 유지했다. 실제 Saturn의 stream-json 연결과 같은 입력 순서지만 Saturn engine 전체를 실행한 종단간 시험은 아니다.

Saturn 조건은 `packet` 예제의 `rrf-only`, 토큰 예산 2,048을 썼다. 기록은 실제 CLI 전문을 그대로 넣은 것이 아니라 같은 Read 파일 내용을 정규화한 도구 기록이었다. 패킷에 들어간 기록은 각 8개, 패킷 본문은 각 2,045토큰이었고 모든 질문의 정답 코드가 패킷에 있었다. 현재 engine에 아직 연결되지 않은 판단 기반 선별의 효과로 해석하지 않는다.

| 같은 프로세스의 축약·질문 조건을 추가했다. | 본 실험 집계 후 | CLI 재개 조건은 훅의 삭제 보고와 후속 입력 크기가 맞지 않았다. | 원래 H1을 덮어쓰지 않는다. 삭제를 실제로 적용한 연결의 결과를 별도로 해석한다. |

| 누적 비용의 차분 기준을 보정했다. | 분석 중 | 호출 비용을 단순 합하면 과거 비용이 중복된다. 메시지 재개 위치와 비용 누적 위치도 달랐다. | 본 실험은 사전 대화 누적, 프로세스 유지 조건은 source session의 마지막 누적을 뺐다. API 비용이 없는 fast-jev 축약 응답으로 후자를 대조했다. |
| 수집 후 외곽 셸이 오류로 종료했다. | 본 실험 수집 직후 | 실행 중 run.sh 수정과 읽기 전용 셸 변수 사용 때문에 후처리 명령이 실패했다. | 모델 응답과 수집 행은 모두 저장됐다. 별도 분석·검증 명령으로 완전성과 해시를 확인했다. 모델 호출 실패로 세지 않았다. |
| Python 호환성·재실행 보호와 분석기를 보완했다. | 분석 중 | Python 3.9에서 지원하지 않는 zip 인자를 제거하고, 기존 자료가 있으면 환경 파일도 덮어쓰지 않게 했다. | 정답과 판정 기준은 바뀌지 않았다. 수집기는 항상 stream-json을 쓰도록 사용하지 않는 분기도 제거했다. |

## 결과

### 흐름

| 단계 | 시나리오 | 조건 | 실패·제외 |
|---|---:|---|---|
| 본 실험 | 48/48 | 무축약, 기본 축약 뒤 재개, fast-jev 뒤 재개, 한 턴 패킷 | 모델 호출 실패 0, 제외 0 |
| 패킷 인수 순서 | 48/48 | Ready 응답 뒤 별도 질문 | 실패 0, 제외 0 |
| 프로세스 유지 | 48/48 | 기본 축약, fast-jev | 실패 0, 제외 0 |
| 연결 확인용 탐색 실행 | 1 | 기본 축약 | 위 분석에서 제외 |

각 행은 같은 시나리오를 재사용했다. 서로 독립된 새 표본으로 합치지 않았다. 그 밖의 사전 탐색은 본 설계에 적었으며 확인 분석에 넣지 않았다. 외곽 셸 종료 오류와 모델 호출 오류도 구별했다.

### 본 실험의 확인 분석

| 조건 | 정확한 코드 회수 | Wilson 95% 구간(%) |
|---|---:|---|
| 무축약 | 48/48 (100.0%) | [92.6, 100.0] |
| 기본 축약 후 CLI 재개 | 48/48 (100.0%) | [92.6, 100.0] |
| fast-jev 축약 후 CLI 재개 | 48/48 (100.0%) | [92.6, 100.0] |
| 패킷과 질문을 합친 새 session | 13/48 (27.1%) | [16.6, 41.0] |

| 가설 | 대응 차이 | 사전 지정 95% 구간(%p) | 불일치쌍 | 판정 |
|---|---:|---|---|---|
| H1: fast-jev − 기본 축약 | +0.0%p | [0.0, 0.0] | fast-jev만 성공 0, 기본만 성공 0 | 차이 기준을 충족하지 않아 채택하지 않았다. CLI 재개 조건에 한정한다. |
| H2: 한 턴 패킷 − 무축약 | -72.9%p | [-85.4, -60.4] | 패킷만 성공 0, 무축약만 성공 35 | 채택하지 않았다. 실제 인수 순서와 달라 제품 패킷의 품질 판정에 쓰지 않는다. |

한 턴 패킷의 오답 35개는 모두 `Ready` 한 단어였다. 정답이 없는 패킷이 아니라 상충한 전송 순서였다. 본 실험 fast-jev 훅은 48/48에 적용됐고, Read 호출 384개 중 288개를 제거했다고 보고했다. 그러나 후속 요청 입력은 평균 18,974.2토큰으로, 무축약 18,778.4토큰보다 줄지 않았다. 삭제 로그만으로 후속 모델의 입력 축소를 입증할 수 없었다.

### 탐색 분석: 실제 패킷 인수 순서

첫 응답은 48/48에서 `Ready`였고, 별도 질문의 코드 회수는 48/48 (100.0%), Wilson 구간은 [92.6, 100.0]%였다. 무축약과의 차이는 +0.0%p, 대응 구간은 [0.0, 0.0]%p였다. 불일치쌍은 양쪽 모두 없었다.

이는 이 자료에서 패킷의 내용이 충분했다는 근거다. 모든 파일의 코드가 첫 줄에 있고 예제는 각 결과의 앞부분을 남겨 모든 코드를 보존했으므로, 중요한 내용이 중간에 있거나 예산을 넘는 실제 대화의 선별 성능까지 입증하지 않는다.

## 논의

### 해석

- 같은 session에서 그대로 이어 갈 때는 기본 축약을 유지한다. 이번 조건에서 fast-jev의 기본 삭제는 이후 질문에 필요한 예전 코드를 잃었다.
- provider 전환이나 새 session에는 Saturn 원본 기록 패킷을 유지한다. 단, 패킷 인수 턴이 끝난 뒤 사용자 입력을 보내는 기존 계약을 지켜야 한다.
- Saturn 패킷의 선별을 같은 session 내부에 이식한 구현을 시험한 것은 아니다. 따라서 “Saturn의 세션 내부 축약이 더 우수하다”는 결론은 내리지 않는다.
- 기존 `ProviderClient::compact`, `open_session`, 기록 저장과 패킷 구성을 재사용한다. 실험 결과만으로 새 훅이나 별도 관리자를 제품 경로에 추가하지 않는다.

### 타당성 위협과 한계

| 종류 | 위협 | 이 실험에서 |
|---|---|---|
| 내적 | 호출 순서와 캐시가 비용·지연에 영향을 준다. | 기본 축약과 fast-jev 순서만 교대했다. 무축약·패킷·추가 실험의 실행 시점은 같지 않았다. |
| 내적 | 축약 로그와 다음 모델 입력이 다를 수 있다. | CLI 재개와 프로세스 유지 결과를 분리했고 실제 입력 토큰과 원본 session 기록을 보존했다. |
| 구성 | 정답이 파일 첫 줄에 있어 앞부분을 남기는 패킷에 유리하다. | 모든 패킷에 정답이 있었다. 일반 선별 능력 검증으로 쓰지 않는다. |
| 구성 | 도구 재열람을 막은 회수 과제다. | 근거 자체의 보존만 측정했다. 재열람을 허용한 실제 코딩 완료율은 측정하지 않았다. |
| 외적 | 짧은 합성 Read 대화와 단일 모델·버전이다. | 자동 축약 임계점, 긴 혼합 도구 대화, Codex는 측정하지 않았다. |
| 외적 | 예제를 CLI에 직접 전달했다. | engine의 기록 접수·대기열·provider 전환 전체를 검증하지 않았다. |
| 통계 | 표본이 작고 같은 템플릿을 쓴다. | 천장 효과로 대응 bootstrap 구간이 0에 모일 수 있다. 이는 모집단의 차이가 정확히 0이라는 증거가 아니다. 추가 조건은 모두 탐색 분석이다. |
