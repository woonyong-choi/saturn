# 실제 선주입 선별: 개발 진단 결과

## 요약

12계열 중 10계열에서 source 전문을 확보했다. Jev와 코드 순위의 첫 패킷은 7/12계열에서 달라 사전 H1 개발 기준을 충족했지만, 유효한 10계열은 두 조건 모두 정답이었다. Jev만 정답인 계열은 없고 전체 router·provider 토큰은 Jev가 코드 순위보다 34,323개 많았다. 선별 효과의 독립 확인이나 제품 자동 적용 근거는 아니다.

## 방법

| 항목 | 값 |
|---|---|
| 설계 | [실험 설계](design.md), 수집 전 봉인 `818c9e62`·경로 수정 `26be7a2f`·`6b4ccf73` |
| 실행 ID | `20261006T210043Z-6b4ccf7` |
| 환경 | [env.json](env.json), 실제 engine 바이너리 SHA-256 `b1de516ad87c4c43fa4f189102bbcfd6868cfbe7421844bf0d531811055dca86` |
| 표본 | 네 종류 x 씨앗 세 개, 예정 12계열·36 target, 실제 10계열·30 target |

각 계열에서 Codex가 파일을 개별 도구 호출로 읽게 하고 DB를 세 조건으로 복제했다. 파일을 target 작업 폴더에서 제거해 새 Claude 세션이 기록·조회로만 답하게 했다. 정답은 생성 때 확정한 정수와 마지막 답의 정확한 문자열 일치로 판정했다. 세 조건은 같은 기록·질문·조회 권한을 받았다.

## 설계와 다른 점

| 변경 | 시점 | 이유 | 결론에 미친 영향 |
|---|---|---|
| 첫 실행을 provider 호출 전에 종료하고 짧은 Unix socket 경로로 연결 | 첫 source 전에 | 긴 작업 트리 경로가 OS 소켓 제한을 넘음 | 실패 실행을 별도로 보존했다. 새 실행 ID의 source부터 재수집했다 |
| `related_applied`를 질문 존재가 아닌 패킷 항목의 실제 selector로 집계 | 수집 중, 결과 분석 전 | 질문을 받았어도 적용되지 않은 경우를 구분 | 원응답·가설은 변경하지 않았다. H1·H2에는 영향 없음 |
| 종류별 패킷 차이와 조건별 평균·중앙 시간을 집계 | 수집 뒤, 보고 전 | 설계의 탐색 변수 표시 | 확인 판정에는 사용하지 않았다 |

## 결과

### 흐름

| 단계 | 수 |
|---|---:|
| 예정 source 계열 | 12 |
| source 전문 미기록 | 2 (`exact-2`, `synonym-1`) |
| 유효 source | 10 |
| 예정 target | 36 |
| 실제 target | 30 |
| 미실행 target | 6 |
| Jev 선별 실제 적용 | 10/10 유효 Jev target |

source 전문 실패는 정답 비교에서 임의로 지우지 않고 H1의 12계열 분모에 남겼다. 두 계열의 target은 보내지 않았다. 원자료 해시와 집계 두 번의 바이트 일치 검사는 통과했다.

### 확인 분석

| 가설 | 지표 | 값 | 사전 기준 | 판정 |
|---|---|---|---|---|
| H1 | rank와 Jev의 첫 본문 SHA-256 차이 | 7/12계열 | 3계열 이상 | 개발 기준 충족 |
| H2 | Jev만 정답 대 rank만 정답 | 0 대 0, 양쪽 10/10 | Jev만 정답이 더 많고 전체 정답도 많음 | 신호 없음 |

종류별 본문 차이는 `exact` 2/3, `stale` 2/3, `synonym` 2/3, `middle` 1/3이다. 전문이 없는 계열도 각 3계열 분모에 남겼다.

### 탐색 분석

| 조건 | 정답 | 추가 근거 조회 | provider 토큰 합 | router 토큰 합 | 평균·중앙 완료 시간 |
|---|---:|---:|---:|---:|---:|
| off | 10/12 | 5 | 1,003,077 | 4,859 | 6.976·6.030초 |
| rank | 10/12 | 0 | 873,563 | 4,859 | 6.104·5.982초 |
| jev | 10/12 | 0 | 872,445 | 40,300 | 6.646·6.231초 |

토큰 합은 provider가 보고한 입력·캐시 생성·캐시 읽기·출력과 router의 입력·출력을 같은 숫자 단위로 더한 값이다. 모델별 가격과 실제 청구액으로 바꾼 비용이 아니다. `jev - rank` provider 토큰은 1,118개 적었지만 router 토큰은 35,441개 많아 단순 합계가 34,323개 늘었다. 한 번씩 실행한 완료 시간은 차이의 신뢰구간이나 속도 우열을 제공하지 않는다.

## 논의

### 해석

Jev가 코드 순위와 다른 원문을 보낸다는 작동 경로는 확인했다. 이 계열에서는 코드 순위도 후속 답을 전부 맞히고 추가 조회도 하지 않아 Jev의 품질·탐색 이득은 관측되지 않았다. 다른 패킷을 만든 사실만으로 더 나은 선별이라고 볼 수 없다. 기본 `off`를 유지한다.

### 타당성 위협

| 종류 | 위협 | 이 실험에서 |
|---|---|---|
| 내적 | 조건당 한 번의 provider 출력 변동 | 같은 source를 복제하고 조건 순서를 섞었지만 반복하지 않았다 |
| 구성 | 짧은 숫자 질문이 작업 완료를 대표하지 않음 | 추가 조회와 답만 개발 진단으로 측정했다 |
| 외적 | 합성 파일, Codex→Claude 한 방향 | 실제 사용자 대화와 코드 변경으로 일반화하지 않는다 |

### 한계

- source 미기록 두 계열 때문에 `middle` 등 어려운 사례의 균형이 흐트러질 수 있다.
- 동일한 파일을 읽는 source 지시 자체가 Codex 행동에 의존한다.
- 가격 가중 비용, 실제 다중 턴 코드 작업, 재작업, provider가 받은 본문은 확인하지 않았다.
