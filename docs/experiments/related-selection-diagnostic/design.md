# 실제 선주입 선별: 개발 진단 설계

| 항목 | 값 |
|---|---|
| 이슈 | [#541](https://github.com/woonyong-choi/saturn/issues/541) |
| 관련 설계 | [맥락 고르기](../../design/context-selection.md) |
| 사전 데이터 | #541 B1 결과와 #600의 Atlas 단일 계열 기능 진단을 열람했다. Atlas 계열과 같은 숫자·프로젝트는 표본에서 제외한다. |

## 질문

실제 Saturn 기록의 도구 결과를 새 Claude 세션에 선주입할 때 `related@2.0`의 후보별 Jev 판단이 코드 순위와 다른 본문을 보내는지 확인한다. 다른 본문이 후속 답과 조회 수에 주는 신호를 개발 자료로 측정한다.

## 가설

| 가설 | 예측 | 적용 범위 |
|---|---|---|
| H1 | Jev와 코드 순위의 첫 패킷 본문이 12계열 중 3계열 이상에서 다르다. | 합성 도구 결과를 실제 engine에 기록한 12계열 |
| H2 | Jev의 정답 수가 코드 순위보다 많고, Jev만 정답인 계열이 코드 순위만 정답인 계열보다 많다. | H1을 충족한 계열. 확인 평가의 채택 근거는 아니다. |

## 설계

| 항목 | 값 |
|---|---|
| 조건 | `off`, `rank`, `jev` |
| 배정 | 계열마다 세 조건의 순서를 시드 541202로 섞는다. 세 조건은 같은 source DB 복제본과 같은 질문을 쓴다. |
| 눈가림 | 정답 숫자와 근거 위치는 runner의 채점에만 두며 target 질문과 Jev 요청에 넣지 않는다. source 도구 결과에는 답이 들어간다. |
| 환경 | macOS, 현재 브랜치의 `engine_client.py`, #600 엔진 바이너리, Codex gpt-5.6-luna source, Claude Sonnet target, 실제 router. 바이너리 해시와 버전은 수집 파일에 남긴다. |

계열은 `exact`, `stale`, `synonym`, `middle` 네 종류에 씨앗 세 개씩 둔다. source는 Codex가 각 파일을 별도 명령으로 읽게 하며 도구 결과 전문이 기록됐는지 검사한다. `stale`은 오래된 값과 정정을 함께 두고, `middle`은 필요한 문장을 긴 결과의 중앙에 둔다. target은 정수 하나를 답하도록 하고, 빠진 근거는 같은 `saturn evidence` 조회 권한으로 복구할 수 있다. target 세션은 조건마다 새로 만든다.

## 변수

| 변수 | 종류 | 정의 | 단위 |
|---|---|---|---|
| `packet_diff` | 측정 | `rank`와 `jev`의 첫 패킷 본문 SHA-256이 다른지 | 참·거짓 |
| `correct` | 측정 | target의 마지막 본문이 기대 정수와 정확히 같은지 | 참·거짓 |
| `lookups` | 측정 | target의 성공·실패 근거 조회 건수 | 건 |
| `tokens` | 측정 | target provider와 router의 입력·출력·캐시 토큰을 출처별로 보존 | 토큰 |
| `latency_s` | 측정 | target 입력부터 완료까지의 벽시계 시간 | 초 |

## 표본

| 항목 | 값 |
|---|---|
| 출처 | 생성한 네 종류의 파일을 Codex가 실제 읽어 만든 Saturn 기록 |
| 크기 | 12계열, 각 조건 한 번. 기존 Atlas 계열은 제외 |
| 크기 근거 | 기능 진단 예산. 한쪽만 3건이면 차이를 볼 수 있으나 품질 유지나 비용 절감의 신뢰구간을 좁힐 검정력은 없다. |
| 중단 규칙 | 인증 거절, source 전문 미기록 연속 3회, 또는 target 전송이 확정되지 않은 경우 중단한다. 각 실패는 원자료에 남긴다. |
| 반복과 예열 | 조건당 한 번, 예열 없음. 독립 확인 평가가 아니다. |

## 분석

| 가설 | 지표 | 방법 | 채택 기준 |
|---|---|---|---|
| H1 | 본문이 다른 대응 계열 수 | 12계열을 분모로 정확 계수 | 3계열 이상이면 다음 확인 평가 설계로 진행 |
| H2 | Jev만 정답과 rank만 정답 | 계열별 대응표 | Jev만 정답이 더 많아도 개발 신호로만 기록 |

| 항목 | 규칙 |
|---|---|
| 제외 기준 | source에 목표 도구 결과 전문이 없는 계열은 target을 실행하지 않고 12계열 분모에 실패로 남긴다. |
| 실패한 실행 | 응답 없음·형식 오류·조회 실패는 오답으로 남긴다. 비용·시간 미상은 `null`로 둔다. |
| 다중 비교 | 두 가설은 순서대로 본다. H1 실패 시 H2는 탐색이다. |

## 판정

| 결과 | 설계에 반영 |
|---|---|
| 채택 | 이 개발 진단에서 제품 자동 적용은 채택하지 않는다. H1 통과 시 #541의 독립 다중 턴 확인 평가를 설계한다. |
| 기각 | H1 실패 시 현재 질문·예산의 확인 평가를 중단하고 패킷 차이가 없는 원인을 기록한다. |
| 보류 | source·target 실패가 많거나 품질 신호가 없으면 기본 `off`를 유지한다. |

## 탐색 분석

- 계열별 적용·대체, 근거 조회, 토큰, 시간과 조건 순서의 영향을 보고한다.

## 타당성 위협

| 종류 | 위협 | 대응 |
|---|---|---|
| 내적 | provider 출력과 캐시가 실행마다 달라진다. | 같은 source를 복제하고 순서를 섞되 한 번 실행의 한계를 명시한다. |
| 구성 | 숫자 답이 코드 수정 완료를 대표하지 않는다. | 도구 결과 복구의 개발 신호로만 해석한다. |
| 외적 | 합성 기록 네 종류가 실사용 분포를 대표하지 않는다. | 독립 실과제 확인 평가 전에 제품 기본값을 바꾸지 않는다. |
