## 질문

사용 가능한 provider 안에서 `model.mode = auto`로 Jev가 새 작업의 모델을 고르게 두면, 같은 과제를 사용자가 고른 기본 모델로 고정해 보낸 경우보다 품질을 유지하면서 전체 비용과 완료 시간을 줄이는가. 줄이지 못하면 자동 적용은 켜지 않는다. 이 실험은 효과를 만드는 것이 아니라 지금 배포된 경로(후보 집합, 확신도 0.6 이상일 때만 적용, 아니면 기본 모델 대체)가 실제로 어떻게 동작하는지를 잰다.

## 가설

| 가설 | 예측 | 비교 |
|---|---|---|
| H1 품질 유지 | 같은 과제에서 오토 팔이 실패하고 대조 팔은 성공한 쌍이 0개이고, 그 쌍 비율의 단측 95% Clopper-Pearson 상한이 10%p 이하다. | 오토 대 기본 모델 고정(층마다) |
| H2 비용 절감 | 과제별 전체 비용의 대응 상대 차이 평균의 95% 구간 상한이 -δ 이하다(δ는 아래 확정 절차). | 같음 |
| H3 시간 단축 | 과제별 완료 시간의 대응 차이 평균의 95% 구간 상한이 0 이하이고 오토 팔의 p95 지연이 대조 팔 이하다. | 같음 |
| H4 안전 | 안전 위반 0건(키 문자열 검출, 연습 폴더 밖 변경, 허가 요청 우회). | 모든 팔 |

설명 변수는 팔이고 결과는 성공, 비용, 시간이다. Jev 확신도는 어디에도 작업 성공 확률로 쓰지 않는다. 확신도는 적용 여부(0.6 이상)를 가르는 경로의 일부로만 기록한다.

## 설계

### 후보와 팔

후보는 [모델 평가 근거 목록](../../design/model-evidence.md) 버전 `2026-10-06.1`에 있고 provider가 지금 알린 모델의 교집합이다. 실험 옵션 `model.candidates`([#573](https://github.com/woonyong-choi/saturn/pull/573))로 router에 물을 후보를 이 집합으로 고정한다.

| 층 | 후보 | 사용할 수 있는 provider |
|---|---|---|
| claude | `claude/haiku`, `claude/sonnet`, `claude/opus` | Claude만 설치한 사용자 |
| codex | `codex/gpt-6-luna`, `codex/gpt-6-astra` | Codex만 설치한 사용자 |
| both | 위 다섯 | 둘 다 설치한 사용자 |

제외한 모델: `claude-fable-5-1`(Saturn의 Claude 모델 목록에 별칭이 없다), 목록의 `gpt-6.1-sol`(provider 목록의 `gpt-6-sol`과 같은 모델인지 확인할 수 없고 `codex exec -m gpt-6.1-sol`은 ChatGPT 계정에서 거절됐다, [보고서](report.md)), provider 목록에는 있으나 근거 목록에 없는 `gpt-6-sol`과 `gpt-5.6-*`. 근거 목록의 어떤 모델도 품질이 확정되지 않았다(점수 없음, Codex는 revision 불명). 그래서 모든 후보는 미검증이다.

| 팔 | 방식 | 모델 | 역할 |
|---|---|---|---|
| `c-haiku`, `c-sonnet`, `c-opus` | 매뉴얼, `model.default` 고정 | 해당 모델 | claude 층 고정 대조군. `c-sonnet`이 기본 대조군 |
| `c-auto` | 오토, 대체 기본 모델 `claude/sonnet` | Jev 선택 또는 대체 | claude 층 처치 |
| `x-luna`, `x-astra` | 매뉴얼 고정 | 해당 모델 | codex 층 고정 대조군. `x-astra`가 기본 대조군 |
| `x-auto` | 오토, 대체 기본 모델 `codex/gpt-6-astra` | Jev 선택 또는 대체 | codex 층 처치 |
| `b-auto` | 오토, 후보 다섯, 대체 `claude/sonnet` | Jev 선택 또는 대체 | both 층 처치. 대조는 `c-sonnet`(기본)과 `x-luna` |

기본 대조군은 사용자가 이미 정해 둔 기본 모델에 해당한다. 대체 기본 모델과 같다. 오토 팔이 Jev 선택을 쓰지 못하면(대체) 기본 대조군과 같은 모델로 실행되므로 그 쌍의 차이는 router 질문 하나 분량의 오버헤드와 실행 변동뿐이다. 이 경우를 숨기지 않고 적용률과 대체 사유를 분모와 함께 보고한다.

세 층에서 같은 과제를 모두 실행하므로 `c-sonnet`과 `x-luna`는 both 층 대조에 다시 쓴다(추가 호출 없음). 추론 깊이는 바꾸지 않고 provider 기본값을 따른다. 추론 깊이 조합은 아직 구현되지 않았으므로(#531) 이 실험에서는 관측 대상이 아니며 미측정이다.

### 실행 경로

실제 `saturn` 전체 화면을 `tmux -L 542`의 전용 세션에서 띄운다. 운영 `~/.saturn`, `~/.claude`, `~/.codex` 설정은 쓰지 않고 실행마다 `.runtime/h/NNN`에 전용 `SATURN_HOME`, `.runtime/p/NNN`에 연습 저장소를 만든다. 저장소는 시작 상태를 한 커밋으로 둔다. 로그인된 `claude`, `codex`를 그대로 쓴다. router 키는 수집기가 키체인 항목 `saturn-verify-router`에서 읽어 자식 환경에만 넣고 출력·파일·인자에 쓰지 않는다.

- 고정 팔은 `-c model.default=<모델> -c model.mode=manual`로 띄운다. 입력은 바로 간다.
- 오토 팔은 `-c model.mode=auto`만 주고 `model.default`를 비워 둔다. 그러면 TUI가 처음 고르기 창을 열고 engine이 모든 provider의 모델 목록을 받아 둔다. 창에서 대체 기본 모델 줄로 내려가 `Enter`로 저장한 뒤 입력한다. 실제 사용자의 첫 실행과 같은 경로다. `--plain` 출력으로 입력을 파이프하면 이 창이 없어 첫 입력의 후보 목록이 비고 모든 오토 입력이 `no-candidates`로 기본 모델에 간다(예비 실행에서 확인했고 [보고서](report.md)에 적는다). 그래서 plain 출력은 쓰지 않는다.
- 모든 팔: `-c permission.mode=edit -c permission.shell="allow"`, `-c model.candidates=<층의 후보>`. 허가 요청 창이 뜨면 답하지 않고 그 시도를 실패로 기록한다.
- 입력은 과제 지시문 한 줄을 그대로 보낸다. 입력당 새 채팅 하나, 새 `SATURN_HOME`이라 이어 가기와 끼워 넣기는 없다.
- 개발 구간만 `router.shadow.model_selection = true`를 사용자 설정에 둔다(후보별 충분성 확률, 비용 판정에는 쓰지 않는다). 확인 구간은 끈다. 배포 경로의 비용을 그대로 재기 위해서다.

### 과제

합성 파이썬 과제다. 에이전트가 고친 저장소에 숨은 시험 입력을 흘려 기준 해법 저장소와 결과(또는 예외 종류)를 비교한다. 시험 입력과 기준 해법은 에이전트의 작업 폴더에 들어가지 않는다. `scripts/tasks.py`의 자체 시험은 시작 저장소가 실패하고 기준 해법이 통과하는지를 모든 과제에 대해 매번 확인한다.

| 구간 | 계열(난이도) | 과제 수 |
|---|---|---|
| 개발 | retry(중), paginate(중), ttl(상) | 3계열 x 4 = 12 |
| 확인 | duration(상), ranges(중), cart(상), config(하), csv(중), semver(상) | 6계열 x 6 = 36 |

계열은 한 구간에만 속한다. 계열마다 변형(매개변수: 규칙의 수치, 지시문의 규칙 선택)이 다르고, 변형마다 언어(한국어, 혼합어)와 맥락 길이(짧음, 긴 저장소)를 번갈아 배정한다. 긴 저장소는 관계없는 모듈 열 개와 메모 문서를 더한 것이다. 지시문은 한국어 문장 또는 한국어에 영어 용어를 섞은 문장이고 규칙을 모두 적는다. 검증은 `fixture_hash`로 시작 저장소와 지시문을 묶는다.

### 표본, 순서, 호출 상한

| 항목 | 값 |
|---|---|
| 과제 x 팔 | 개발 12 x 8 = 96 시도, 확인 36 x 8 = 288 시도 |
| 실행 순서 | 시도 전체를 시드 542100(개발), 542200(확인)로 섞은 한 줄. 세 작업자가 앞에서부터 가져간다. 한 과제의 팔이 같은 시간대에 퍼진다. |
| 표본 근거 | 확인 36쌍은 예산 상한이다. 쌍 손실 0건일 때 단측 95% 상한이 8.0%이고 H1의 10%p 이하를 만족할 수 있는 최소 규모다. 개발 12과제의 불일치와 분산은 과제의 판별력과 절감 기준 확정에만 쓰고 확인 표본 수는 바꾸지 않는다. |
| 판별력 규칙 | 확인에서 같은 층의 고정 대조군들이 모두 같은 과제에서 항상 성공하면(불일치 0) 품질 비교는 모델 선택의 이득도 손실도 보지 못하므로 H1은 채택하지 않고 보류로 적는다. |
| 호출 상한 | 개발: provider 요청 110, router 호출 110. 확인: provider 요청 300, router 호출 300. 예약 계획은 96과 288. 상한에 닿으면 멈춘다. |
| Claude·Codex 모델 | 후보가 곧 처치라 설계가 요구하는 모델(Claude opus·sonnet, Codex astra)을 쓴다. 공통 규칙의 저렴한 모델 기본에 대한 예외다. 과제가 작아 시도당 토큰은 수만이다. |
| 중단 규칙 | 호출 상한, 인증 거절, 연속 여섯 시도 실패. 개별 실패와 시간 초과는 보존하고 다음 시도를 진행한다. 자동 재시도 없음. |

개발 구간 수집 뒤 확인 구간 수집 전에 아래 값만 이 문서의 확정 절에 고정하고 따로 커밋한다.

| 값 | 확정 규칙 |
|---|---|
| δ(비용 절감 기준) | 10%. 개발 구간에서 router 호출 오버헤드(오토 팔 router 토큰 중 고정 팔에 없는 부분)가 provider 비용의 5%를 넘으면 그 오버헤드 비율의 두 배로 올린다. 낮추지 않는다. |
| 과제 제외 | 개발에서 모든 고정 팔이 실패하는 과제는 기준 해법과 지시문 불일치를 의심해 계열의 지시문 문구를 고칠 수 있다(확인 계열은 건드리지 않는다). 기준 해법과 시험은 바꾸지 않는다. |

### 측정

| 변수 | 정의 |
|---|---|
| success | 숨은 시험 호출 전부가 기준 해법과 일치. 시도 실패와 시간 초과는 실패로 분모에 둔다. 통과한 호출 수는 별도 기록한다. |
| 비용 | 모든 provider 사용량 행(재작업, 하위 에이전트 포함)을 목록 가격(근거 목록 버전 `2026-10-06.1`, 백만 토큰당)으로 환산한 상한. `(입력 + 캐시 읽기 + 캐시 쓰기) x 입력 단가 + 출력 x 출력 단가`. 캐시 할인을 적용하지 않는 상한이고 구독 한도와 실제 청구액은 아니다. Codex의 `ThreadCumulative` 행은 session별 마지막 값, Claude의 `MainTurn` 행은 합이다. |
| router 오버헤드 | router 입력·출력 토큰(판단 기록). Jev 단가는 미상이라 달러로 바꾸지 않고 토큰으로 보고하고 provider 토큰 대비 비율을 함께 낸다. |
| 완료 시간 | 입력 접수(`inputs.accepted_at`)부터 마지막 실행 끝(`runs.ended_at`)까지. router 판단, 모델 대체, 새 session 열기를 포함한다. 작업자 세 개가 같이 돌므로 절대값은 부하에 따라 달라지고 팔 사이 비교만 의미가 있다. |
| 적용률, 대체율 | 오토 입력 중 `model_selections.source = router`로 적용된 수, 아닌 입력의 사유(`fallback`, `invalid`, `unsupported`, `router-failed`, `no-candidates`). `target_model` 확률 최댓값 분포. |
| 누락·재조회 | 사용량 행이 없는 실행 수, 값이 비어 있는 행 수, `evidence_lookups` 수, 입력당 실행 수(재작업). |
| 안전 | 기록 저장소·화면·수집 원자료의 router 키 문자열 수(셸 `grep -c`), 연습 폴더 밖 변경, 허가 요청 창으로 멈춘 시도 수. |

층, provider, 언어, 맥락 길이, 난이도별 표는 분모와 함께 따로 낸다(검정 없이 개수만).

## 분석

| 분석 | 방법 |
|---|---|
| H1 | 층마다 오토 팔과 기본 대조 팔의 쌍. 손실 쌍(오토만 실패)과 이득 쌍(대조만 실패) 개수, 손실 비율의 Clopper-Pearson 단측 95% 상한, 정확 McNemar 단측 p. |
| H2, H3 | 과제별 대응 차이. 비용은 `cost_auto / cost_control - 1`, 시간은 초 차이. 과제를 단위로 부트스트랩 10,000회(시드 542, 백분위 95% 양측). p95는 선형 보간 백분위. 비용 계산에서 사용량이 비어 있는 시도는 그 쌍을 비용 분석에서 빼고 개수를 보고한다. |
| H4 | 합계. |
| 보조(탐색) | 오토 팔이 대체한 입력을 `target_model` 확률 최댓값 모델로 가정한 반사실 재현. 같은 과제의 그 모델 고정 팔 시도의 결과를 쓴다(한 번의 표본이라 잡음이 있고 새 session 열기와 캐시 손실은 빠진다). 확신도 문턱 0.6을 없앴을 때의 이득과 손실이 어떤지만 본다. 판정에 쓰지 않는다. |
| 보조(탐색, 개발만) | 그림자의 후보별 충분성 확률과 고정 팔의 실제 성공의 관계. 판정에 쓰지 않는다. |

분석은 같은 원자료에서 두 번 실행해 출력 바이트가 같아야 한다. 원자료는 시도마다 gzip JSON 하나(화면 마지막 상태, 기록 저장소 표 덤프, 연습 저장소 diff, 채점 결과, 실제 설정 인자)이고 해시 목록을 함께 커밋한다. 정답과 미래 기록은 router 입력에 없다(입력은 과제 지시문 한 줄뿐이다). 확인 구간에서 설계나 기준을 바꾸면 그 수집은 탐색으로만 보고한다.

## 판정

| 결과 | 조건 |
|---|---|
| 채택(층마다) | H1~H4를 모두 만족하고 판별력 규칙에 걸리지 않는다. 채택해도 기본 자동 적용은 별도 결정이다. |
| 기각(층마다) | 손실 쌍이 이득 쌍보다 많고 정확 McNemar 단측 p < 0.05이거나, 비용 또는 시간 증가의 95% 구간 하한이 0 초과다. |
| 보류 | 그 밖. 신뢰구간이 넓거나 품질·효율을 함께 만족하지 못하면 자동 적용을 켜지 않고 부족한 증거와 다음 실험을 이슈에 남긴다. |

품질 허용폭은 0이다(손실 쌍 0건이 H1의 첫 조건). 임의로 완화하지 않는다.
