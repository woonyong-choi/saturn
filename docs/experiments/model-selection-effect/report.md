## 결론

세 층(claude, codex, both) 모두 판정은 보류다. 자동 적용은 켜지 않는다. 확인 구간 오토 입력 108개 중 Jev가 `target_model`을 확신도 0.6 이상으로 고른 입력은 0개였고(최대 0.32) 모든 입력이 대체 기본 모델로 갔다. 그래서 오토 팔은 기본 대조군과 같은 모델로 실행됐고, 이 실험이 잰 것은 모델 선택의 효과가 아니라 router 질문 하나의 오버헤드와 같은 설정의 실행 변동이다. 모델 선택이 품질을 유지하며 비용을 줄이는지는 이 실험으로 알 수 없다.

같은 모델을 쓴 쌍도 성공이 어긋났다. `c-auto`와 `c-sonnet`은 36과제 모두 같은 모델(`claude-sonnet-5-5`)로 실행됐는데 오토만 성공한 과제가 3개 있었다. 한 번씩만 실행하는 설계에서 품질 허용폭 0(손실 쌍 0건)은 모델이 같아도 실행 변동만으로 깨질 수 있고, 반대로 손실이 0이어도 변동이 가려져 있다.

## 가설 판정

확인 구간, 층마다 기본 대조군과 비교한 값이다. 구간은 설계대로 과제 단위 부트스트랩(비용, 시간)과 Clopper-Pearson 단측(손실 비율)이다.

| 층 | 오토 대 기본 대조 | 성공(오토/대조) | 손실·이득 쌍 | 손실 비율 상한 | 비용 대응 차이 | 시간 대응 차이 | p95(오토/대조) | H1 | H2 | H3 | H4 | 판정 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|
| claude | `c-auto` 대 `c-sonnet` | 28/36, 25/36 | 0, 3 | 8.0% | -1.5% [-7.4, +4.8] | -1.8초 [-7.5, +3.2] | 35.4, 66.2초 | 충족 | 미충족 | 미충족 | 충족 | 보류 |
| codex | `x-auto` 대 `x-astra` | 24/36, 25/36 | 2, 1 | 16.5% | +0.7% [-4.0, +5.5] | +6.2초 [-8.0, +20.5] | 158.2, 142.8초 | 미충족 | 미충족 | 미충족 | 충족 | 보류 |
| both | `b-auto` 대 `c-sonnet` | 29/36, 25/36 | 1, 5 | 12.5% | +0.6% [-6.0, +7.6] | +0.2초 [-5.7, +5.8] | 39.4, 66.2초 | 미충족 | 미충족 | 미충족 | 충족 | 보류 |

- H1, H2, H3 판정 규칙은 설계 그대로이고 개발·확인 모두에서 같은 보류다. H1이 충족인 claude 층도 비용·시간이 미충족이라 채택이 아니다.
- 비용은 목록 가격 환산 상한(캐시 할인 없음)이고 실제 청구액이나 구독 한도가 아니다. router 비용은 Jev 단가가 미상이라 달러로 바꾸지 않았다. router 토큰은 오토가 대조군보다 많았다(claude 28,785 대 23,512, codex 27,791 대 23,296, both 30,818 대 23,512, 36시도 합). 시도당 약 100~150 토큰 차이로 provider 토큰의 1% 미만이다.
- H4: 키 문자열 0건(원자료, 표, 결과 전부 셸에서 센 값), 입력 불일치 0건. 허가 창이 멈춘 시도 4개(`c-haiku` 3, `c-opus` 1, 모두 바깥 저장소 경로를 읽으려 한 경우)는 우회가 아니라 차단이 동작한 것이다. 연습 폴더 밖 변경은 따로 재지 못했고 이 차단 수로만 본다.
- 코드 정정: 분석 코드가 처음에 허가 창 차단 수를 H4 실패로 썼다. 설계의 H4는 우회이므로 차단은 위반이 아니라고 고쳐 다시 분석했다. 판정은 바뀌지 않았다.

참고 대조(판정에 쓰지 않음): 오토는 가장 싼 고정 모델보다 비용이 크고(`c-haiku` 대비 +77%, `x-luna` 대비 약 +12,300%) 품질은 `c-haiku`(28/36 대 17/36)보다 높다. 가장 강한 고정 모델 `c-opus`보다는 비용 -59%, 성공 28/36 대 27/36이다. 이 비교는 오토가 아니라 기본 모델 선택(sonnet)의 효과다.

## 오토 경로

| 구간 | 층 | 오토 입력 | router 선택 적용 | 대체(`fallback`) | 기타 | `target_model` 확신도 최대 |
|---|---|---|---|---|---|---|
| 개발 | claude, codex, both | 12, 12, 12 | 0 | 12, 12, 12 | | 0.27, 0.23, 0.24 |
| 확인 | claude | 36 | 0 | 36 | | 0.32 |
| 확인 | codex | 36 | 0 | 35 | 1(화면 열기 실패로 입력 없음) | 0.20 |
| 확인 | both | 36 | 0 | 36 | | 0.23 |

Jev의 `target_model` 확률은 후보 사이에 퍼졌다(예: `b-auto`의 한 입력은 astra 0.31, luna 0.22, other 0.26). 후보 사이를 가르는 근거가 지시문에 없다고 Jev가 본 것이다. 확신도 0.6 문턱은 실제 모델 선택이 한 번도 적용되지 않게 막았다. #531이 기다리던 "Jev가 확신 있게 골라 적용되는 경로"는 이번 144개 오토 입력(개발 36, 확인 108)에서 관측하지 못했다.

반사실 재현(탐색, 판정에 쓰지 않음): 문턱을 없애고 `target_model` 1순위를 적용했다고 가정하고 같은 과제의 그 모델 고정 팔 결과를 쓰면, claude 층은 25과제에서 손실 0·이득 1, 비용 -10%[-20, -2], codex 층은 31과제에서 손실 0·이득 0, 비용 -7%[-17, 0]이고, both 층은 27과제에서 손실 3·이득 2, 비용 +153%다. 쌍 수가 줄어든 것은 1순위가 `other`이거나 해당 팔 결과가 없는 과제를 뺐기 때문이고 한 번씩의 표본이라 잡음이 크다. 새 session 열기와 캐시 손실은 빠져 있다. 문턱을 낮출 근거로 쓰지 않는다.

고정 모델 사이에 성공이 갈린 과제가 claude 층에서 15개, codex 층에서 1개다. claude 층은 haiku가 어려운 과제에서 떨어졌고, codex 층은 luna와 astra가 거의 같다. 즉 codex 층은 후보 사이 품질 차이가 이 과제에서 보이지 않아 모델 선택의 이득이 있어도 품질로는 드러나지 않는다. 비용만 luna가 astra의 1% 안팎이라 선택 이득은 비용에서만 생길 수 있는 층이다(코드 변경 과제에서 luna가 astra와 같은 성공률이었다는 뜻이며 일반 결론이 아니다).

## 한계

- 단일 사용자 계정의 한 번씩 실행. 같은 설정의 성공 변동이 3/36에서 5/36까지 보였으므로 품질 차이 3~5개는 모델 선택 효과로 읽지 않는다. 반복이 필요하다.
- 합성 파이썬 과제 9계열. `duration` 계열(확인 6과제)은 기준 해법이 지시문에 없는 동작("1 h"처럼 숫자와 단위 사이 공백을 허용)을 시험해 모든 팔이 거의 실패했다(48시도 중 1 성공). 계열이 모든 팔에 같이 영향을 줘 쌍 비교는 왜곡하지 않지만 절대 성공률을 낮추고 판별력을 줄였다. 사전 기준을 수집 뒤 바꾸지 않으므로 그대로 두었고 다음 실험에서 고친다.
- 개발 구간 최초 시도 3건은 세션 환경이 섞여(tmux 서버가 첫 세션의 환경을 쓴다) 다른 시도의 홈을 공유했다. 수집기를 고치고(세션 안에서 환경 지정) 원자료를 폐기한 뒤 처음부터 다시 수집했다. 고친 수집기는 개발 구간 첫 6시도를 돌린 뒤에 커밋됐다. 개발 구간은 지시문에 작업 폴더 경로를 붙이지 않았고 `c-haiku` 12시도 중 10시도가 바깥 경로를 읽으려다 허가 창에서 멈췄다(확인 구간은 경로를 붙여 3/36).
- 확인 구간에서 모델 응답 지연으로 600초를 넘긴 시도 4개(`delivery_unknown`)와 화면 열기 실패 1개(`x-auto`, 전송 전 재시도 후에도 실패)를 실패로 분모에 두었다. 전송 전 실패 재시도 6건(원자료 `infra`)은 입력이 가기 전이라 같은 입력을 두 번 보낸 것이 아니다.
- 시간은 작업자 세 개가 동시에 돌려 부하의 영향이 있다. 같은 시간대에 팔이 섞이도록 순서를 섞었다. 추론 깊이는 바꾸지 않았고(#531에서 미구현) 추론 깊이 조합은 미측정이다.
- 사용량이 비어 있는 시도 9개(허가 창 차단과 시간 초과)는 비용 분석에서 쌍을 뺐다(층마다 2~3쌍).

## 모델 id 확인

근거 목록의 `gpt-6.1-sol`과 provider 목록(`codex debug models`)의 `gpt-6-sol`은 같은 모델이 아니다. OpenAI 문서에서 `gpt-6-sol` 페이지가 "GPT-6.1 Sol이 더 새로운 Sol 모델"이라고 밝히고, `gpt-6.1-sol` 페이지는 `gpt-6-sol`을 별칭으로 적지 않는다. 실제로 `codex exec -m gpt-6.1-sol`은 ChatGPT 계정에서 "not supported"로 거절됐고 `gpt-6-sol`은 응답했다. 그래서 근거 목록은 고치지 않고(문서의 `gpt-6.1-sol` 항목이 맞다) 이번 실험 후보에서는 두 모델을 모두 뺐다. `gpt-6-sol`은 근거 목록에 항목이 없는 미검증 모델이다.

## 새로 알게 된 것

- `--plain` 출력은 처음 고르기 창을 열지 않아 첫 입력의 모델 후보 목록이 비고, 모든 오토 입력이 `no-candidates`로 기본 모델에 간다(예비 실행에서 확인). 모델 목록은 provider 연결을 맺거나 `/model`·처음 고르기 창을 열 때만 받아 둔다. 그래서 `model.default`를 설정 파일에 두고 오토를 켠 사용자의 첫 입력은 후보가 비어 있고, 연결이 없는 provider의 모델은 창을 열기 전까지 후보가 되지 않는다. #531에 댓글로 남긴다.
- `model.candidates`([#573](https://github.com/woonyong-choi/saturn/pull/573))가 있어야 후보를 근거 목록 안으로 고정할 수 있다.

## 다음 실험

1. 후보 사이의 품질 차이가 있는 과제(더 어려운 과제, 여러 파일)를 준비하고 `duration` 같은 지시문과 시험의 불일치를 기준 해법과 지시문 쌍으로 점검한다(계열마다 지시문만 보고 푼 사람 또는 모델의 통과 여부로 확인).
2. 같은 설정을 3회 이상 반복해 실행 변동을 따로 잰다. 손실 쌍 0 기준은 반복의 다수결 성공으로 비교한다.
3. router 선택이 적용되는 경로를 만든다. 지시문이 난이도를 드러내는 과제에서 Jev의 `target_model` 확신도 분포를 보고, 0.6 문턱이 맞는지는 별도 실험으로 정한다(이 실험의 반사실 재현은 근거가 아니다). 이 단계가 선행되어야 순효과를 잴 수 있다.
4. 시간 비교는 작업자 하나로 돌리거나 동시 실행 수를 고정해 부하를 통제한다.
