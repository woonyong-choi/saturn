## 결론

검증기는 설계한 세 가설을 모두 만족했다. 선택기의 효과는 판정 기준을 넘지 못했다. 이 표본으로는 어떤 선택기도 제품 기본값으로 켜지 않는다. Jev 선택은 어휘 검색보다 좋은 경향이 있었지만 사전 규칙의 결함 하나가 결과의 절반을 덮었고, 원문 전체 대비 토큰과 시간 이득은 없었다.

## 검증기 판정

| 가설 | 결과 | 판정 |
|---|---|---|
| H1 주입한 결함 16종을 모두 거절 | live 원자료에서도 16종 모두 거절했고 결함 없는 자료는 통과했다 | 채택 |
| H2 가공과 분석을 두 번 실행해 바이트 동일 | 분석 두 번의 출력이 같았다 | 채택 |
| H3 실패·시간 초과·미보고 사용량을 분모에 남김 | 192 trial이 모두 집계됐다. 제외 fixture 0, 재시도 0, 실패 0, 전송 불명 0. 사용량 미보고 호출 36건은 따로 센다 | 채택 |

실제 수집에서는 호출 실패와 시간 초과가 없어 실패 집계 경로는 stub 실행에서만 시험했다. 키 문자열은 원응답, 실험 폴더, 로그에서 0건이었다.

## 선택기 결과

봉인 평가 36과제 기준이다. 구간은 Wilson 95%다. 개발 12과제는 결과의 방향이 같고 [summary.json](results/summary.json)에 있다.

| 조건 | 후속 성공 | 의도한 선택기 적용 | 후속 입력 캐시 생성 토큰 | 선택·실행 시간 합 | 중앙 시간 |
|---|---|---|---|---|---|
| full | 36/36 [0.904, 1.000] | 해당 없음 | 99,860 | 117.0초 | 3.21초 |
| code | 21/36 [0.422, 0.729] | 해당 없음 | 45,026 | 126.1초 | 3.16초 |
| llm | 35/36 [0.858, 0.995] | 27/36, 대체 9 | 147,008(선택 호출 포함) | 233.6초 | 6.34초 |
| jev | 36/36 [0.904, 1.000] | 18/36, 대체 18 | 44,944, 별도 Jev 입력 76,224·출력 8,211 | 124.9초 | 3.34초 |

| 대응 비교 | 한쪽만 성공 | 성공 차이 |
|---|---|---|
| jev와 code | jev만 15, code만 0 | +41.7%p |
| jev와 full | 둘 다 0 | 0.0%p |
| llm과 code | llm만 14, code만 0 | +38.9%p |
| llm과 full | full만 1 | -2.8%p |

과제 종류별로 보면 전체 설정을 묻는 24과제(필요 블록 3개)에서 code 3/24, jev 24/24, llm 23/24, full 24/24다. 포트만 묻는 24과제(필요 블록 1개)는 네 조건 모두 24/24다.

## 판정

| 항목 | 판정 | 근거 |
|---|---|---|
| 검증기 오프라인 단계 | 채택 | 위 세 가설 충족 |
| Jev 선택의 효과 | 보류 | design.md는 이 표본에서 효과를 채택하지 않는다고 정했다(48과제, 계열 24). 판정 기준인 총 지연 15% 감소는 jev 124.9초 대 full 117.0초로 충족하지 못했다. 비용은 Jev 사용량 일부가 미보고라 완전한 합계를 만들 수 없어 절감을 주장하지 않는다. |
| 작업 LLM 선택 | 기각 | 토큰과 시간이 원문 전체보다 크고, 응답이 형식이나 3개 조건을 어겨 9건을 대체했다(대부분 필요한 블록이 하나뿐인 과제) |
| 자동 적용 | 켜지 않음 | 품질 유지는 full과 같았지만 시간·비용 이득이 없고, 적용률 50%는 규칙 결함으로 해석할 수 없다 |

## 관찰과 한계

사전 규칙 결함: 낮은 확신 규칙은 3번째로 높은 확률이 0.5 미만이면 대체한다. 필요한 블록이 1개인 과제에서는 Jev가 맞는 블록에 0.95, 나머지에 0.29 이하를 주고도 3번째 확률이 낮아 24건 모두 코드 검색으로 대체됐다. 따라서 jev 36/36 중 18건은 코드 검색의 결과이고, 포트 과제의 성공은 Jev의 기여가 아니다. 필요 블록이 3개인 과제에서 대체 없이 적용된 24건만 Jev의 선택이며 이 24건은 모두 성공했다(code는 3건). 설계는 수집 전에 봉인됐으므로 규칙을 바꾸지 않고 보고한다.

그 밖의 한계는 다음과 같다.

- 합성 과제의 전체 기록은 12블록 6,144바이트라 원문 전체도 작다. 선택으로 줄일 여지가 작아 토큰 이득이 시간으로 이어지지 않는다.
- 각 조합을 한 번씩만 실행했다. 시간 차이 몇 초는 반복 안정성을 확인한 값이 아니다.
- Jev 응답은 캐시 토큰을 보고하지 않아 36건이 미보고다. Jev 토큰과 Claude 토큰은 모델이 달라 더하지 않았다.
- USD 비용은 집계하지 않았다. Claude 원응답의 보고 비용은 원자료에 있다.
- 후속 실행 모델은 Claude Sonnet 하나다. Codex 경로와 Codex 사용량 매핑은 이 실행에서 부르지 않았으므로 미검증이다.

## 도구 조회를 포함한 실제 과제 계측

온라인 단계는 #538(전달 패킷 근거 기록)과 #539(근거 검색과 원문 조회)가 main에 들어간 뒤 실제 engine 경로로 수집했다. 설계와 수집기는 [수집 전 커밋](design.md#온라인-단계-도구-조회-실계측)했다. 집계는 [online-summary.json](results/online-summary.json), 원응답 해시는 [online-SHA256SUMS](data/online-SHA256SUMS)다.

| 항목 | 값 |
|---|---|
| 수집 | 2026-10-06, main `b3dae25`의 `saturn-engine` 릴리스 빌드, Claude 2.1.288(haiku)과 Codex 0.158.0(gpt-5.6-luna), TypeSafe Jev 1.13.0 |
| 표본 | 과제 `x000a` 하나, 받는 쪽 2 x 조건 3(`full`, `code`=RRF, `jev`) x 3회 = 18 trial, 방향마다 스냅샷 1개 |
| 호출 | provider 입력과 패킷 전달: Claude 19, Codex 20(상한 40). router 판단 27(상한 60). 보강 수집 3 trial을 더해 Claude 25, router 30. 재시도 0, 제외 0 |
| 미측정 | `llm` 조건은 engine에 작업 LLM 호출 연결이 없어 이 경로에 없다(미지원) |

### 계측 가설 판정

| 가설 | 결과 | 판정 |
|---|---|---|
| O1 trial이 온라인 계약을 통과 | 18건 모두 `input_id`, `run_id`, `session_id`, 모델 실제 이름, 패킷 해시가 있고 `validate_trial(online=True)`를 통과했다. 원응답 변조와 정답 누출 시험도 거절했다. | 채택 |
| O2 기록 저장소 행으로 재구성, 분석 바이트 일치 | 원자료만으로 trial 18건이 같게 다시 만들어지고 집계가 두 번 같았다. Claude는 `usage` 합이 요청 합계 알림과 9건 모두 같았다. Codex는 알림이 `usage`의 입력+출력보다 9건 중 8건에서 정확히 추론 토큰만큼 컸다(1건은 알림이 없었다). 사용량 목록은 Codex 출력에 추론이 이미 들어 있다고 보고 그대로 합쳤다. 알림 쪽 이중 계산 의심은 [#576](https://github.com/woonyong-choi/saturn/issues/576) | 채택(Codex 사용량 합계 규칙은 #576 확인 전까지 잠정) |
| O3 명령 수와 `evidence_lookups` 행 수가 같다 | 같지 않다. Codex 조회 명령 114개(`--help` 제외) 중 14개가 행을 남기지 않았다. 6개는 `\| tail`이 붙은 명령이고 단독 재현에서 `Could not reach a running engine`으로 실패했다([#574](https://github.com/woonyong-choi/saturn/issues/574)). 나머지 8개는 따옴표 없는 여러 단어 검색어를 CLI가 인자 오류로 거절한 것이다([#577](https://github.com/woonyong-choi/saturn/issues/577), 요청이 engine에 가지 않아 행이 없는 것이 맞다). Claude 보강 수집의 2개도 같은 여러 단어 거절이다. 두 원인을 빼면 명령과 행이 모두 맞았다. | 기각(원인 두 건을 이슈로 분리) |
| O4 조건은 패킷 구성만 바꾼다 | `full`은 후보 12개가 모두 전문, `code`와 `jev`는 모두 `Digest`(원문 전문 0개)였다. `jev`의 패킷 항목 선택 표시는 `compact`, `code`는 `rank`로 달랐다. 한도를 약 5,000토큰으로 잡았는데 근거가 블록 끝에만 있고 발췌가 앞 300글자라 전문이 한도 안에 하나도 들지 못했다. | 채택(한도가 너무 작아 조건 차이가 작았다) |

| 받는 쪽 | 조건 | 성공 | 패킷 항목 | 조회 명령 | 조회 행 | 읽은 서로 다른 블록 수(trial별) | 중앙 시간 | Restart 패킷 |
|---|---|---|---|---|---|---|---|---|
| Claude | full | 2/3 | 전문 12 | 0 | 0 | 0 | 10.8초 | 0 |
| Claude | code | 0/3 | 요약 12 | 0 | 0 | 0 | 13.7초 | 0 |
| Claude | jev | 0/3 | 요약 12 | 0 | 0 | 0 | 25.2초 | 0 |
| Codex | full | 3/3 | 전문 12 | 0 | 0 | 0 | 42.2초 | 0 |
| Codex | code | 0/3 | 요약 12 | 68 | 62 | 0, 12, 12 | 95.1초 | 0 |
| Codex | jev | 0/3 | 요약 12 | 46 | 38 | 0 | 72.9초 | 1 |

표본이 한 과제 3회라 성공률과 시간은 선택 방법의 효과로 읽지 않는다. 계측 점검에서 확인한 것은 다음과 같다.

- Claude haiku는 기본 18 trial에서 `saturn evidence`를 한 번도 쓰지 않았다. 패킷에 안내 한 줄이 있었지만 요약만 보고 값이 없다고 답하거나 질문을 되물었다(성공 0/6, 값 없음 답변 포함). 도구를 쓰지 않은 실행의 사용량과 시간도 같은 trial 행으로 기록됐다.
- Codex는 검색을 여러 번 한 뒤 읽기를 반복했고 `code`의 두 trial은 12개 블록을 모두 읽었다. 그런데도 둘 다 갱신된 포트 대신 이전 포트를 답했다(기대 6715, 답 6705). 읽은 범위를 끝 500~700글자로 줄이는 방식에서 갱신 문장이 아닌 이전 문장을 골랐다. 근거를 읽은 것과 맞게 답한 것은 따로 세야 한다.
- 사용량 호출 항목은 trial마다 부모 호출(Claude는 턴마다 `MainTurn`, Codex는 session마다 누적 마지막 값), 판단 호출(입력 판단과 `jev`의 `compact` 판단)이 호출 ID별 한 항목씩 들어갔다. router 판단은 캐시 필드가 없어 미보고(null)로 남고 trial 18건 모두 `unreported_calls`가 1 이상이다. Claude 사용량 합 입력+캐시 생성+출력은 `jev`가 `full`보다 컸다(router 판단 입력 약 9,400토큰이 더해진다).
- `jev`의 router 호출은 Claude 쪽 trial에서 입력 판단 1회와 `compact` 판단 1회, Codex 쪽 `Restart`가 있었던 trial은 한 번 더였다. router 판단 토큰이 trial마다 `usage`에 들어갔다.
- Codex `jev` r0에서 맥락이 한도를 넘어 `Restart` 패킷이 한 번 있었다. 이때 새 session의 사용량도 같은 trial에 포함했다.
- `jev` Codex r1은 요청 합계 알림이 원응답에 없었다(수집이 마지막 알림 전에 끝난 것으로 보인다). 이 trial의 사용량은 기록 저장소 행으로만 재구성했고 알림 대조는 하지 못했다.

### 보강 수집: Claude 도구 조회 계측

Claude의 조회 계측을 확인하려고 [설계 보강](design.md#보강-수집탐색)으로 입력에 조회 방법 한 줄을 더해 Claude 받는 쪽, 조건 `code`를 3회 추가 수집했다(탐색, 앞의 18 trial과 비교하지 않는다).

| trial | 조회 명령 | 조회 행 | 읽은 근거 블록 | 시간 | 사용량 합(입력 + 캐시 생성 + 출력) | 성공 |
|---|---|---|---|---|---|---|
| hint r0 | 3(검색) | 3 | 0 | 35초 | 22,144(요청 합계 알림과 같음) | 아니오(null 답) |
| hint r1 | 3(검색) | 2 | 0 | 23초 | 21,018(같음) | 아니오 |
| hint r2 | 4(검색) | 3 | 0 | 27초 | 22,784(같음) | 아니오 |

Claude는 안내를 받으면 `saturn evidence search`를 쓴다. 명령과 행의 차이 2개는 따옴표 없는 여러 단어 검색어를 CLI가 거절한 것이다(#577). 검색 결과만 보고 `read`로 원문을 읽지는 않아 답은 모두 null이었다. 조회 호출, 사용량(`MainTurn`), 시간, 검사 결과가 trial 행으로 맞게 기록된다는 점은 확인했고 사용량 합은 요청 합계 알림과 3건 모두 같았다. 읽기까지 가는 Claude 조회와 근거 블록을 읽은 뒤의 정답은 이 계측으로 확인하지 못했다.

### 가공 코드 수정

수집 뒤 가공 코드 두 곳을 고쳤다. 원응답은 바꾸지 않았다. (1) 패킷 항목의 기록 번호를 블록으로 옮기는 정규식을 `cat` 명령에서 파일 경로로 넓혔다. Codex는 파일 읽기를 명령 줄이 아니라 읽은 경로로 기록한다. (2) 조회 명령 수에서 `--help`를 뺐다(조회 행이 남지 않는 명령). 수정 뒤 가공과 검증을 다시 실행했다.

### 한계

- 과제 하나, 반복 3회, 모델 둘이다. 선택기의 효과나 비용 이득을 말하지 않는다.
- 패킷 한도를 근거가 요약에서 빠질 만큼 작게 잡아 `code`와 `jev`가 모두 같은 상태(요약만)에서 시작했고, 같은 한도에서 선택기 차이가 패킷 구성으로 드러나지 않았다. 다음 단계는 근거 블록이 한도 안에 들거나 빠지는 층을 만드는 설계가 필요하다.
- Codex 사용량 매핑은 입력, 캐시 읽기, 출력으로 맞췄고 추론 토큰은 출력에 포함된 값으로 간주했다. 포함 관계의 공식 확인은 #576에서 한다.
- `llm` 조건의 온라인 측정은 engine에 연결이 없어 하지 못했다.
- 같은 시각에 다른 작업자가 같은 provider 구독으로 실행을 돌리고 있어 시간은 상대 비교로도 흔들렸을 수 있다.

## 보존 우선 비교 연결: 측정과 예정

위 결과는 모두 보존 이전의 선택 비교와 도구 조회 계측이다. [보존 우선 비교](../context-preservation/design.md)의 96칸에는 이 실행기를 [연결](design.md#보존-우선-비교-연결)했지만 provider를 호출해 얻은 값은 아직 없다. 아래는 측정한 것과 예정인 것을 나눈 표다.

| 항목 | 상태 | 값 |
|---|---|---|
| 선택 비교 오프라인 검증(`all`) | 측정 | 192 trial 재가공, 16종 주입 결함 거절, 분석 두 번 바이트 일치. 이 변경 뒤에도 같다 |
| 보존 우선 장치 시험(`preserve-verify`) | 측정(가짜 기록) | 96칸 가짜 기록에서 48종 주입 결함 모두 거절, 분석 두 번 바이트 일치. 성공률과 비용은 의미 없는 값이다 |
| 현재 지원 범위의 실행 가능 칸 | 측정(코드와 문서 확인) | 20/96(다른 provider로 가는 R·J 중 interrupted-unknown 계열을 뺀 칸). 사유는 `no_full_packet_control` 24, `no_native_same_session_observable` 24, `forced_restart_trigger_unproven` 24, `interrupted_replay_unproven` 4. 20칸도 아직 실행하지 않았다 |
| 96칸 provider 실행, H1~H3 판정, 성공률·비용·시간 | 예정 | 값 없음. F·N 48칸은 engine에 능력이 생길 때까지 분모에만 남는다 |
| 독립 확인 평가 | 예정 | 진단과 분리해 사전 등록한다 |
| Claude·Codex 각각의 전달·검색·read·응답·사용량 대조 한 과제 | 부분 | 도구 조회 계측 18 trial과 보강 3 trial에서 확인했다. 보존 우선 경로에서는 아직 실행하지 않았다 |

남은 막힘은 다음과 같다. 같은 `P_send`에서 전문을 싣는 F 경로, N의 적용 경로 관측, 같은 provider 새 session을 매번 일으키는 설정의 사전 확인, 고정된 지점에서 실행을 끊는 interrupted-unknown 계열의 재생이다. 보낼 패킷 본문은 engine이 격리 홈에서 남기는 캡처로 확보한다([전달 패킷 근거](../../design/records.md#전달-패킷-근거)). 이는 engine이 내보낸 값이며 provider가 받았다는 증거가 아니다. 다른 provider로 가는 R·J 20칸의 수집기는 구현했지만 router 키와 두 CLI 로그인이 있는 환경에서 실제 engine으로 돌린 적이 없다. 수집기 시험은 가짜 기록, 가짜 호출 계수기, 사전 점검까지다. 시도 장부(중단 후 재시작에서 provider를 다시 부르지 않음, 재시작을 넘는 예약·계수, 세지 못한 값을 0으로 세지 않음)와 로그 읽기 사전 조건도 가짜 계수기로만 시험했고 20칸은 코드 경로일 뿐 실행하지 않았다. 실제 호출이 예약치를 넘으면 후속 칸을 중단하지만 예약치는 외부 과금의 절대 상한이 아니다. 패킷 캡처 폴더는 기존 폴더의 권한을 0700으로 바로잡고 심볼릭 링크를 따라가지 않는다.

## 다음 실험

1. 낮은 확신 규칙을 수집 전에 다시 정한다. 필요한 개수를 고정하지 않고 확률이 기준 이상인 블록만 예산 안에서 고르고, 기준 이상이 하나도 없을 때만 대체한다. 기준값은 개발 구간에서만 정하고 봉인 평가는 건드리지 않는다.
2. 후보를 실제 길이로 늘린다(수십~수백 블록, 블록당 수 KB). 전체 원문이 예산을 넘는 구간에서 토큰과 시간 이득이 생기는지 본다.
3. 조합마다 3회 이상 반복해 시간 분산을 본다. 계열 240개 이상을 사전 등록하고 표본 크기를 불일치율로 계산한다.
4. 온라인 단계는 한 과제 계측으로 끝났다. 효과 측정으로 넓히려면 먼저 #574(파이프가 붙은 조회 명령)와 #576(Codex 합계)을 닫고, 패킷 한도를 근거 블록이 들거나 빠지는 값으로 다시 정한다.

1~3은 [#541](https://github.com/woonyong-choi/saturn/issues/541)의 사전 등록 실험으로 이어진다.
