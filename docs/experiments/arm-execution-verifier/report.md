| 항목 | 값 |
|---|---|

| 수집 | 2026-10-06, Claude CLI Sonnet 240회와 TypeSafe Jev 1.13.0 48회(예약 상한 260회와 60회 이내, 호출 원장 288행) |

## 결론

검증기는 설계한 세 가설을 모두 만족했다. 선택기의 효과는 판정 기준을 넘지 못했다. 이 표본으로는 어떤 선택기도 제품 기본값으로 켜지 않는다. Jev 선택은 어휘 검색보다 좋은 경향이 있었지만 사전 규칙의 결함 하나가 결과의 절반을 덮었고, 원문 전체 대비 토큰과 시간 이득은 없었다.

## 검증기 판정

| 가설 | 결과 | 판정 |
|---|---|---|
| H1 주입한 결함 16종을 모두 거절 | live 원자료에서도 16종 모두 거절했고 결함 없는 자료는 통과했다 | 채택 |
| H2 가공과 분석을 두 번 실행해 바이트 동일 | 분석 두 번의 출력이 같았다 | 채택 |
| H3 실패·시간 초과·미보고 사용량을 분모에 남김 | 192 trial이 모두 집계됐다. 제외 fixture 0, 재시도 0, 실패 0, 전송 불명 0. 사용량 미보고 호출 36건은 따로 센다 | 채택 |

실제 수집에서는 호출 실패와 시간 초과가 없어 실패 집계 경로는 stub 실행에서만 시험했다. 키 문자열은 원응답, 실험 폴더, 로그에서 0건이었다.

## 선택기 결과

봉인 평가 36과제 기준이다. 구간은 Wilson 95%다. 개발 12과제는 결과의 방향이 같고 [summary.json](results/summary.json)에 있다.

| 조건 | 후속 성공 | 의도한 선택기 적용 | 후속 입력 캐시 생성 토큰 | 선택·실행 시간 합 | 중앙 시간 |
|---|---|---|---|---|---|
| full | 36/36 [0.904, 1.000] | 해당 없음 | 99,860 | 117.0초 | 3.21초 |
| code | 21/36 [0.422, 0.729] | 해당 없음 | 45,026 | 126.1초 | 3.16초 |
| llm | 35/36 [0.858, 0.995] | 27/36, 대체 9 | 147,008(선택 호출 포함) | 233.6초 | 6.34초 |
| jev | 36/36 [0.904, 1.000] | 18/36, 대체 18 | 44,944, 별도 Jev 입력 76,224·출력 8,211 | 124.9초 | 3.34초 |

| 대응 비교 | 한쪽만 성공 | 성공 차이 |
|---|---|---|
| jev와 code | jev만 15, code만 0 | +41.7%p |
| jev와 full | 둘 다 0 | 0.0%p |
| llm과 code | llm만 14, code만 0 | +38.9%p |
| llm과 full | full만 1 | -2.8%p |

과제 종류별로 보면 전체 설정을 묻는 24과제(필요 블록 3개)에서 code 3/24, jev 24/24, llm 23/24, full 24/24다. 포트만 묻는 24과제(필요 블록 1개)는 네 조건 모두 24/24다.

## 판정

| 항목 | 판정 | 근거 |
|---|---|---|
| 검증기 오프라인 단계 | 채택 | 위 세 가설 충족 |
| Jev 선택의 효과 | 보류 | design.md는 이 표본에서 효과를 채택하지 않는다고 정했다(48과제, 계열 24). 판정 기준인 총 지연 15% 감소는 jev 124.9초 대 full 117.0초로 충족하지 못했다. 비용은 Jev 사용량 일부가 미보고라 완전한 합계를 만들 수 없어 절감을 주장하지 않는다. |
| 작업 LLM 선택 | 기각 | 토큰과 시간이 원문 전체보다 크고, 응답이 형식이나 3개 조건을 어겨 9건을 대체했다(대부분 필요한 블록이 하나뿐인 과제) |
| 자동 적용 | 켜지 않음 | 품질 유지는 full과 같았지만 시간·비용 이득이 없고, 적용률 50%는 규칙 결함으로 해석할 수 없다 |

## 관찰과 한계

사전 규칙 결함: 낮은 확신 규칙은 3번째로 높은 확률이 0.5 미만이면 대체한다. 필요한 블록이 1개인 과제에서는 Jev가 맞는 블록에 0.95, 나머지에 0.29 이하를 주고도 3번째 확률이 낮아 24건 모두 코드 검색으로 대체됐다. 따라서 jev 36/36 중 18건은 코드 검색의 결과이고, 포트 과제의 성공은 Jev의 기여가 아니다. 필요 블록이 3개인 과제에서 대체 없이 적용된 24건만 Jev의 선택이며 이 24건은 모두 성공했다(code는 3건). 설계는 수집 전에 봉인됐으므로 규칙을 바꾸지 않고 보고한다.

그 밖의 한계는 다음과 같다.

- 합성 과제의 전체 기록은 12블록 6,144바이트라 원문 전체도 작다. 선택으로 줄일 여지가 작아 토큰 이득이 시간으로 이어지지 않는다.
- 각 조합을 한 번씩만 실행했다. 시간 차이 몇 초는 반복 안정성을 확인한 값이 아니다.
- Jev 응답은 캐시 토큰을 보고하지 않아 36건이 미보고다. Jev 토큰과 Claude 토큰은 모델이 달라 더하지 않았다.
- USD 비용은 집계하지 않았다. Claude 원응답의 보고 비용은 원자료에 있다.
- 후속 실행 모델은 Claude Sonnet 하나다. Codex 경로와 Codex 사용량 매핑은 이 실행에서 부르지 않았으므로 미검증이다.

## 도구 조회를 포함한 실제 과제 계측

하지 않았다. 이유는 다음과 같다.

- 생략한 기록을 ID로 다시 읽는 조회 경로는 #539(조건별 선택기와 원문 조회)가 머지된 뒤에 존재한다.
- 보낸 패킷과 항목 근거는 #538(PR #555)이 머지된 뒤에 조회할 수 있다.
- CLI 하나에 파일 읽기 도구만 켠 실행은 Saturn의 기록·권한 경로를 지나지 않아 완료 조건이 요구한 호출, 입력, cache, 출력, 검사, 시간 계측의 검증이 아니다. 검증하지 않은 채 했다고 쓰지 않는다.

이 항목은 미검증이며 #538과 #539 이후의 온라인 단계로 남긴다.

## 다음 실험

1. 낮은 확신 규칙을 수집 전에 다시 정한다. 필요한 개수를 고정하지 않고 확률이 기준 이상인 블록만 예산 안에서 고르고, 기준 이상이 하나도 없을 때만 대체한다. 기준값은 개발 구간에서만 정하고 봉인 평가는 건드리지 않는다.
2. 후보를 실제 길이로 늘린다(수십~수백 블록, 블록당 수 KB). 전체 원문이 예산을 넘는 구간에서 토큰과 시간 이득이 생기는지 본다.
3. 조합마다 3회 이상 반복해 시간 분산을 본다. 계열 240개 이상을 사전 등록하고 표본 크기를 불일치율로 계산한다.
4. 온라인 단계: #538과 #539 이후 같은 trial 행을 engine 경로로 채워 실제 검색, 재조회, 전체 사용량을 측정하고 Claude와 Codex 각각 도구 조회 한 과제를 먼저 확인한다.
