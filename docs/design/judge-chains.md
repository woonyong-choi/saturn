# judge 사슬

| 항목 | 값 |
|---|---|
| 상태 | 제안 |
| 관련 결정 | [판단 규격은 Saturn이 정하고 judge는 중립 이름과 출처로 기록한다](../decisions/2026-09-29-vendor-neutral-judge-spec.md), [판단 기록은 로컬에 쌓고 동의한 레코드만 서버로 올린다](../decisions/2026-09-29-local-first-judgment-collection.md) |

## 요약

judge 사슬은 앞 judge 호출의 답으로 다음 호출의 state, 선택지, 대상을 정하는 다단 판단이다. 좁혀 다시 읽기, 계층 내려가기, 검증 뒤 올리기의 세 모양이 있고 깊이는 2단까지다. 사슬은 1단 답을 항상 기록하므로 판단 기록만으로 "단발 판단과 사슬 중 어느 쪽이 맞았나"를 다시 계산할 수 있다. 질문, 기준값, 호출 규칙은 [judge](judge.md)를 따른다.

## 동기

지금 judge는 입력마다 한 번 불리고, 한 호출 안의 질문은 서로의 답을 보지 못한다. 그래서 세 가지가 어렵다.

- 질문마다 state를 좁히지 못한다. 기준 judge는 무관한 내용이 많은 큰 state와 여러 단계를 거치는 추론에서 정확도가 떨어진다([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md) 4, 5번).
- 확신도가 기준보다 낮으면 판단 전체를 버리고 대체 규칙으로 간다. 넓은 범주는 확실하고 세부만 모호한 경우에도 사용자가 직접 할 일이 늘어난다.
- 선택지가 늘거나 바뀌면 옛 답과 라벨이 깨진다([#68](https://github.com/woonyong-choi/saturn/issues/68)).

이미 `context-select`는 게이트 뒤 `fits_<n>`을 묻는 2단 판단이고, `file-rank`는 `answer_present`를 함께 묻는다. 이 문서는 이런 쓰임을 모양 셋으로 묶고, 각 모양이 효과가 있는지 판단 기록으로 확인하는 방법을 정한다.

## 예시

### skill 힌트를 두 번에 고를 때

1. 사용자가 "발표 자료 만들어 줘"를 입력한다.
2. 1단 호출이 skill 목록 전체를 한 줄씩 넣고 `skills`와 `needs_skill`을 묻는다.
3. `needs_skill`이 0.8이고 `skills` 상위 세 개가 `pptx-author`, `pptx-edit`, `docx`다.
4. 2단 호출이 세 skill의 설명 전문과 본문 앞부분만 state에 넣고 `skill_confirm`과 skill마다 `does_<n>`을 묻는다.
5. 2단이 `pptx-author`를 고르고, engine이 그 이름을 힌트 한 줄로 에이전트에 넘긴다.

### 모델은 모호하고 provider는 확실할 때

1. `target_model` 질문이 Claude 계열 모델 둘에 0.46, 0.44를 답해 확신도가 0.6 미만이 된다.
2. `core`가 같은 답에서 provider별 확률을 더해 Claude 0.90을 얻는다.
3. `core`는 현재 모델로 돌아가지 않고 Claude의 기본 모델을 고른다.
4. 판단 기록에는 선택지 답, 계산한 상위 답, 후퇴한 층이 함께 남는다.

### 싼 모델의 결과를 검증할 때

1. judge가 `difficulty`를 낮음으로 답해 빠른 모델이 턴을 맡는다.
2. 턴이 끝나면 engine이 턴 결과를 state에 넣고 `verify` 질문 세트를 부른다.
3. `claims_done_without_evidence`가 0.82로 기준 0.7을 넘는다.
4. TUI가 결과 옆에 `검증 신호: 완료 근거 없음 · 상위 모델로 다시 맡기기`를 보인다.
5. 사용자가 고르면 같은 입력이 상위 모델로 새 입력처럼 접수된다.

## 상세 설계

### 사슬을 쓰는 조건

- 같은 state에 대한 독립 질문은 지금처럼 한 호출에 묶는다. 13개 질문을 한 호출로 묶으면 따로 부를 때보다 12.2배 싸고 10.0배 빨랐고 답은 같았다([Parallel questions](https://docs.typesafe.ai/cookbooks/parallel_questions.md)).
- 2단 호출은 1단 답이 다음 호출의 state, 선택지, 대상을 바꿀 때만 만든다. 답을 보지 않고 미리 물을 수 있는 질문은 1단에 추측 질문으로 넣는다([Speculative fan-out](https://docs.typesafe.ai/patterns/fan-out.md)).
- 사슬 깊이는 2단까지다. 입력 경로의 지연이 호출 한 번만 늘게 하기 위해서다. 기준 judge 한 호출은 70~500ms로 알려져 있고 이는 벤더 주장이다([saturn-evidence EV-127](../archive/research/saturn-evidence.md)).
- 2단은 발동 조건을 만족할 때만 부른다. 발동 조건은 모양별로 정하고 판단 기록에 `trigger`로 남긴다.
- 1단 답만으로 행동할 수 있으면 2단을 부르지 않는다. 예를 들어 `needs_skill`이 0.3 미만이면 skill 2단을 생략한다.

### 모양 1: 좁혀 다시 읽기

1단이 전체 후보를 짧게 보고 상위 후보를 고르면, 2단이 그 후보의 자세한 내용만 state에 넣어 다시 판단한다. 2단은 후보 전부를 거부할 수 있다.

| 쓰는 곳 | 1단 | 2단 발동 조건 | 2단 state |
|---|---|---|---|
| `skills` | skill마다 한 줄, `needs_skill` | `needs_skill` 0.5 이상 | 상위 3개의 설명 전문과 본문 앞부분 |
| `context-select` | 게이트 `noul` 3개와 `pick` | 게이트 평균 0.3 이상 | 고른 후보의 원문 |
| `file-rank` | 파일 20개의 경로와 앞부분 | `answer_present` 0.35~0.7 | 상위 5개 파일의 관련 구간 |

- 근거: 182개 skill 목록에서 두 번 물어 고르면 틀린 skill을 읽는 비율이 16.8%에서 7.3%로, 맞는 skill이 없는데 읽는 비율이 9.8%에서 4.0%로 줄었다. 488건, 벤더 cookbook이다([Skill suggestion](https://docs.typesafe.ai/cookbooks/skill_suggestion.md)).

### 모양 2: 계층 내려가기와 후퇴

선택지를 트리로 두고 라벨은 잎 노드로 저장한다. 상위 노드의 확률은 자식 잎 확률의 합으로 코드가 계산한다. 선택지가 바뀌어도 잎 라벨과 상위 경로를 다시 쓰기 위해서다.

1. 잎이 255개 이하면 잎 전체를 `choice` 한 번에 묻는다.
2. 잎 확신도가 기준 이상이면 잎으로 행동한다.
3. 잎 확신도가 낮으면 한 층 위 노드의 확신도를 계산하고, 기준 이상이면 그 노드의 기본 행동을 따른다.
4. 어느 층도 기준에 못 미치면 질문별 대체 규칙을 따른다.
5. 잎이 255개를 넘으면 층마다 `choice`로 내려가며, 경로 3개를 유지해 한 호출에 함께 묻는다.

| 트리 | 상위 노드 | 상위 노드의 기본 행동 |
|---|---|---|
| `target_model` | provider | 그 provider의 기본 모델 |
| `relation_to_running` | 같은 작업(`refines`, `continues`), 다른 작업(`independent`, `conflicts`) | 같은 작업이면 현재 에이전트에 대기 뒤 전송 |
| `skills` | skill 묶음 | 묶음 이름을 힌트로 전달 |

- 후퇴 근거: 75개 산업군 분류에서 확신도 0.9 미만인 절반의 정답률 40%가 한 층 위로 보고하자 70%가 됐다. 60건, 추가 호출 없음, 벤더 cookbook이다([Classification using confidence](https://docs.typesafe.ai/cookbooks/classification_using_confidence.md)).
- 경로 유지 근거: 경로 3개를 유지하면 4개 계층 중 4개, 가장 높은 자식만 따라가면 2개가 기대한 잎에 닿았다. 4건이라 방향만 보여 준다([Hierarchical classification](https://docs.typesafe.ai/cookbooks/hierarchical_classification.md)).
- 경로 점수는 간선 확률의 기하평균이다. 깊이가 다른 잎을 공정하게 비교하기 위해서다.

### 모양 3: 검증 뒤 올리기

빠른 모델이 끝낸 턴을 judge가 항목별 `noul`로 검증하고, 어느 한 항목이라도 기준을 넘으면 상위 모델로 올리기를 제안한다.

- 검증 질문은 "문제가 있다"가 yes가 되게 쓴다. 예: `claims_done_without_evidence`, `ignored_user_constraint`, `left_failing_test`.
- 올리기 판정은 항목 확률의 최댓값으로 한다. 평균을 쓰면 확실한 신호 하나가 묻히기 때문이다.
- 올리기는 제안만 하고 자동으로 보내지 않는다. 같은 작업이 사용자 모르게 두 번 실행되는 일을 막기 위해서다.
- 근거: 작은 모델 추출, judge의 필드별 검증, 추론 모델로 올리기의 3단으로 추론 모델 품질의 대부분을 일부 비용으로 얻었다. 벤더 내부 결과다([SDE cascade](https://docs.typesafe.ai/cookbooks/sde_cascade.md)).
- 검증 state에는 턴 결과 전체가 아니라 마지막 답과 도구 결과 요약만 넣는다. 턴 결과 안의 문장이 judge에 지시로 읽히는 일을 줄이기 위해서다([Jev 1.13 jaggedness](https://docs.typesafe.ai/model-jaggedness/jev-1.13.md) 6번).

### 앞 판단을 state에 넣는 규칙

- 앞 호출의 답은 `inferred` 아래에 선택한 값과 확신도만 넣고, 관측한 사실은 `observed` 아래에 둔다. judge가 추정을 사실로 읽는 일을 막기 위해서다.
- 앞 호출의 확률 분포 전체와 질문 문장은 넣지 않는다. state를 작게 두기 위해서다.
- 2단 호출 직전에 채팅 revision을 다시 비교한다. 다르면 사슬 전체를 `superseded`로 기록하고 [입력 처리](input-handling.md)의 다시 판단 규칙을 따른다.

### 사슬 기록

판단 기록에 다음 칸을 더한다. 기존 칸과 출처, 사용 제한 규칙은 [judge](judge.md)를 따른다.

| 칸 | 뜻 |
|---|---|
| `chain_id` | 한 사슬의 호출을 묶는 id |
| `step` | 1 또는 2 |
| `parent_call_id` | 2단이 참조한 1단 호출 |
| `trigger` | 2단을 부른 발동 조건 이름 |
| `applied_step` | 실제 행동에 쓴 단 |
| `backoff_level` | 모양 2에서 행동에 쓴 층. 잎이면 0 |

- 1단 답은 2단이 있어도 항상 기록한다. 1단 답이 곧 "사슬이 없었다면 한 행동"이므로 같은 입력에서 단발과 사슬을 비교할 수 있기 때문이다.

### 근거 뽑기

각 모양은 먼저 기록만 하는 단계로 켠다. 이 단계에서는 2단도 호출하고 기록하지만 행동은 지금 규칙대로 1단 답으로 정한다. 효과는 [judge 학습](judge-training.md)의 틀림 신호와 놓침 신호로 잰다.

| 가설 | 비교 대상 | 지표 | 채택 조건 |
|---|---|---|---|
| 모양 1이 skill, 파일 선택을 고친다 | 1단과 2단 답이 다른 건 | 사용자가 교정한 값이 2단 답과 같은 비율 | 1단 답과 같은 비율보다 높고 차이의 95% 신뢰구간이 0을 넘음 |
| 모양 2 후퇴가 대체 규칙보다 낫다 | `backoff_level` 1 이상인 건 | 후퇴 행동의 틀림 신호율, 대체 규칙으로 간 비율 | 틀림 신호율이 잎 기준 행동보다 높지 않고 대체 규칙 비율이 줄어듦 |
| 모양 3이 싼 모델의 실패를 잡는다 | 검증 신호가 켜진 턴과 꺼진 턴 | 뒤이은 사용자 재요청, 되돌리기 비율 | 켜진 턴의 재요청 비율이 꺼진 턴보다 높음 |
| 사슬 지연이 견딜 만하다 | 2단을 부른 입력 | 접수부터 전송까지 p95 | 단발 대비 증가가 1초 이하 |

- 비교 건수가 200건을 넘으면 `/judge version` 화면에 모양별 지표를 보인다.
- 지표 계산은 기준 judge의 답을 Saturn 모델 학습 라벨로 쓰지 않는다. 사용자 신호끼리 비교하는 계산이라 약관 제약은 [judge 학습](judge-training.md)의 출처 규칙을 그대로 따른다.

### 오류 처리

| 상황 | 동작 |
|---|---|
| 2단 호출 실패, 무응답 | 1단 답과 질문별 대체 규칙으로 행동하고 `trigger`와 실패 사유를 기록한다. |
| 2단 답 `invalid` | 1단 답으로 행동하고 2단을 `invalid`로 기록한다. |
| 1단과 2단 사이 revision 변경 | 사슬 전체를 `superseded`로 기록한다. |
| 검증 호출 실패 | 검증 신호 없이 턴 결과를 그대로 보인다. |

### 요구사항

| 요구사항 | 검증 계획 |
|---|---|
| 사슬은 2단을 넘지 않는다. | 2단 답이 다시 발동 조건을 만족해도 3단 호출이 없는지 확인한다. |
| 2단이 있어도 1단 답을 기록한다. | 2단을 부른 입력마다 `step` 1과 2 기록이 모두 있는지 확인한다. |
| 상위 노드 확률은 자식 잎 확률의 합이다. | 잎 분포를 넣고 계산한 provider 확률이 합과 같은지 확인한다. |
| 올리기는 사용자 선택 없이 보내지 않는다. | 검증 신호가 켜진 턴에서 새 입력이 자동 접수되지 않는지 확인한다. |
| 2단 실패는 1단 답으로 처리한다. | 2단에 실패와 `invalid`를 주고 행동이 1단 규칙대로인지 확인한다. |

## 단점

- 2단을 부른 입력은 판단 지연이 호출 한 번만큼 늘어난다.
- 질문 세트가 단별로 나뉘어 버전과 대응표 관리가 늘어난다.
- 1단이 후보를 잘못 좁히면 2단이 고칠 수 없다. 모양 1의 2단 후보 수가 이 오류의 상한을 정한다.

## 대안

- 계층의 층마다 항상 호출하는 방식은 대부분의 입력에서 한 번이면 되는 판단의 호출 수와 지연을 늘려 버렸다.
- 확신도가 낮을 때 추론형 LLM에 텍스트로 묻는 방식은 입력마다 수 초의 지연과 비용이 들어 입력 경로에서 버렸다.

## 미해결 질문

- 2단 발동 구간을 고정 값으로 둘지, 기록만 하는 단계의 결과로 질문마다 정할지 ([#68](https://github.com/woonyong-choi/saturn/issues/68))
- 검증 뒤 올리기를 제안으로만 둘지, 사용자가 켠 폴더에서는 자동으로 보낼지 ([#68](https://github.com/woonyong-choi/saturn/issues/68))
- 관계 판단의 상위 노드가 다른 작업일 때 기본 행동을 보조 에이전트로 할지, 대기로 둘지 ([#36](https://github.com/woonyong-choi/saturn/issues/36))
