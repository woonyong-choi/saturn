## 배경

제약을 풀거나 바꾸는 판단을 어떻게 할지 정해야 했다. 기록 없는 대화에서 새 입력이 기존 제약을 대체하거나 합치는지 자동으로 판단하면 대체 정밀도가 0~1.6%였다([constraint-relation](../experiments/constraint-relation/report.md)). 사용자가 `제약 등록됨` 줄을 보고 풀어 달라고 말하는 흐름은 Jev가 요청 식별 정밀도 100%, 선택형 질문 하나로 쌍별 질문보다 +5.7%p 더 맞혔다([constraint-cancel-request](../experiments/constraint-cancel-request/report.md)). 다만 `이번 작업만`이나 조건부 요청을 영구 해제로 처리하면 잘못된 해제가 된다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 등록 기록을 본 사용자의 요청을 Jev 선택형 질문 하나로 판단하고 예외 종류까지 묻는다 | 해제 요청 재현율 96.8%(사후 계산), 응답 0.28초, 비용이 가장 낮다 | 종류 구분 정확도 87.8%여서 사용자가 줄에서 고쳐야 한다 |
| 같은 판단을 저렴한 LLM(Haiku)에 맡긴다 | 문장 이해가 넓다 | 종합 정확도 84.0% 대 91.2%, 응답 10.4초, 비용 약 100배([constraint-exception-judge](../experiments/constraint-exception-judge/report.md), 둘 다 사후 계산) |
| 기록 없이 새 입력과 기존 제약을 쌍으로 비교해 자동 대체·합침 | 사용자 입력이 필요 없다 | 대체 정밀도 0~1.6% |

## 결정

판단은 Jev로 한다. 등록은 `is_constraint` 0.8 이상이면 자동, 0.7 이상 0.8 미만이면 사용자에게 묻고, 0.7 미만이면 하지 않는다([근거](../experiments/constraint-human-check/report.md)). 기록 없는 대화의 대체·합침 자동 판단은 쓰지 않는다. 해제와 예외는 사용자가 등록 줄을 본 뒤 하는 입력을 선택형 질문 하나로 판단해 요청 여부, 대상, 종류(영구 해제, 이번 작업 예외, 조건·범위 예외)를 정한다. 예외는 대화 기록 줄로 보이고 `/constraints`에서 종류를 바꾸거나 되돌린다. 권한 모드 `full`에서는 묻지 않고 줄에 `확인 없이`를 표시한다.

## 결과

- 대체와 합침이 없어져 질문, 기준값 세 개, 상태 하나, 표 열이 줄고 예외 표가 하나 는다.
- 새 제약이 앞 제약과 부딪치면 둘 다 유효로 남고 사용자가 정리한다.
- 입력의 절반가량이 AI가 쓴 지시문이라 작업 하나에만 해당하는 규칙이 많다. 대응은 정하지 못했다.

## 다시 볼 조건

- 종류 구분 정확도가 90% 이상으로 오르거나, 사용자가 예외 줄에서 종류를 자주 고쳐 자동 적용이 부담이 되는 때
- 독립 프로젝트 표본에서 0.8과 0.7의 정밀도가 크게 다를 때
