## 배경

패킷, 결과 전달, 파일 순위는 후보 중 관련 항목을 골라야 한다. 이전 결정은 RRF 순위의 상위 N개만 router에 물어 요청 크기를 고정했다. router 전체 판단을 50세트(후보 5,943개, 남긴 항목 400개)에서 모은 측정에서 남긴 항목 중 RRF 상위 10개에 든 비율은 12.0% [9.2, 15.6]였고 무작위 기대값은 8.7%였다. 상위 40개도 44.5% [39.7, 49.4]였고, 95%에 닿으려면 세트당 후보 중앙값 127개보다 많은 132~133개가 필요했다([#116](https://github.com/woonyong-choi/saturn/issues/116)). 기준 router의 입력 비용은 100만 토큰당 $0.042이고 같은 질문의 일치율은 98.4%였다. 요청은 64K, `state`와 가장 긴 질문의 합은 32K를 넘으면 나눠 보내야 한다(2026-09-29 확인).

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| router가 후보 전체를 판단하고 순위는 대체 순서로만 쓴다 | router 전체 판단과 같은 결과, 순위 품질과 무관한 결과 | 후보 수에 비례하는 질문 수, 여러 건으로 나뉘는 요청 |
| RRF 상위 N=40을 유지한다 | 전체의 3분의 1 안팎인 질문 수 | router가 남길 항목의 절반 이상을 보지 않는 구조 |
| 상위 N을 후보 수에 맞춰 늘린다 | 질문 수 조절 | 후보 수와 비슷한 N, 전체를 묻는 것과 작은 차이 |

## 결정

router가 후보 전체를 판단하게 한다. RRF 순위는 router가 답하지 못한 항목의 순서와 같은 확률일 때의 순서에만 쓴다. router 결과의 완전성과 순위 품질에 기대지 않는 것을 가장 중요하게 본다.

## 결과

- 후보 전체를 묻는 `compact`와 `file-rank` 질문
- 크기 한도를 넘는 요청을 질문 단위로 나누고 조각마다 같은 state를 싣는 규칙
- 남긴 항목은 확률이 높은 순, 같은 확률이면 RRF 순
- 답이 없는 항목의 RRF 순 후미 배치, router 전부 실패 때 RRF 순서로 예산까지 채우기
- 상위 N 설정 `context.select.router_top_n` 제거
- 후보 수에 비례하는 router 입력 토큰과 지연
- 나뉜 요청마다 같은 state를 보내는 입력 토큰

## 다시 볼 조건

- 후보 수가 커져 전체를 묻는 요청의 비용이나 지연이 한 입력의 대기 시간으로 받아들이기 어려움
- [후보 순위와 router 결합의 전환 품질 측정](https://github.com/woonyong-choi/saturn/issues/117)에서 router 전체 판단이 순위 보조 없이 전환 품질을 낮춤
