## 배경

사용자가 화면을 꺼도 작업은 계속되어야 했다. 엔진은 공급자 연결, 대기열, 판단기, 기록을 맡았다. 엔진에 붙는 쪽은 화면(`tui`), 명령(`cli`), 나중의 데스크톱 앱으로 여럿이었다. 기록 저장소는 SQLite 파일 하나에 쓰는 프로세스를 하나로 두는 규칙을 따랐다. Codex의 전체 화면도 app-server에 붙는 클라이언트로 동작했다(2026-09-29 확인).

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 상주 엔진과 Unix 소켓 JSON-RPC | 화면 종료 뒤 작업 계속, 여러 화면 동시 접속, 사용자당 엔진 하나로 쓰기 프로세스 하나 유지 | 엔진 잠금, 소켓 연결, 약속 버전 관리 |
| 화면 프로세스 안에 엔진 포함 | 프로세스 하나, 약속 정의 불필요 | 화면 종료 때 작업 중지, 화면마다 공급자 연결과 기록 쓰기 중복 |

## 결정

상주 엔진과 Unix 소켓 JSON-RPC를 골랐다. 화면을 끈 뒤의 작업 계속, 여러 화면의 동시 접속이 기준이었다.

## 결과

- 화면을 꺼도 접수된 대기 입력의 순서대로 처리
- 화면과 앱은 공급자를 모르고 Saturn 용어만으로 표시
- `saturn-tui`와 `saturn-cli`의 엔진 비의존을 Cargo로 강제
- 엔진 수명 관리(사용자당 잠금, 유예 뒤 종료) 부담
- 엔진 RPC 메서드 정의 작업 추가

## 다시 볼 조건

- 지원 운영체제에서 Unix 소켓 사용 불가
- 여러 화면 동시 접속을 쓰는 사용 사례 없음
