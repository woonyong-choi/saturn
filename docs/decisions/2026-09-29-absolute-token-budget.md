# compaction 기준을 절대 토큰 예산으로 정한다

| 항목 | 값 |
|---|---|
| 날짜 | 2026-09-29 |
| 상태 | 채택 |
| 대체 | 없음 |
| 관련 문서 | [아키텍처](../architecture.md), [맥락 정리](../design/context-management.md) |

## 배경

맥락이 커지면 provider 압축이나 새 session 재시작으로 맥락 정리(compaction)를 해야 한다. Claude Code 기본 모델의 맥락 창은 1M이다(2026-09-29 확인). Codex 기본 모델 계열의 맥락 창은 272K다(2026-09-29 확인). 두 창 크기는 약 3.7배 차이가 난다. Chroma의 "Context Rot"(2025)는 18개 모델 모두 입력이 길수록 성능이 떨어진다고 보고한다. "Lost in the Middle"(2023)은 정답이 가운데 있을 때 정확도가 75.8%에서 53.8%로 떨어진다고 보고한다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 절대 토큰 예산 `T = min(T_abs, N% × 창 크기)` | 창 크기와 무관한 품질 기준, 길이에 따른 성능 저하 연구와 일치 | provider별 `T_abs` 값 측정 필요 |
| 창 크기 대비 비율 N% | 설정 값 하나로 두 provider 공통 적용 | 같은 비율에서 1M 창의 맥락이 700K까지 누적 |

## 결정

절대 토큰 예산 `T = min(T_abs, N% × 창 크기)`를 쓴다. 성능 저하가 창 대비 비율이 아니라 절대 길이를 따른다는 연구 결과를 가장 중요하게 본다.

## 결과

- 두 provider에 같은 길이 기준 적용
- provider별 `T_abs`와 공통 `N` 두 설정 관리
- 활성 맥락을 측정하지 못하는 경로는 provider 자동 압축에 의존
