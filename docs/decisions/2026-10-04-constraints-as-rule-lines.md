## 배경

사용자가 앞서 정한 제약을 새 session에 넘기려면 제약을 식별하고, 저장하고, 뒤집힌 제약을 정리하고, 패킷 자리 안에서 골라야 한다. 입력 원문을 그대로 제약으로 등록하면 일과 제약이 섞인 입력이 패킷의 자리를 차지하고, 제약이 쌓일수록 고정 구역이 넘친다. 제약 판단은 router 확률이라 틀릴 수 있고, 잘못 해제하거나 대체한 제약은 새 session이 알 수 없다. 사용자가 모르게 등록하거나 지우면 무엇이 지켜지는지 알 수 없다. 간접 지시 입력의 `is_constraint` 정확도는 74.5% [68.0, 80.0]이고, `replaces_<n>` 0.5 이상 0.8 미만 구간은 부분 변경과 대체가 섞여 질문 하나로 가르지 못했다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 입력 원문에서 코드로 자른 규칙 한 줄과 적용 범위로 저장하고, 상태를 이벤트로 이어 쓰고, 낮은 확신은 사용자에게 묻는다 | 원문이 정본이라 뜻이 바뀌지 않고, 변경이 보이고 되돌릴 수 있고, 잘못 정한 제약이 줄어든다 | 문장 나누기 질문이 늘고, 묻는 구간만큼 사용자 입력이 든다 |
| 입력 전체 원문을 제약으로 저장한다 | 구현이 단순하다 | 섞인 입력이 패킷을 길게 만들고 제약이 쌓이면 자리를 못 지킨다 |
| LLM으로 규칙 한 줄을 요약해 저장한다 | 한 줄이 가장 짧다 | 호출과 출력 비용이 들고 원문 대신 생성문이 정본이 되어 뜻이 바뀔 수 있다 |
| 확신이 낮아도 기준값 하나로 자동 결정한다 | 사용자를 방해하지 않는다 | 잘못 해제한 제약을 아무도 모르고, 되돌릴 근거가 없다 |

## 결정

제약은 입력 원문에서 코드가 자른 규칙 한 줄과 적용 범위로 저장한다. 상태는 유효, 해제, 대체이고 같은 뜻은 합치며, 모든 변경은 이벤트로 이어 쓰고 대화 기록에 한 줄로 남겨 `/constraints`에서 되돌릴 수 있다. 패킷의 제약 칸은 상한 안에서 전체 제약, 지금 작업 범위와 겹치는 제약, 관련도와 최신 순으로 채우고 넘치면 생략한 수를 표시한다. 확신이 기준보다 낮으면 등록, 해제, 대체를 자동으로 하지 않고 그 자리에서 사용자에게 묻는다. 사용자가 보지 못한 채 제약이 바뀌는 일과 잘못 지운 제약을 가장 중요하게 본다.

## 결과

- 제약 표, 이벤트 표, 확인 표, 예외 표, 전환별 패킷 제약 표 다섯 개가 기록 저장소에 생기고 스키마가 한 번 올라간다.
- `route` 요청에 질문 둘이 늘고, 기존 제약이 있으면 판단 요청이 한두 번 더 간다.
- 사용자는 확신이 낮은 판단에서 질문을 받는다. 묻는 구간 값은 긴 대화 실측으로 정한다.
- 패킷 제약 칸 상한을 넘는 제약은 새 session에서 빠지고 빠진 수가 보인다.

## 다시 볼 조건

- 긴 대화 실측에서 묻는 구간의 사용자 답이 대부분 router의 우세한 쪽과 같아 질문이 불필요함
- 문장 나누기 질문의 재현율이 낮아 입력 전체 원문 등록이 잦음
- 규칙 한 줄이 앞 말에 기대어 혼자 뜻이 통하지 않는 입력이 많음
